이 글은 `bluetape4k-exposed` 시리즈의 1편입니다. 처음부터 Exposed가 정답이라고 정해둔 것은 아닙니다.
JPA, MyBatis, R2DBC, Vert.x SQL Client, 가상 스레드까지 실제로 검토하고 예제를 만들어 보면서
"운영 코드에서 오래 가져갈 수 있는 방식"을 찾았습니다.

그 과정에서 중심에 둔 선택지가 Exposed였고, 그 위에 운영에서 반복해서 필요했던 저장소, R2DBC, JSON/암호화,
캐시, 멀티테넌시 경계를 얇게 붙인 것이 `bluetape4k-exposed`입니다.

Part 1의 질문은 단순합니다.

> JPA도 있고, MyBatis도 있고, R2DBC도 있고, Vert.x SQL Client도 있는데 왜 Exposed인가?

이 질문은 "DSL이 예쁘다" 정도로 답하면 부족합니다. 실제 출발점은 제가 비동기·논블로킹 데이터 접근
라이브러리를 고르던 과정이었습니다. WebFlux를 붙였는데 내부 DB 접근이 블로킹이면 이벤트 루프가 기다립니다.
R2DBC를 붙이면 논블로킹 I/O는 얻지만 SQL DSL과 Kotlin 사용성이 다시 아쉬워집니다. 가상 스레드를
쓰면 블로킹 JDBC를 유지하면서 대기 비용을 낮출 수 있지만, SQL을 안전하게 만들 도구가 필요합니다.

그 중간 지점에 Exposed가 있었습니다. SQL을 감추지 않으면서 Kotlin DSL로 안전하게 쓰고, 필요하면 JDBC와 R2DBC
양쪽을 워크로드에 맞게 선택할 수 있었기 때문입니다.

## 출발점: JDBC는 블로킹 방식이다

JDBC는 동기 방식입니다. 요청이 DB 응답을 기다리는 동안 스레드는 그 작업에 묶입니다. 트래픽이 늘고 DB
응답 시간이 늘어나면 애플리케이션 서버를 증설하는 방식으로 버티는 경우가 많았습니다.

한동안 NoSQL로 우회하는 선택도 많았습니다. MongoDB, Cassandra, Elasticsearch 같은 저장소는 자기 영역에서
강합니다. 하지만 모든 주 저장소를 NoSQL로 바꾸면 스키마 변경, 예외 업무, 운영 노하우, 백오피스성 수작업에서
다른 비용을 냅니다. 결국 많은 서비스는 다시 관계형 데이터베이스를 주 저장소로 둡니다. DB가 약해서가 아니라,
오히려 DB가 충분히 강하고 운영하기 편하기 때문입니다.

문제는 그 다음입니다. Spring WebFlux 같은 비동기·논블로킹 웹 프레임워크를 쓰면서 내부 DB 접근은 JDBC/JPA로
블로킹하면, API 입구만 비동기고 안쪽은 줄 서는 구조가 됩니다. 이벤트 루프가 DB 대기에 시간을 쓰기 시작하면
응답성 개선을 기대했던 구조가 오히려 위험해집니다. 흔히 말하는 Reactor meltdown 쪽으로 갑니다. 이름부터
운영자가 반길 만한 단어는 아닙니다.

그래서 저는 선택지를 제가 시도해봤던 순서와 운영에서 걸렸던 지점으로 나눠 봤습니다.

| 선택지 | 장점 | 걸리는 지점 |
|---|---|---|
| Hibernate Reactive | ORM 경험을 리액티브 쪽으로 가져갑니다 | Vert.x 기반이라 학습 비용과 생태계 제약이 있습니다 |
| Vert.x SQL Client | I/O 중심 논블로킹 DB 접근이 깔끔합니다 | SQL 문자열과 매핑 코드를 직접 다루는 부담이 큽니다 |
| Spring Data R2DBC | Spring 리액티브 스택에 자연스럽습니다 | JPQL/QueryDSL/Exposed 같은 SQL DSL이 약하고 Reactor 타입이 앞에 나옵니다 |
| JPA + 가상 스레드 | 기존 블로킹 API를 크게 바꾸지 않습니다 | JPA의 무거운 매핑과 SQL 제어 문제는 그대로 남습니다 |
| Exposed + 가상 스레드 | JDBC 드라이버 성숙도와 Kotlin SQL DSL을 같이 씁니다 | 블로킹 JDBC 경계는 여전히 이해하고 측정해야 합니다 |
| Exposed R2DBC + 코루틴 | suspend/Flow 기반으로 Exposed SQL DSL을 씁니다 | 드라이버와 워크로드별 성능 차이를 반드시 봐야 합니다 |

여기서 결론은 "R2DBC가 틀렸다"가 아닙니다. 반대로 "가상 스레드가 모든 걸 이긴다"도 아닙니다.
서비스의 형태나 요구사항에 따라 선택이 달라집니다. 스트리밍과 배압이 핵심이면 R2DBC가 낫고,
기존 JDBC 드라이버의 배치 처리, 익숙한 트랜잭션 경계, 단순한 호출 스택이 더 중요하면 JDBC + 가상 스레드가
더 편할 수 있습니다.

## Exposed에서 기대한 것

저는 JPA처럼 큰 ORM 세계가 필요했던 것이 아닙니다. 복잡한 도메인 그래프와 지연 로딩을 모두 맡기는 방식보다,
SQL 문을 알고 있는 개발자가 Kotlin 코드로 안전하게 쿼리를 작성하는 쪽이 더 맞았습니다. 그 지점에서 Exposed의
SQL DSL이 잘 맞았습니다.

```kotlin
val rows = Users
    .selectAll()
    .where { Users.email eq email }
    .orderBy(Users.id)
    .limit(1)
    .toList()
```

문자열 SQL을 줄이는 것은 단순 취향 문제가 아닙니다. 컬럼 이름, 타입, join 조건, where 조건이 코드 안에서
검사되면 운영에서 만나는 사소한 오타가 줄어듭니다. SQL을 전혀 모르게 해주는 추상화가 아니라, SQL을 더
안전하게 쓰게 해주는 Kotlin DSL에 가깝습니다.

DAO도 쓸 수 있습니다. 단건 조회나 단순 관계는 `EntityClass`로 간결하게 표현할 수 있습니다. 다만 운영 코드에서는
복잡한 쿼리, 트랜잭션 경계, 캐시, 라우팅, 관측성이 같이 움직입니다. 그래서 이 시리즈에서는 DAO 자체보다
SQL DSL과 저장소 경계를 더 앞에 둡니다.

## bluetape4k-exposed에 붙인 층

`bluetape4k-exposed`는 Exposed를 대체하려고 만든 것이 아닙니다. 중심에는 여전히 JetBrains Exposed가 있습니다.
제가 붙인 것은 운영 서비스에서 계속 다시 만들던 조각입니다. 아래 개요 다이어그램은 그 경계를
한눈에 보이도록 그린 것입니다.

<figure class="bt4k-architecture">
  <img src="/assets/bluetape4k-exposed-readme-overview-ko.png" alt="bluetape4k-exposed 루트 README의 주요 기능 개요 다이어그램" loading="lazy" />
  <figcaption>Exposed는 SQL DSL과 트랜잭션을 맡고, bluetape4k-exposed는 저장소, 캐시, JSON, 암호화, 다이얼렉트, Spring Boot 연결 경계를 나눕니다.</figcaption>
</figure>

| 영역 | 대표 확장 | 맡는 일 |
|---|---|---|
| 저장소 | `exposed-jdbc`, `exposed-r2dbc` | JDBC/R2DBC 저장소 추상화, 감사/소프트 삭제 계열 |
| 캐시 | `exposed-cache`, `exposed-jdbc-caffeine`, `exposed-r2dbc-lettuce` | 로컬/Redis 캐시를 붙인 읽기 경로 |
| 컬럼 코덱 | `exposed-jackson2`, `exposed-jackson3`, `exposed-fastjson2`, `exposed-tink` | JSON 컬럼, 암호화 컬럼, 측정 단위 컬럼 |
| 다이얼렉트 | `exposed-postgresql`, `exposed-mysql8`, `exposed-bigquery`, `exposed-clickhouse`, `exposed-trino`, `exposed-duckdb` | DB별 SQL/커넥터 보조 기능 |
| Spring Boot | `exposed-spring-boot-jdbc`, `exposed-spring-boot-r2dbc`, `exposed-spring-boot-batch` | Boot 4 자동 설정과 애플리케이션 연결 |

사용할 때도 필요한 것만 가져오는 방식을 권합니다.

```kotlin
dependencies {
    implementation("io.github.bluetape4k.exposed:bluetape4k-exposed-jdbc:1.9.2")
    implementation("io.github.bluetape4k.exposed:bluetape4k-exposed-r2dbc:1.9.2")
    implementation("io.github.bluetape4k.exposed:bluetape4k-exposed-jdbc-lettuce:1.9.2")
    implementation("io.github.bluetape4k.exposed:bluetape4k-exposed-jackson2:1.9.2")
    implementation("io.github.bluetape4k.exposed:bluetape4k-exposed-spring-boot-jdbc:1.9.2")
}
```

제가 의도한 사용법은 "다 가져오라"가 아닙니다. JDBC 저장소만 필요하면 JDBC만 가져옵니다. 캐시 기반
읽기 경로가 필요하면 캐시 어댑터를 붙입니다. Spring Boot 자동 설정이 필요할 때만 Boot 모듈을 붙입니다.
이 정도 거리는 유지해야 라이브러리가 프레임워크인 척하지 않습니다.

## 숫자를 보고 선택하자

데이터 접근 라이브러리 선택에서 가장 위험한 문장은 "이론적으로 더 빠르다"입니다. 이론은 방향만 줍니다.
운영 선택은 측정값으로 다시 봐야 합니다.

그래서 저는 예제와 벤치마크를 같이 둡니다. `exposed-workshop`의 가상 스레드/JDBC 벤치마크 노트에서는
대표 수치를 이렇게 잡았습니다. 여기서는 절대값보다 배율을 먼저 보겠습니다.

<figure class="bt4k-architecture">
  <img src="/assets/bluetape4k-exposed-part1-virtual-thread-chart-ko.png" alt="가상 스레드가 인덱스 SELECT 2.54배, 복잡 쿼리 1.79배, 10ms I/O 지연 2.27배, CPU 중심 작업 1.03배를 개선한 벤치마크 차트" loading="lazy" />
  <figcaption>가상 스레드는 CPU 중심 작업보다 I/O 대기가 있는 JDBC 워크로드에서 의미가 커집니다.</figcaption>
</figure>

| 워크로드 | 가상 스레드 향상 배율 |
|---|---:|
| 단순 인덱스 SELECT | 2.2-2.6x |
| 복잡 쿼리, UPDATE + 집계 | 1.8x |
| 10ms I/O 지연 시뮬레이션 | 2.3x |
| CPU 중심 작업 | 1.02-1.03x |

이 수치는 "가상 스레드를 켜면 모든 코드가 빨라진다"가 아닙니다. I/O 대기 중 캐리어 스레드를 반납할 수
있을 때 효과가 큽니다. 반대로 CPU 중심 작업은 거의 좋아지지 않습니다. 그러니 JDBC + 가상 스레드 선택은
블로킹 API를 유지하면서 대기 비용을 낮추는 선택이지, CPU 성능을 공짜로 올리는 버튼이 아닙니다.

`bluetape4k-exposed` 자체에도 `kotlinx-benchmark` 기반 `ExposedJdbcBenchmark`를 넣었습니다. PostgreSQL
Testcontainers, HikariCP 최대 24, JMH 처리량 조건에서 단건 CRUD와 JOIN, 배치 삽입을 측정합니다.

<figure class="bt4k-architecture">
  <img src="/assets/bluetape4k-exposed-part1-jdbc-benchmark-chart-ko.png" alt="Exposed JDBC 벤치마크 처리량 차트: singleFindById 15000 ops/s, singleInsert 14400 ops/s, singleUpdate 14300 ops/s, joinQuery 1510 ops/s, batchInsert 217 ops/s" loading="lazy" />
  <figcaption>Exposed JDBC 방식도 쿼리 종류에 따라 처리량이 크게 다릅니다. 단건 CRUD와 JOIN/배치를 같은 기준으로 보면 안 됩니다.</figcaption>
</figure>

| 벤치마크 | 처리량 |
|---|---:|
| `singleFindById` | 15,000 ops/s |
| `singleInsert` | 14,400 ops/s |
| `singleUpdate` | 14,300 ops/s |
| `joinQuery` | 1,510 ops/s |
| `batchInsert` | 217 ops/s |

이 표는 JDBC와 R2DBC의 최종 승부표가 아닙니다. 그 이야기는 Part 3에서 배치 벤치마크와 함께 따로 보겠습니다.
Part 1에서 필요한 결론은 이것입니다. Exposed를 고를 때도 추상 계층 이름만 보지 말고, 쿼리 모양과
드라이버 처리 방식, 커넥션 풀, 트랜잭션 경계를 같이 측정해야 합니다.

JPA와의 비교군도 넣었습니다. `exposed-workshop/11-high-performance/04-benchmark`에서는 PostgreSQL
Testcontainers, JMH 평균 지연 시간 조건으로 Person 단건 CRUD와 관계 CRUD를 비교했습니다. 아래 차트는 단건 CRUD
일부입니다. 지연 시간은 낮을수록 좋습니다.

<figure class="bt4k-architecture">
  <img src="/assets/bluetape4k-exposed-part1-jpa-comparison-chart-ko.png" alt="Exposed와 JPA 단건 CRUD 평균 지연 시간을 create, read, update, delete, batchCreate로 비교한 차트" loading="lazy" />
  <figcaption>같은 PostgreSQL 조건에서 단건 CRUD는 Exposed가 JPA보다 3.9-8.3배 낮은 지연 시간을 보였습니다.</figcaption>

| 연산 | Exposed | JPA | 해석 |
|---|---:|---:|---|

이 결과가 "JPA를 쓰지 말자"는 뜻은 아닙니다. JPA는 복잡한 도메인 그래프, 2차 캐시, Spring Data 생태계가
중요할 때 여전히 강합니다. 다만 SQL 제어와 낮은 ORM 오버헤드가 중요하면 Exposed가 충분히 설득력 있는
비교군이라는 뜻입니다.

## 워크숍을 같이 둔 이유

블로그 글만 보고 데이터 접근 계층을 바꾸면 위험합니다. 예제가 작으면 실제 문제를 숨깁니다.
그래서 저는 이 시리즈에서 `exposed-workshop`, `exposed-r2dbc-workshop`, 운영 예제를 계속 같이 연결합니다.

| 저장소 / 장 | 코드에서 볼 것 |
|---|---|
| `exposed-workshop/02-alternatives-to-jpa` | R2DBC, Vert.x, Exposed를 왜 비교했는지 코드로 봅니다 |
| `exposed-workshop/03-exposed-basic` | Exposed DSL/DAO의 기본 사용법을 직접 따라갑니다 |
| `exposed-workshop/08-coroutines` | 코루틴, 가상 스레드 경계를 비교합니다 |
| `exposed-workshop/10-multi-tenant` | 테넌트 격리, 라우팅 데이터소스, 캐시 격리를 봅니다 |
| `exposed-workshop/11-high-performance` | 캐시 전략과 벤치마크 중심 예제를 봅니다 |
| `exposed-workshop/12-production-integration` | outbox, 멱등성, 관측성, 준비 상태 경계를 봅니다 |
| `exposed-r2dbc-workshop` | 같은 설계를 R2DBC/코루틴 방식에서 다시 봅니다 |

특히 운영 예제에서는 캐시 전략과 멀티테넌시를 중심에 두었습니다. 설계 그림에서 끝내지
않고, 실행 결과와 성능 차트까지 같이 두려는 의도입니다. 캐시는 "빠르겠지"로 붙이면 안 됩니다. 테넌트 ID가
캐시 키에 빠지는 순간 성능 최적화가 아니라 데이터 유출 후보가 됩니다. 이건 느린 것보다 더 나쁩니다.

## 맺음말

제가 `bluetape4k-exposed`를 만든 이유는 Exposed가 모든 문제를 대신 풀어주기 때문이 아닙니다. 오히려 반대입니다.
Exposed는 SQL을 SQL답게 남겨두면서 Kotlin 타입 시스템과 DSL로 안전하게 다루게 해줍니다. 그 위에
`bluetape4k-exposed`로 저장소, 캐시, JSON/암호화 컬럼, 다이얼렉트, Spring Boot 연결을 붙였습니다.

그래서 저는 선택 기준을 이렇게 잡습니다.

- SQL을 문자열보다 Kotlin DSL로 안전하게 쓰고 싶다.
- JDBC + 가상 스레드와 R2DBC + 코루틴을 워크로드별로 고르고 싶다.
- 캐시, JSON, 암호화, 다이얼렉트, Spring Boot 연결을 매번 새로 만들고 싶지 않다.
- 벤치마크와 워크숍 예제로 실제 성능과 운영 경계를 확인하고 싶다.

다음 글에서는 JDBC 저장소와 SQL DSL 패턴을 보겠습니다. 제가 저장소 추상화를 만든 이유는 SQL DSL을 숨기기 위해서가
아니라, 반복되는 매핑과 페이징, 소프트 삭제 경계를 매번 새로 만들지 않기 위해서였습니다. 그 경계를 어디서 나눴는지
코드로 보겠습니다.
