월요일 오전, 피부과의 레이저 장비 `L-02`가 점검 대상으로 전환됐습니다. 오후까지 이 장비를 사용하는 예약은
여덟 건입니다. 여섯 건은 앞으로 14일 안에 대체 시간을 찾을 수 있지만, 두 건은 같은 의사와 진료 항목에 맞는
빈시간이 없습니다.

이 상황을 “장비 고장 → 예약 시간 변경”으로 줄이면 운영에 필요한 판단이 사라집니다.

- 장비 사용 중단 기간과 실제로 겹치는 예약은 무엇인가?
- 후보 계산이 끝난 뒤 원래 예약이 다른 작업으로 바뀌지 않았는가?
- 대체 후보가 없거나 스트림이 중간에 끊긴 예약은 누가 확인하는가?
- 후보를 골랐다는 사실과 환자가 변경에 동의했다는 사실을 같은 것으로 봐도 되는가?
- 병원 책임으로 바뀐 예약을 환자의 예약 신뢰도에 불리하게 반영하지 않는가?

예약 복구는 날짜 필드 하나를 수정하는 기능이 아닙니다. **영향 범위 확인, 대체 후보 계산, 쓰기 직전 재검증,
상태 변경, 운영자 확인**을 서로 다른 단계로 나눠야 합니다.

## 장비 충돌을 찾는 일과 예약을 복구하는 일은 다르다

장비 사용 중단은 먼저 충돌 조회로 확인합니다. 현재 `EquipmentUnavailabilityService`는 등록된 사용 불가 일정의
적용 기간을 계산하고, 같은 장비를 사용하는 예약 가운데 그 기간과 겹치는 예약을 반환합니다. 새 일정을 저장하기
전에는 `previewConflicts`로 예상 충돌을 확인할 수도 있습니다.

```text
GET  /api/{tenantCode}/clinics/{clinicId}/equipments/{equipmentId}/unavailabilities/{id}/conflicts
POST /api/{tenantCode}/clinics/{clinicId}/equipments/{equipmentId}/unavailabilities/preview-conflicts
```

이 API의 결과는 **영향을 받을 수 있는 예약 목록**입니다. 예약 상태를 `PENDING_RESCHEDULE`로 바꾸거나 대체
후보를 만들지는 않습니다. 충돌 조회와 재배정을 하나의 작업으로 합치면, 운영자가 범위를 검토하기 전에 쓰기가
시작될 수 있고 장비 일정 수정과 예약 복구의 실패 원인도 구분하기 어렵습니다.

휴진 복구 경로는 별도로 동작합니다. `ClosureRescheduleService`는 특정 날짜의 활성 예약을 읽고 대체 후보를 만든
뒤, 현재 상태를 다시 확인해 복구 대기로 전환합니다. 현재 구현의 이름은 휴진을 기준으로 하지만, 장비 장애
운영 화면에서도 먼저 충돌 범위를 확정한 뒤 같은 재배정 경계를 참고할 수 있습니다. 장비 충돌 API가 휴진
재배정 서비스를 자동 호출한다고 이해해서는 안 됩니다.

## 후보 계산과 상태 변경 사이에 버전 확인이 필요하다

동기식 `processClosureReschedule`은 처리 비용이 큰 후보 계산을 트랜잭션 밖에서 수행합니다. 순서는 다음과
같습니다.

1. 병원이 요청한 테넌트 범위에 속하는지 확인한다.
2. 휴진 날짜의 활성 예약 ID와 예약 스냅숏을 읽고, 영향 예약 수의 상한을 확인한다.
3. 예약 수와 `searchDays`로 후보 계산량을 제한한다.
4. 의사·진료 항목·날짜가 같은 조회는 캐시하면서 대체 빈시간을 계산한다.
5. 쓰기 트랜잭션을 시작하고 활성 예약을 다시 읽는다.
6. 예약 수, ID, `status`, `version`이 처음 읽은 스냅숏과 같은지 확인한다.
7. 각 예약의 버전을 조건으로 갱신(CAS)해 `PENDING_RESCHEDULE`로 바꾸고, 상태 이력·상태 이벤트·후보를 저장한다.

후보 계산이 트랜잭션 밖에 있다는 말은 오래된 계산 결과를 그대로 쓴다는 뜻이 아닙니다. 계산하는 동안 환자가
예약을 취소하거나 다른 직원이 상태를 바꿀 수 있으므로, 쓰기 직전에 처음 읽은 스냅숏과 현재 행을 다시
대조합니다. 어느 예약이든 달라졌다면 동기식 일괄 작업 전체를 롤백합니다.

이 구조는 트랜잭션을 짧게 유지하면서도 “처음 확인한 영향 범위 전체가 아직 같은가?”를 하나의 조건으로
보호합니다. 후보 계산을 긴 트랜잭션 안에 넣으면 DB 연결과 잠금을 오래 유지합니다. 반대로 재검증 없이
트랜잭션 밖 계산만 믿으면 이미 취소되거나 변경된 예약을 복구 대기로 되돌릴 수 있습니다.

## 동기식 일괄 처리와 스트리밍은 실패 범위가 다르다

운영 화면은 같은 휴진 복구를 동기식 요청이나 SSE 스트림으로 시작할 수 있습니다. 두 경로는 진행률 표시만
다른 것이 아닙니다.

| 구분 | 동기식 `processClosureReschedule` | 스트리밍 `streamClosureReschedule` |
| --- | --- | --- |
| 후보 계산 | 전체 영향 예약의 후보를 트랜잭션 밖에서 먼저 계산 | 예약별 트랜잭션 안에서 계산 |
| 쓰기 범위 | 모든 영향 예약을 하나의 트랜잭션으로 저장 | 예약마다 별도 트랜잭션으로 저장 |
| 동시 변경 | 전체 스냅숏이 달라지면 일괄 롤백 | 해당 예약의 CAS가 실패하면 그 예약을 건너뜀 |
| 진행 이벤트 | 응답이 끝날 때 전체 결과 반환 | 예약별 커밋 뒤 `progress` 이벤트 전송 |
| 연결 중단 | 요청 전체의 성공·실패로 판단 | 이미 커밋된 예약은 남고, 아직 시작하지 않은 예약은 중단될 수 있음 |

스트리밍 경로는 예약별 트랜잭션이 커밋된 뒤 DB 연결을 반환하고 `onProgress`를 호출합니다. 따라서 SSE
전송이 느려져도 DB 연결을 잡은 채 기다리지 않습니다. 대신 스트림이 중간에 끊기면 “화면에서 마지막으로 본
순번”만으로 전체 실패를 선언하면 안 됩니다. 이미 커밋된 예약과 아직 처리하지 못한 예약을 서버 상태로 다시
대조해야 합니다.

동기식 경로가 필요한 때는 영향 범위 전체를 함께 바꾸거나 전혀 바꾸지 않아야 할 때입니다. 스트리밍 경로는
처리 시간이 길고 운영자가 진행 상황을 봐야 할 때 유용하지만, 예약별 부분 성공을 후속 작업에 포함해야 합니다.
두 경로를 같은 원자성으로 설명하면 복구 시 잘못된 재실행이나 중복 확인이 생깁니다.

## 운영 화면은 목록보다 다음 작업을 먼저 보여줘야 한다

영향 예약을 시간순으로 나열하기만 하면 `STAFF`는 후보가 있는 예약과 없는 예약, 이미 상태가 바뀐 예약을 매번
직접 구분해야 합니다. 운영 화면은 병원 단위 사건과 처리 결과를 먼저 요약하고, 다음 작업이 다른 항목을 조치
큐로 나눠 보여줘야 합니다.

이번 화면 시안은 다음 정보를 한 흐름으로 배치합니다.

- 사건 원인, 영향 시간 범위, 후보 검색 기간
- 영향 예약 수, 후보가 있는 예약 수, 후보가 없는 예약 수
- `PENDING_RESCHEDULE`, 후보 수, 다음 작업을 함께 보여주는 조치 큐
- 선택한 예약의 익명 참조값과 읽기 시점의 `currentVersion`
- 우선순위, 날짜·시간, 의사와 장비를 함께 보여주는 대체 후보
- 후보 선택, 자동 재배정, 후보 없음 별도 처리
- 현재 구현과 아직 구현하지 않은 운영 경계

`currentVersion`은 화면이 읽은 상태를 설명하는 근거입니다. 현재 확정 API가 클라이언트의
`expectedVersion`을 입력으로 받는다는 뜻은 아닙니다. 확정 서비스가 원본 예약을 다시 읽고, 그 버전을 내부 CAS
조건으로 사용합니다. 화면은 이 차이를 숨기지 않아야 API 계약과 실제 동시성 제어를 혼동하지 않습니다.

## 후보 선택과 자동 재배정은 같은 확정 경계를 사용한다

`STAFF`는 예약별 후보 목록에서 대체 시간을 하나 선택할 수 있습니다. 자동 재배정은 별도의 마법 같은 최적화
단계가 아니라, 현재 후보 가운데 우선순위가 가장 높은 항목을 고른 뒤 같은 확정 로직을 호출합니다. 후보가
없으면 `null`을 반환하므로 “자동 재배정 버튼을 눌렀다”는 사실만으로 성공 처리하면 안 됩니다.

확정 트랜잭션은 다음 작업을 함께 수행합니다.

1. 후보가 원본 예약과 같은 요청 테넌트·병원 범위에 속하는지 확인한다.
2. 후보 의료진이 원본 예약과 같은 병원에 속하는지 확인한다.
3. 후보 날짜와 시간으로 새 예약을 `CONFIRMED` 상태로 생성한다.
4. 원본 예약을 현재 버전을 조건으로 갱신(CAS)해 `RESCHEDULED` 상태로 바꾼다.
5. 원본 예약의 상태 이력을 기록한다.
6. 선택한 후보를 다시 선택할 수 없도록 표시한다.
7. 변경 알림을 아웃박스(outbox)에 기록한다.

원본 예약의 상태나 버전이 중간에 바뀌면 CAS가 실패하고 트랜잭션은 완료되지 않습니다. 새 예약만 남거나 원본만
`RESCHEDULED`가 되는 부분 성공을 허용하지 않는 이유입니다.

다만 현재 확정 경계에는 중요한 제한이 있습니다. 새 예약은 바로 `CONFIRMED`로 생성됩니다. 환자에게 대체
일정을 제안하고 동의를 기록한 뒤 확정하는 별도 단계는 이 경로에 연결되어 있지 않습니다. 운영 화면의 “이
후보로 재배정”은 현재 구현을 표현한 버튼이지, 환자 동의 근거가 이미 수집됐음을 증명하는 버튼이 아닙니다.

## 정책에 적혀 있다는 것과 실행 경로가 지킨다는 것은 다르다

예약 정책 모델에는 `DisruptionRecoveryPolicy`가 있습니다. 이 정책의
`preserveConfirmedAppointment=true`는 고객이 대체 일정을 수락하거나 명시적으로 취소하기 전까지 기존 확정
방문 약속을 유지해야 한다는 비활성화 불가 조건입니다. validator도 이 값이 `true`가 아니면 테넌트 기본 정책을
거부하고, 병원별 재정의에서는 이 항목을 바꿀 수 없게 제외합니다.

그러나 현재 `ClosureRescheduleService.confirmReschedule`은 이 정책을 읽지 않습니다. 후보를 확정하면 대체
예약을 바로 `CONFIRMED`로 만들고 원본을 `RESCHEDULED`로 바꿉니다. 따라서 다음 두 문장을 구분해야 합니다.

- **현재 정책 모델:** 기존 확정 방문 약속을 고객 동의 없이 변경하지 않는 원칙을 표현하고 검증한다.
- **현재 재배정 확정 경로:** 그 정책과 동의 근거를 입력으로 받지 않고 후보를 즉시 확정한다.

운영 절차로 환자 동의를 먼저 확인할 수는 있지만, 시스템이 그 근거를 강제하고 감사 가능한 데이터로 보존한다고
말할 수는 없습니다. 정책 모델과 쓰기 경로가 연결되기 전까지는 운영 준비 항목으로 남겨야 합니다.

## Timefold 결과 반영은 별도의 원자적 쓰기 경로다

여러 예약을 한꺼번에 최적화할 때는 `SolverService.optimizeReschedule`을 사용할 수 있습니다. 그러나 solver가
계산한 배치 결과를 화면에서 봤다는 사실만으로 DB에 반영하면 안 됩니다. 계산 뒤 다른 작업이 원본 예약을 바꿀
수 있기 때문입니다.

`applyOptimizedAssignments`는 원본 행의 버전을 잠근 트랜잭션에서 확인하고, 각 배치를 버전을 조건으로
갱신(CAS)합니다. 하나라도 오래된 결과이거나 갱신이 실패하면 전체를 롤백하고 `false`를 반환합니다.

이 경로는 `ClosureRescheduleService`의 후보 선택·확정과 같은 API가 아닙니다. 한쪽은 후보를 저장하고 `STAFF`가
선택한 대체 예약을 새로 만드는 경로이고, 다른 쪽은 solver가 계산한 기존 예약 배치를 원본 버전 보호 조건과
함께 반영하는 경로입니다. 운영 화면에서 둘을 하나의 “자동 최적화” 버튼으로 합치려면 결과 모델과 실패
의미부터 통일해야 합니다.

## 병원 책임과 환자 보상도 자동으로 연결되지 않는다

장비 고장과 휴진은 환자가 만든 사건이 아닙니다. 예약 신뢰도 모델의 책임 값에는 `CLINIC`과
`OPERATIONAL_EXCEPTION`이 있으며, 환자 책임으로 확인된 이벤트만 신규 예약 제한의 근거에 포함해야 합니다.
병원 사정으로 바뀐 예약이 환자의 노쇼나 늦은 취소처럼 계산되면 복구가 또 다른 불이익을 만듭니다.

보상도 별도의 판단입니다. 대기 목록 운영 API에는 복구 크레딧(recovery credit)을 부여하고 취소하는 경로가
있지만, 휴진이나 장비 충돌이 발생했다고 자동으로 복구 크레딧을 만들지는 않습니다.

```text
POST /api/{tenantCode}/clinics/{clinicId}/waitlist/recovery-credits
POST /api/{tenantCode}/clinics/{clinicId}/waitlist/recovery-credits/{recoveryCreditRef}/revoke
```

보상이 필요한지, 어떤 근거와 승인으로 얼마 동안 적용할지는 병원 운영 정책이 정해야 합니다. 예약 복구
트랜잭션 안에서 임의로 보상까지 만들면 재배정 실패와 보상 실패의 원자성, 중복 지급, 취소 권한을 함께 해결해야
합니다. 현재는 독립된 기능으로 다루는 편이 정확합니다.

## 현재 구현과 후속 작업을 같은 문장에 섞지 않는다

| 구분 | 확인된 범위 |
| --- | --- |
| **현재 구현** | 장비 사용 불가 기간과 충돌 예약 조회, 휴진 영향 예약 탐색, 동기식 일괄 후보 계산·재검증·원자적 저장, 예약별 스트리밍 처리, 수동·자동 후보 확정, solver 결과의 원자적 반영 |
| **현재 정책 모델** | 운영 장애 자동 제안 여부와 지연 한도, 기존 확정 방문 약속 보호 조건, 병원별 재정의 제한 |
| **운영 준비** | 장애 원인과 영향 범위 승인, 후보 없음 조치 큐, 스트림 중단 뒤 상태 대조, 환자 연락과 동의 확인, 병원 책임 분류, 보상 승인 |
| **후속 개선** | 동의 근거를 포함한 제안→수락→확정 단계, 재배정 확정 경로의 `DisruptionRecoveryPolicy` 적용, 복구·알림·보상 사이의 감사 가능한 상관관계 |

이 표에서 가장 중요한 부분은 “정책 모델이 있으므로 현재 확정 경로도 이미 동의를 강제한다”라고 쓰지 않는
것입니다. 반대로 동기식 일괄 처리의 스냅숏 재검증과 롤백, 스트림의 예약별 커밋처럼 이미 구현된 안전장치를
단순한 향후 계획으로 낮춰서도 안 됩니다.

## 정리

병원 사정으로 예약을 바꿔야 할 때 운영자가 필요한 것은 변경 버튼 하나가 아닙니다.

- 장비 충돌 조회는 영향 예약을 찾을 뿐, 자동으로 재배정하지 않는다.
- 동기식 휴진 복구는 후보를 트랜잭션 밖에서 계산하고, 전체 스냅숏을 다시 확인한 뒤 한 번에 저장한다.
- 스트리밍 복구는 예약별로 커밋하므로 연결 중단 뒤 이미 처리된 예약과 남은 예약을 대조해야 한다.
- 후보 선택과 자동 재배정은 같은 확정 트랜잭션을 사용하며, 대체 예약은 현재 바로 `CONFIRMED`가 된다.
- 정책 모델은 기존 확정 방문 약속 보호를 요구하지만, 현재 확정 경로가 환자 동의 근거를 강제하지는 않는다.
- solver 결과 반영과 복구 크레딧은 각각 별도의 경계다.
- 병원 책임 사건은 환자의 예약 신뢰도 불이익으로 이어지지 않아야 한다.

운영 화면은 더 많은 정보보다 명확한 정보를 제공해야 합니다. 어떤 예약이 영향을 받았는지, 후보가 있는지,
지금 실행할 수 있는 작업은 무엇인지, 실행 뒤 어떤 상태를 다시 확인해야 하는지를 한 흐름으로 보여줘야 합니다.
그래야 병원 운영자, PO, 개발자가 같은 화면을 보면서 현재 구현과 다음 개선을 구분할 수 있습니다.
