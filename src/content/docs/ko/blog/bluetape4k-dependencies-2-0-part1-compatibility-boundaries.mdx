<p class="bt4k-post-meta">2026-09-06 · bluetape4k-dependencies 2.0.0 활용기 · Part 1</p>

`bluetape4k-dependencies 2.0.0`은 여러 라이브러리의 안정판을 하나의 검증된 조합으로 선택합니다. 그렇다고
BOM이 Java runtime이나 애플리케이션 코드를 대신 migration해 주는 것은 아닙니다. 버전 한 줄을 올리기 전에
호환성 경계를 먼저 확인해야 합니다.

```kotlin
dependencies {
    implementation(platform("io.github.bluetape4k:bluetape4k-dependencies:2.0.0"))
    implementation("io.github.bluetape4k:bluetape4k-core")
}
```

## 업그레이드 전에 답할 질문

다음 중 하나라도 해당하면 단순한 dependency refresh로 끝나지 않습니다.

- 서비스 runtime이 Java 21–24인가?
- `bluetape4k-virtualthread-api` 타입을 직접 import하거나 binary API에 노출했는가?
- QueryDSL Q 타입을 Kotlin source에서 생성하는가?
- Spring Boot MongoDB 연결을 `spring.data.mongodb.uri`로 설정했는가?
- Testcontainers에서 custom Ignite2 image의 tag를 생략했는가?

`2.0.0`은 이런 차이를 fallback으로 숨기지 않습니다. build 또는 startup에서 빨리 드러내는 쪽을 선택합니다.

## 2.0.0이 선택한 릴리스

중앙 [2.0.0 release](https://github.com/bluetape4k/bluetape4k-dependencies/releases/tag/2.0.0)는 다음 주요 안정판을
한 catalog에 고정합니다.

| Library | Version |
| --- | ---: |
| `bluetape4k-projects` | `2.0.0` |
| `bluetape4k-exposed` | `2.0.0` |
| `bluetape4k-aws` | `1.0.0` |
| `bluetape4k-image` | `1.0.0` |
| `bluetape4k-text` | `1.0.0` |
| `bluetape4k-graph` | `1.0.0` |
| `bluetape4k-javers` | `1.0.0` |
| `bluetape4k-leader` | `1.0.0` |

같은 catalog는 Kotlin `2.4.10`, Spring Boot `4.1.0`, Exposed `1.4.0`도 선택합니다. 이 숫자를 “새 기능 목록”으로
읽기보다, 함께 빌드하고 검증한 compatibility line으로 읽는 편이 정확합니다. 개별 기능의 근거는 각 라이브러리의
release source와 테스트입니다.

## Java 25 바닥선과 Java 21 호환 영역

[`bluetape4k-projects 2.0.0`](https://github.com/bluetape4k/bluetape4k-projects/releases/tag/2.0.0)은 일반 published
artifact의 runtime 바닥선을 Java 25로 올렸습니다. Java 21 호환 영역은 다음 다섯 artifact로 제한됩니다.

- `bluetape4k-assertions`
- `bluetape4k-junit5`
- `bluetape4k-logging`
- `bluetape4k-virtualthread-api`
- `bluetape4k-virtualthread-jdk21`

따라서 “일부 artifact가 Java 21에서 동작한다”와 “2.0.0 전체가 Java 21을 지원한다”는 같은 말이 아닙니다.
Java 21–24를 유지해야 하는 애플리케이션은 사용하는 artifact가 이 영역 안에 있는지 확인하고, 그렇지 않다면 Java 25로
이동하거나 `1.13.x` line을 유지해야 합니다. 이 결정은 [Java baseline issue](https://github.com/bluetape4k/bluetape4k-projects/issues/1335)에
기록돼 있습니다.

## 컴파일과 설정에서 드러나는 migration

### virtual-thread API는 import와 재컴파일이 필요하다

Java 21 호환 API 타입은 `io.bluetape4k.concurrent.virtualthread.api` package로 이동했습니다.

```kotlin
import io.bluetape4k.concurrent.virtualthread.api.StructuredTaskScopes
import io.bluetape4k.concurrent.virtualthread.api.VirtualThreads

val executor = VirtualThreads.executorService()
val value = StructuredTaskScopes.failFast { scope ->
    val task = scope.fork { loadValue() }
    scope.join().throwIfFailed()
    task.get()
}
```

이전 package의 타입을 source나 public signature에서 사용했다면 BOM만 바꿔서는 해결되지 않습니다. import를 고치고
consumer를 재컴파일해야 합니다. `core`와 `virtualthread-api` JAR가 같은 package를 나누어 소유하지 않도록 정리한
binary ownership 변경이기 때문입니다.

### QueryDSL Kotlin codegen은 기본 경로에서 빠졌다

Kotlin 2.4와 JDK 25 조합에서 QueryDSL Kotlin annotation processing이 upstream `NullPointerException`을 내므로
Kotlin codegen은 기본 지원 경로에서 제외됐습니다. Java APT로 생성한 Q 타입과 association query는 유지됩니다.
Kotlin Q 타입 생성에 의존한다면 clean build에서 생성 source와 compiler task를 먼저 확인해야 합니다. 자세한 결정은
[QueryDSL issue](https://github.com/bluetape4k/bluetape4k-projects/issues/1346)에 있습니다.

### MongoDB 설정 key가 바뀌었다

Spring Boot 4.1에서는 다음처럼 옮깁니다.

```yaml
spring:
  mongodb:
    uri: mongodb://localhost:27017/app
```

legacy `spring.data.mongodb.uri`만 남기면 localhost 기본값으로 조용히 연결하지 않고 다음 오류로 startup이 중단됩니다.

```text
Unsupported legacy MongoDB property 'spring.data.mongodb.uri'; use 'spring.mongodb.uri' on Spring Boot 4.1+
```

두 key가 함께 있으면 새 key가 우선합니다. 즉시 바꿀 수 없다면 legacy namespace를 지원하는 이전 artifact를 임시로
고정해야 합니다. [MongoDB migration issue](https://github.com/bluetape4k/bluetape4k-projects/issues/1358)가 이 경계를 고정합니다.

## 실패를 앞당기는 startup 경계

Custom Ignite2 image는 명시적인 tag가 필요합니다.

```kotlin
val ignite = Ignite2Server(
    image = "custom/ignite",
    tag = "2.18.0-company.3",
)
```

`Ignite2Server(image = "custom/ignite")`처럼 tag를 생략하면 `Custom Ignite2 image requires an explicit tag`로
실패합니다. `DockerImageName` 경로도 custom image에 `latest`를 암묵적으로 적용하지 않습니다. 지원하지 않는 CPU
architecture에서 canonical tag를 생략한 경우도 즉시 실패합니다. 운영자가 검증하지 않은 image가 우연히 선택되는 것보다
startup 실패가 안전하다는 판단입니다. 세부 계약은 [Ignite2 migration issue](https://github.com/bluetape4k/bluetape4k-projects/issues/1520)에서
확인할 수 있습니다.

## 적용 체크리스트

1. `java -version`과 배포 image의 JRE를 Java 25 기준으로 확인합니다.
2. Java 21 호환 영역만 사용한다면 실제 runtime classpath가 다섯 artifact 안에 닫히는지 검사합니다.
3. `io.bluetape4k.concurrent.virtualthread`의 이전 API import를 검색하고 재컴파일합니다.
4. QueryDSL generated source가 Java APT 경로에서 생성되는지 clean build로 확인합니다.
5. MongoDB key를 옮기고 legacy-only configuration이 startup에서 실패하는지 환경별로 점검합니다.
6. 모든 custom container image에 digest 또는 명시적 tag를 둡니다.

BOM은 호환 가능한 출발점을 제공합니다. 실제 migration의 완료 조건은 애플리케이션의 compile, startup, runtime 검증입니다.
