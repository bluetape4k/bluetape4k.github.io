메시지가 handler에 도착했다고 업무 처리가 끝난 것은 아닙니다. Database write 뒤 ack 전에 process가 종료될 수 있고,
stream record를 방출한 뒤 checkpoint 저장이 실패할 수도 있습니다. 재전달 가능한 시스템에서는 이 틈을 정상 경로로
설계해야 합니다.

[`bluetape4k-dependencies 2.0.0`](https://github.com/bluetape4k/bluetape4k-dependencies/releases/tag/2.0.0)은
[`bluetape4k-projects 2.0.0`](https://github.com/bluetape4k/bluetape4k-projects/releases/tag/2.0.0)과
[`bluetape4k-aws 1.0.0`](https://github.com/bluetape4k/bluetape4k-aws/releases/tag/1.0.0)을 함께 선택합니다.
두 release의 messaging API는 at-least-once 재전달과 호출자 소유 idempotency를 숨기지 않습니다.

## 메시지 수신과 업무 성공은 같은 사건이 아니다

가장 작은 안전 순서는 다음과 같습니다.

```kotlin
flow.collect { message ->
    try {
        processIdempotently(message)  // 업무 side effect가 먼저 성공한다.
        message.ack()                 // 그다음 consumer 위치를 전진시킨다.
    } catch (retryable: RetryableFailure) {
        message.nak()
    } catch (permanent: PermanentFailure) {
        message.term()
    }
}
```

실제 transaction과 broker 기능에 맞춰 inbox/outbox 또는 idempotency key가 필요할 수 있습니다. Adapter는 업무 side
effect와 broker acknowledgement를 하나의 원자적 transaction으로 만들어 주지 않습니다.

## NATS manual ack

Projects 2.0.0은 JetStream `ConsumerContext` pull consumer와 `JetStream` push subscription을 수집마다 생성하는 cold
`Flow<Message>`를 추가했습니다. Flow 용량과 NATS pending limit을 검증하며, 취소 시 adapter가 만든
`JetStreamSubscription` 또는 `IterableConsumer`만 닫습니다. Connection과 stream/consumer 설정은 호출자가 소유합니다.

Adapter는 manual acknowledgement만 제공합니다. 업무 성공 뒤 호출자가 `ack()`를 호출하고, 재시도할 실패에는 `nak()`,
처리할 수 없는 메시지에는 `term()` 정책을 적용합니다. Pending queue drop은 정상 완료가 아니라
`NatsConsumerFlowException`입니다.

- [NATS Flow issue](https://github.com/bluetape4k/bluetape4k-projects/issues/1350)
- [NATS JetStream Flow visual companion](/visual-companions/bluetape4k-projects/projects-nats-jetstream-flow/)

## DynamoDB Streams와 Kinesis checkpoint

DynamoDB Streams `Flow`는 shard graph의 parent-before-child 순서를 따릅니다. Checkpoint에서 다시 시작할 때는 저장된
sequence를 포함해 replay할 수 있으므로 consumer의 업무 처리는 idempotent해야 합니다. 이 adapter에는 Kinesis와 같은
분산 lease 계약이 없습니다.

Kinesis `consumerFlow`는 shard discovery, parent ordering, bounded concurrency, lease와 fencing을 함께 다룹니다.
Record를 downstream으로 `emit`한 것만으로 checkpoint를 저장하지 않습니다. Collector가 반환해 해당 record의 처리가
성공한 뒤 checkpoint를 전진시킵니다. Lease를 잃으면 새 emit과 checkpoint를 중단합니다.

| Adapter | Ordering | Progress state | 호출자 책임 |
| --- | --- | --- | --- |
| DynamoDB Streams | parent-before-child | inclusive checkpoint replay | idempotency, checkpoint store 수명 |
| Kinesis | shard graph와 parent ordering | lease·fencing 뒤 checkpoint | idempotency, lease/checkpoint store 구성 |

- [DynamoDB Streams issue](https://github.com/bluetape4k/bluetape4k-aws/issues/469)
- [Kinesis runtime issue](https://github.com/bluetape4k/bluetape4k-aws/issues/470)
- [AWS Streams visual companion](/visual-companions/bluetape4k-aws/aws-streams-shard-consumers/)

## SQS의 visibility와 payload 소유권

긴 작업은 visibility timeout보다 오래 걸릴 수 있습니다. SQS visibility heartbeat는 처리 중인 message의 visibility를
연장하지만 업무 성공을 대신 판정하지 않습니다. Batch listener는 성공한 항목만 partial acknowledgement하고 실패한 항목을
재전달 대상으로 남깁니다. FIFO queue에서는 message-group ordering과 backpressure도 같이 지켜야 합니다.

Extended Client는 큰 payload를 S3에 offload하고 SQS 본문에는 signed pointer를 둡니다. 애플리케이션은 bucket, IAM,
encryption, retention, lifecycle, retry와 orphan cleanup을 구성합니다. 이 pointer는 module 전용이며 AWS Java Extended
Client와 자동으로 상호운용되지 않습니다.

- [Visibility heartbeat](https://github.com/bluetape4k/bluetape4k-aws/issues/453)
- [Partial acknowledgement](https://github.com/bluetape4k/bluetape4k-aws/issues/454)
- [Extended Client payload offload](https://github.com/bluetape4k/bluetape4k-aws/issues/455)
- [SQS Extended Client visual companion](/visual-companions/bluetape4k-aws/aws-sqs-extended-client/)

## SNS 검증과 Modulith 방향

SNS HTTP adapter는 구조를 파싱한 뒤 exact `TopicArn` allowlist를 network 접근 전에 적용하고, 허용된 인증서 URL에서
certificate를 가져와 Signature v1/v2를 검증합니다. 검증을 통과한 메시지만 handler로 보냅니다. Subscription confirmation은
자동 side effect가 아니라 handler가 `NotificationStatus.confirmSubscription()`을 명시적으로 호출할 때 수행됩니다.

[SNS signature visual companion](/visual-companions/bluetape4k-aws/aws-sns-signature-verification/)에서 이 순서를 단계별로
확인할 수 있습니다.

Spring Modulith 연동은 두 방향을 구분합니다.

- Producer externalization: application event를 SNS/SQS로 내보냅니다.
- Consumer ingress: DIRECT body 또는 SNS-wrapped SQS body를 검증하고 application dispatch로 들여옵니다.

한 방향을 활성화했다고 반대 방향까지 자동 구성되는 것은 아닙니다. [Modulith issue](https://github.com/bluetape4k/bluetape4k-aws/issues/471)와
[event externalization visual companion](/visual-companions/bluetape4k-aws/aws-modulith-event-externalization/)이 경계를 보여 줍니다.

## 소유권 표

| 대상 | Adapter 소유 | 호출자 소유 |
| --- | --- | --- |
| NATS Flow | cold bridge, bounded channel, 생성한 handle cleanup | connection, 업무 성공, ack 정책 |
| AWS Streams | shard traversal, 방출 순서, 정의된 checkpoint hook | idempotency, durable store, 운영 설정 |
| SQS listener | polling·heartbeat·partial ack protocol | handler transaction, retry/DLQ, payload storage policy |
| SNS HTTP | allowlist·signature gate | 허용 topic, confirmation, 업무 side effect |
| Modulith | 선택한 outbound/inbound adapter | event contract, version, idempotency, 반대 방향 활성화 |

Adapter가 만든 handle만 adapter가 닫습니다. Client, credential, IAM, queue/topic, durable store, 업무 transaction은
애플리케이션 경계에 남습니다.
