## Caffeine: 가장 가까운 캐시

`cache-caffeine` 예제는 Spring Cache abstraction에 Caffeine을 연결합니다.

```kotlin
@Configuration
class CaffeineConfig {
    @Bean
    fun cacheManager(caffeine: Caffeine<Any, Any>): CacheManager {
        return CaffeineCacheManager("cache:countries", "cache:cities").apply {
            setCaffeine(caffeine)
        }
    }

    @Bean
    fun caffeineBean(): Caffeine<Any, Any> = caffeine {
        maximumSize(10_000)
        expireAfterWrite(30.minutes)
    }
}
```

전체 소스:
[CaffeineConfig.kt](https://github.com/bluetape4k/bluetape4k-workshop/blob/develop/spring-boot/cache-caffeine/src/main/kotlin/io/bluetape4k/workshop/cache/caffeine/config/CaffeineConfig.kt)

이 예제는 단일 인스턴스 read-heavy 캐시에 좋습니다. 빠르고 단순합니다. 단점도 단순합니다. 인스턴스가 둘이면 캐시도 둘입니다. 둘은 서로 대화하지 않습니다. 의외로 많은 문제가 "서로 대화하지 않음"에서 시작합니다.

## Redis: 공유되는 캐시

`cache-redis` 예제는 Redis를 Spring Cache와 `RedisTemplate`에 연결합니다.

```kotlin
@Bean
fun redisCacheManager(connectionFactory: RedisConnectionFactory): CacheManager =
    RedisCacheManager.builder(connectionFactory)
        .cacheDefaults(
            RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofDays(1))
        )
        .build()
```

전체 소스:
[LettuceRedisCacheConfiguration.kt](https://github.com/bluetape4k/bluetape4k-workshop/blob/develop/spring-boot/cache-redis/src/main/kotlin/io/bluetape4k/workshop/cache/redis/config/LettuceRedisCacheConfiguration.kt)

Redis는 여러 인스턴스가 같은 값을 보게 해줍니다. 대신 read path마다 remote hop이 있습니다. 그래서 Part 2에서 본 것처럼 hot read가 많으면 Near Cache가 후보가 됩니다.

## cache-benchmark: 이름과 실제 구현을 분리해서 읽기

`cache-benchmark`는 여러 구현을 `ProductCacheService`라는 같은 인터페이스 아래 둡니다.

```kotlin
interface ProductCacheService {
    fun findById(id: Long): Product?
    fun save(product: Product): Product
    fun evict(id: Long)
    fun clearAll()
}
```

전체 소스:
[ProductCacheService.kt](https://github.com/bluetape4k/bluetape4k-workshop/blob/develop/spring-boot/cache-benchmark/src/main/kotlin/io/bluetape4k/workshop/cache/benchmark/service/ProductCacheService.kt)

하지만 같은 인터페이스를 구현한다고 해서 의미론까지 같아지는 것은 아닙니다. 현재 구현은 두 그룹으로 나눠 읽어야 합니다.

| 구현체 | 실제 동작 | 해석 |
|---|---|---|
| `NoCacheService` | DB만 사용 | baseline |
| `CaffeineService` | JVM local cache 사용 | local cache 배치 |
| `RedisCacheService` | remote Redis cache 사용 | distributed cache 배치 |
| `NearCacheService` | local + Redis near cache 사용 | L1/L2 cache 배치 |
| `ReadThroughService` | service가 Redis miss를 확인하고 DB fallback과 cache 적재를 수행 | 이름과 달리 cache-aside |
| `WriteThroughService` | service가 DB 저장 후 Redis를 직접 갱신 | 이름과 달리 application dual-write |
| `WriteBehindService` | 기존 entity는 Redis 갱신 후 건별 `@Async` DB 저장, 신규 entity는 DB 먼저 저장 | cache가 queue와 batch flush를 소유하는 표준 write-behind가 아님 |

첫 네 구현은 cache의 배치 위치에 따른 처리량과 코드 비용을 비교하는 데 사용할 수 있습니다.

- 캐시가 없으면 baseline은 얼마인가?
- local cache만으로 충분한가?
- Redis 공유가 필요한가?
- Near Cache가 read path를 충분히 줄이는가?

반면 마지막 세 구현의 수치를 표준 read-through, write-through, write-behind 전략의 성능으로 해석하면 안 됩니다. 이름과 실제 계약이 다르기 때문입니다. 표준 계약에서는 application이 cache만 호출하고, cache가 loader 또는 writer를 통해 DB 접근을 소유합니다.

## 현재 구현에서 비교할 수 있는 범위

아래 값은 이번 글에서 새로 실행한 측정 결과가 아니라, 현재 `cache-benchmark` README에 기록된 수치입니다. 이름과 계약이 일치하는 네 구현만 추려 보면 local cache, remote cache, near cache의 배치 차이는 비교할 수 있습니다. 읽기와 쓰기 모두 `ops/s` 기준이며 높을수록 좋습니다.

| 프로파일 | 읽기 ops/s | 쓰기 ops/s | 실제 경로 |
|---|---:|---:|---|
| No Cache | ~8,200 | ~8,200 | DB만 |
| Caffeine | ~490,000 | ~8,100 | DB + local cache |
| Redis Cache | ~43,000 | ~7,300 | DB + remote Redis |
| Near Cache | ~465,000 | ~7,200 | DB + `RLocalCachedMap` |

이 수치는 local hit가 remote hop을 크게 줄일 수 있다는 점과, write path에는 DB 비용이 계속 남는다는 점을 보여줍니다. 반면 read-through, write-through, write-behind 사이의 우열은 보여주지 않습니다. 그 비교에는 같은 loader/writer 계약, 같은 일관성 조건, 같은 flush 정책으로 다시 만든 benchmark가 필요합니다.

## NearCacheService: local과 remote 사이

Near Cache 예제는 Redisson의 local cached map을 사용합니다.

```kotlin
class NearCacheService(
    private val productRepository: ProductRepository,
    redissonClient: RedissonClient,
) : ProductCacheService {
    companion object : KLoggingChannel() {
        const val CACHE_NAME = "products-near-cache"
    }
}
```

전체 소스:
[NearCacheService.kt](https://github.com/bluetape4k/bluetape4k-workshop/blob/develop/spring-boot/cache-benchmark/src/main/kotlin/io/bluetape4k/workshop/cache/benchmark/service/NearCacheService.kt)

코드는 짧아 보이지만 의미는 큽니다. hot read는 local에서 끝내고, remote cache는 공유와 invalidation을 담당합니다. 여기서 중요한 것은 "Near Cache를 썼다"가 아니라 "L1 hit이 충분히 나온다"입니다. hit이 안 나오면 작업대 위 서랍을 샀는데 계속 창고에 뛰어가는 상황입니다.

## resilience: 캐시 장애를 서비스 장애로 키우지 않기

`cache-resilience`는 Redis를 primary cache로 쓰고 Caffeine을 fallback으로 둡니다.

```kotlin
suspend fun getProduct(id: String): String? {
    val redisKey = "$REDIS_KEY_PREFIX$id"

    return SuspendDecorators.ofSupplier {
        redisTemplate.opsForValue().get(redisKey)
    }
        .withCircuitBreaker(circuitBreaker)
        .withFallback { localCache.getIfPresent(id) }
        .invoke()
}
```

전체 소스:
[ResilientProductService.kt](https://github.com/bluetape4k/bluetape4k-workshop/blob/develop/spring-boot/cache-resilience/src/main/kotlin/io/bluetape4k/workshop/cache/resilience/service/ResilientProductService.kt)

이 예제는 운영에서 바로 중요해집니다. 캐시는 성능을 위해 붙였는데, Redis가 잠깐 불안정해졌다고 서비스 전체가 같이 영향을 받으면 이상합니다. 캐시는 보조 인프라입니다. 보조 인프라가 서비스의 중심 장애가 되면 설계를 다시 봐야 합니다.

## 실전 체크리스트

서비스에 캐시를 넣기 전에 최소한 아래 질문에는 답해야 합니다.

| 질문 | 답해야 하는 이유 |
|---|---|
| baseline latency는? | 캐시가 실제로 개선하는지 알아야 함 |
| hit ratio 목표는? | hit이 낮으면 비용만 늘 수 있음 |
| stale 허용 시간은? | Near Cache와 write-behind의 핵심 계약 |
| write 실패 정책은? | throw, retry, queue, best effort 중 선택 |
| invalidate 범위는? | 단일 key, bulk, prefix, 전체 clear 구분 |
| 장애 시 fallback은? | Redis 장애가 서비스 장애가 되지 않게 함 |
| 관측 지표는? | hit/miss, latency, queue depth, circuit state |

## 마무리

이 시리즈의 결론은 "무조건 Near Cache"가 아닙니다.

더 정확한 결론은 이렇습니다.

- 단일 JVM hot read면 Caffeine이 가장 단순합니다.
- 여러 인스턴스가 공유해야 하면 Redis 같은 remote cache가 필요합니다.
- remote read가 병목이면 Near Cache를 검토합니다.
- Exposed repository에 붙일 때는 read/write 전략을 분리합니다.
- 장애 동작을 정하지 않은 캐시는 아직 설계가 끝난 게 아닙니다.

캐시는 성능 최적화이기도 하지만, 운영 계약이기도 합니다. 운영 계약을 대충 쓰면 나중에 아주 또렷하게 돌아옵니다. 보통 새벽에요.
