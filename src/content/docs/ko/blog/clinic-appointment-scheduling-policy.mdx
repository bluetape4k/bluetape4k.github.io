## 같은 요청인데 왜 병원마다 결과가 다를까

환자가 같은 상품을 선택하고 같은 시간대를 요청해도 결과가 병원마다 다를 수 있습니다. A 병원은 상담원의 확인을 거쳐야 예약을 확정하고, B 병원은 이미 검증된 조건이면 바로 확정할 수 있습니다. 이것은 예약 생성 코드가 병원 이름을 보고 예외를 고르는 문제가 아닙니다. **예약을 판단하는 정책이 테넌트 기본값과 병원별 규칙을 합성한 결과이기 때문입니다.**

이 차이를 설명하려면 다음 네 가지를 분리해야 합니다.

| 구분 | 답해야 하는 질문 |
| --- | --- |
| 범위 | 이 규칙은 모든 병원에 적용되는가, 특정 병원에만 적용되는가? |
| 선택 | 병원 설정이 기본값을 그대로 상속하는가, 값을 바꾸는가, 선택 기능을 끄는가? |
| 시점 | 예약을 판단한 때와 실제 방문 서비스가 일어나는 때는 언제인가? |
| 이력 | 나중에 정책이 바뀌어도 당시의 판단을 다시 설명할 수 있는가? |

정책을 단순한 설정 테이블로만 다루면 마지막 두 질문에 답하기 어렵습니다. 그래서 이번 설계에서는 정책을 버전이 있는 계약으로 저장하고, 예약 판단에 사용할 **유효 정책 스냅숏(effective policy snapshot)** 을 따로 만듭니다.

## 기본 정책과 병원별 재정의는 합성 규칙이다

정책의 적용 범위는 두 층으로 나뉩니다.

| 범위 | 역할 | 예 |
| --- | --- | --- |
| 테넌트 기본 정책 | 해당 테넌트의 모든 병원이 사용할 기준 | 기본 승인 방식, 안전 상한, 운영 시간 |
| 병원별 재정의 | 특정 병원의 업무 차이를 표현 | 특정 기능의 추가 확인, 선택 기능 비활성화 |

병원별 재정의는 세 가지 의도로 표현합니다.

| 의도 | 의미 | 결과 |
| --- | --- | --- |
| `INHERIT` | 테넌트 기본 정책을 그대로 사용 | 기본 정책의 값을 유효 정책에 기록 |
| `SET` | 병원에 다른 값을 지정 | 병원 정책을 해당 경로의 출처로 기록 |
| `DISABLE` | 선택 기능만 사용하지 않음 | 비활성화된 경로를 별도로 기록 |

`INHERIT`를 null과 같은 뜻으로 취급하지 않는 것이 중요합니다. null은 “값을 아직 모른다”는 뜻일 수 있지만, `INHERIT`는 “테넌트 값을 의도적으로 따른다”는 명시적인 결정입니다. 반대로 안전 상한이나 필수 정책은 `DISABLE`로 끄거나 기본값보다 느슨하게 바꿀 수 없습니다.

같은 규칙을 코드 곳곳에서 다시 해석하지 않고 이 합성 단계를 한 곳에 모으면, “이 병원은 왜 다르게 처리되었나?”라는 운영 질문에 답할 수 있습니다. 실제 구현에서도 `INHERIT`, `SET`, `DISABLE`을 payload 계약으로 구분하고, 컴파일러가 각 정책 경로의 출처를 남깁니다.

## 정책은 값을 바꾸는 설정이 아니라 버전이 있는 계약이다

운영자가 화면에서 숫자나 옵션을 바꿨다고 해서 그 값이 즉시 모든 예약에 적용되면 곤란합니다. 변경에는 검증, 승인, 적용 시점, 실패 시 되돌릴 경계가 필요합니다.

정책의 생명주기는 다음처럼 제한합니다.

```text
DRAFT ──▶ SCHEDULED ──▶ ACTIVE ──▶ RETIRED
  └──────────────▶ ACTIVE
  └────────────────────────────▶ RETIRED
```

| 단계 | 의미 | 운영자가 확인할 것 |
| --- | --- | --- |
| `DRAFT` | 아직 적용하지 않은 정책 | 필수 항목과 안전 상한을 만족하는가? |
| `SCHEDULED` | 미래 시점에 적용할 정책 | 적용 시점과 예상되는 영향이 분명한가? |
| `ACTIVE` | 현재 읽기에 사용할 정책 | 기대한 세대와 버전으로 활성화되었는가? |
| `RETIRED` | 더 이상 새 판단에 쓰지 않는 정책 | 과거 이력을 추적할 수 있는가? |

초안 작성, 검증, 미리보기, 승인, 예약 적용 또는 즉시 활성화, 폐기는 서로 다른 단계입니다. 특히 승인은 상태 전이와 같은 말이 아닙니다. 승인된 내용이라도 적용 시점에 세대가 바뀌었거나 다른 운영자가 먼저 활성화했다면 다시 확인해야 합니다.

## 유효 정책 스냅숏이 있어야 당시의 결정을 설명할 수 있다

예약 판단에 필요한 것은 “현재 병원 설정”이 아니라 **그 순간에 유효했던 정책의 묶음**입니다. 스냅숏에는 다음 정보가 함께 들어갑니다.

| 필드 | 역할 |
| --- | --- |
| `decisionAt` | 정책을 판단한 시점 |
| `serviceAt` | 실제 방문 서비스가 일어날 시점 |
| `generation` | 테넌트와 병원 정책의 세대 벡터 |
| `sourceVersions` | 각 정책 경로에 사용한 버전 |
| `sourceByPath` | 각 값이 기본 정책에서 왔는지 병원 재정의에서 왔는지 |
| `snapshotHash` | 같은 입력이면 같은 결과가 나왔음을 확인하는 해시 |

개념적으로는 다음과 같은 불변 객체입니다.

```kotlin
data class EffectiveSchedulingPolicy(
    val decisionAt: Instant,
    val serviceAt: Instant,
    val generation: PolicyGenerationVector,
    val sourceVersions: Map<SchedulingPolicyKind, Long>,
    val sourceByPath: Map<String, PolicyValueSource>,
    val snapshotHash: String,
)
```

`serviceAt`이 `decisionAt`보다 앞설 수 없다는 시간 경계도 컴파일 단계에서 검사합니다. 이렇게 만든 스냅숏은 예약 요청, 미리보기, 운영 화면이 제각각 정책을 읽는 일을 막고, 나중에 같은 결정을 재현할 수 있게 합니다. 스냅숏은 정책을 자동으로 예약에 적용한다는 뜻이 아니라, **적용할 정책을 하나의 검증 가능한 결과로 고정한다는 뜻**입니다.

## 활성화 충돌은 이전 정책을 보존하는 방식으로 닫는다

두 운영자가 같은 병원의 정책을 동시에 활성화할 수 있습니다. 이때 마지막 요청이 무조건 성공하면 먼저 승인된 변경이 조용히 덮어써집니다. 활성화 요청에는 기대한 revision과 generation을 함께 보내고, 저장 시점에 값이 달라졌는지 비교하는 CAS(Compare-And-Set) 경계를 둡니다.

충돌이 나면 새 정책을 억지로 적용하지 않고 다음을 보장합니다.

- 기대한 세대가 아니면 활성화를 거부한다.
- 같은 idempotency key로 재시도한 요청은 같은 결과를 돌려준다.
- 예약된 활성화 시점을 놓쳐도 직전 `ACTIVE` 정책은 유지한다.
- 운영자는 충돌 원인을 확인한 뒤 새 세대로 다시 미리 보고 승인한다.

이 원칙은 “정책 변경 버튼을 눌렀으니 성공했을 것”이라는 추측을 없앱니다. 활성화 성공 여부와 실제 유효 정책을 다시 읽는 과정이 분리되어야 운영자가 결과를 확인할 수 있습니다.

## 정책이 바뀌어도 기존 확정 방문 약속은 다시 쓰지 않는다

정책 변경의 적용 범위는 미래의 판단으로 제한합니다. 이미 환자에게 확정한 방문 약속을 현재 정책으로 다시 계산하면, 시스템이 환자와 맺은 약속을 사후에 바꾸게 됩니다.

| 기존 상태 | 정책 변경 시 기본 처리 |
| --- | --- |
| `PROPOSED` | 새 정책으로 다시 계산할 수 있음 |
| `HELD` | 보류 만료와 함께 새 정책을 적용할 수 있음 |
| `CONFIRMED` | 기존 확정 방문 약속을 보호하고 자동으로 다시 쓰지 않음 |

확정된 방문 시간이나 가격을 바꿔야 한다면 기존 약속을 덮어쓰는 대신 새 제안을 만들고 환자의 동의를 다시 받아야 합니다. 정책 스냅숏과 방문 약속의 스냅숏을 분리하는 이유가 여기에 있습니다. 정책은 앞으로의 판단 규칙이고, 확정 방문 약속은 이미 외부에 약속한 결과입니다.

## 현재 구현과 아직 연결하지 않은 경계

이번 기반 설계는 정책을 만들고, 검증하고, 유효 스냅숏으로 읽고, 안전하게 활성화하는 경계를 마련합니다. 예약 생성 경로가 이 정책을 실제 결정에 소비하는 일은 별도의 연결 단계입니다. 그래서 기능 플래그도 다음 순서로 나뉘어 있으며 기본값은 꺼져 있습니다.

1. shadow compile
2. effective read
3. admin write
4. preview worker
5. scheduled activation

이 순서를 지키면 저장된 정책이 기존 예약 흐름에 갑자기 영향을 주지 않는지 단계별로 확인할 수 있습니다. “정책 데이터를 저장할 수 있다”와 “예약 결과가 정책에 따라 달라진다”는 서로 다른 출시 주장입니다.

## 정리

병원마다 예약 규칙이 다른 이유는 병원별 예외를 코드에 흩뿌렸기 때문이 아닙니다. 테넌트 기본 정책을 기준으로 병원별 재정의를 명시적으로 합성하고, 그 결과를 세대·출처·해시가 있는 유효 정책 스냅숏으로 고정하기 때문입니다.

이 구조가 지키는 경계는 분명합니다.

- `INHERIT`, `SET`, `DISABLE`은 서로 다른 의도다.
- 정책 변경은 버전과 생명주기를 가진다.
- 활성화는 CAS와 세대 검사로 충돌을 닫는다.
- 기존 `CONFIRMED` 방문 약속은 미래 정책으로 다시 쓰지 않는다.

다음 글에서는 이 정책 경계와 연결되는 대기 목록을 살펴봅니다. 빈시간이 생겼을 때 누구에게 어떤 제안을 만들 수 있는지는 정책을 읽는 시점과 확정 방문 약속을 보호하는 규칙 위에서 결정됩니다.
