<p class="bt4k-post-meta">2026-06-11 · bluetape4k idgenerators benchmark note</p>

처음 목표는 단순했다. `bluetape-go`에 `idgenerators` 구현을 붙이고,
기존 `bluetape4k-idgenerators`와 비교한다. Go 쪽은 primitive와 작은 struct를 많이 쓰니
꽤 앞설 것이라고 예상했다.

그런데 benchmark는 그렇게 얌전하게 끝나지 않았다. Go도 매번 random entropy를 읽고 있었고,
Kotlin도 Snowflake에서 불필요한 중간 객체를 만들고 있었다. `ULID`, `KSUID`, `KsuidMillis`도
각각 다른 병목을 갖고 있었다. 결국 작업은 세 번의 비교로 커졌다.

1. Go 구현을 만들고 1차 비교를 했다.
2. Go 쪽 per-call allocation과 entropy 병목을 줄이고 2차 비교를 했다.
3. Kotlin 쪽 Snowflake, ULID, KSUID, KsuidMillis를 다시 줄이고 3차 비교를 했다.

이 글은 그 과정의 기록이다. 결론부터 말하면 "Go가 빠르다"나 "Kotlin이 이겼다"로 끝낼 수 없는
숫자가 나왔다. generator family마다 병목이 달랐고, 한번 고친 뒤에는 다음 병목이 바로 보였다.

## bluetape-go의 ID generator 구현

`bluetape-go`의 구현은 `id` 패키지에 모았다.

- UUID v4/v7은 convenience 함수와 재사용 가능한 generator를 모두 제공한다.
- ULID는 random ULID와 monotonic ULID를 나눈다.
- KSUID는 초 단위 timestamp를 쓰는 기본 KSUID와, JVM 쪽 구현과 맞춘 millisecond variant를 함께 둔다.
- Snowflake는 integer ID hot path를 노출한다.

구현의 출발점은 단순했다. Go API에서는 문자열 ID를 바로 얻는 `NextString()` 류 entrypoint와,
benchmark에서 allocation이 섞이지 않도록 정수 hot path를 분리한 entrypoint를 같이 둔다.

```go
id.NewULIDMonotonicGenerator().NextString()
id.NewKSUIDGenerator().NextString()
id.NewKSUIDMillisGenerator().NextString()
id.NewSnowflakeGenerator(...).NextInt64()
```

소스는 [`bluetape-go/id`](https://github.com/bluetape4k/bluetape-go/tree/develop/id)와
[`id_benchmark_test.go`](https://github.com/bluetape4k/bluetape-go/blob/develop/id/id_benchmark_test.go)에 있다.
첫 benchmark 보고서는
[`Issue #168 ID generator benchmark`](https://github.com/bluetape4k/bluetape-go/blob/develop/docs/research/2026-06-10-issue-168-id-generator-benchmark.md)에 남겼다.

## 1차 비교: 예상보다 단순하지 않았다

1차 비교에서는 Go가 모든 row를 가져가지는 못했다. Snowflake처럼 synthetic clock으로 hot path를 재는
row는 Go가 압도적으로 낮은 `ns/id`를 보였다. 반대로 Kotlin의 UUID v7, single-thread monotonic ULID,
KSUID seconds는 이미 꽤 강했다.

중요한 점은 benchmark shape였다. Go Snowflake row는 synthetic clock hook을 쓰는 hot path였다.
Kotlin Snowflake row는 real system clock과 `kotlinx-benchmark` batch shape를 사용했다. 이 둘을 같은
production verdict로 읽으면 안 된다. Snowflake row는 "Go 코드가 이 상황에서 빠르다"는 자료이지,
"언어 차이만으로 이 정도가 난다"는 자료가 아니다.

그래도 1차 비교는 쓸모가 있었다. Go 쪽 profile을 보니, 기대와 달리 generator 재사용만으로는 gap이
크게 줄지 않았다. 병목은 더 아래에 있었다. random entropy read와 문자열 encoding이 눈에 띄었다.

## Go 개선: 매번 할당보다 먼저 entropy가 보였다

Go 쪽 개선은 두 갈래였다.

첫째, default entropy source를 바꿨다. UUID, ULID, KSUID가 매 ID마다 `crypto/rand`를 직접 두드리면
ID 생성이라기보다 syscall 체조에 가깝다. 그래서 package-local locked buffered reader를 두고,
기본 generator들이 이 reader를 공유하도록 했다. entropy source는 여전히 `crypto/rand` 기반이다.
ID는 인증 토큰이 아니라 identifier라는 boundary도 보고서에 명시했다.

둘째, `KSUIDMillis` 문자열 encoding에서 불필요한 임시 slice를 줄였다. 27글자 prefix를 고정 local
buffer에 바로 encode해서, 이전처럼 만든 뒤 자르는 경로를 피했다.

최종 `benchstat` 요약은 꽤 선명했다.

| Go benchmark | Baseline | Final | Change |
|---|---:|---:|---:|
| UUID v4 reused | 224.10 ns/op | 45.57 ns/op | -79.67% |
| UUID v7 reused | 255.60 ns/op | 73.95 ns/op | -71.07% |
| ULID random | 104.50 ns/op | 63.12 ns/op | -39.60% |
| ULID monotonic | 65.80 ns/op | 65.31 ns/op | -0.74% |
| KSUID seconds | 393.10 ns/op | 217.90 ns/op | -44.58% |
| KSUID millis | 316.80 ns/op | 122.80 ns/op | -61.23% |
| KSUID millis parallel | 621.00 ns/op | 209.00 ns/op | -66.35% |

`ULID monotonic`이 거의 움직이지 않은 것도 중요하다. 이 row는 entropy buffering이 아니라 monotonic
state 관리와 encoding 쪽이 더 큰 비중을 갖고 있었다. 즉, "한 가지 최적화가 모든 ID generator를
고친다"는 식의 이야기는 여기서 바로 깨진다.

자세한 Go 개선 기록은
[`Issue #192 ID generator performance optimization`](https://github.com/bluetape4k/bluetape-go/blob/develop/docs/research/2026-06-11-issue-192-id-generator-performance.md)에 있다.

## 2차 비교: 병목이 이동했다

Go 개선 뒤의 2차 비교에서는 표정이 달라졌다. Go는 UUID v4, KSUID millis, concurrent ULID/KSUID row에서
강해졌다. Kotlin은 UUID v7과 single-thread monotonic ULID에서 여전히 좋은 숫자를 냈다.

| Generator | Go ns/id | Kotlin ns/id | Lower row |
|---|---:|---:|---|
| Snowflake synthetic clock | 11.98 | 244.06 | Go |
| ULID monotonic | 65.31 | 37.01 | Kotlin |
| UUID v4 reused generator | 45.57 | 95.09 | Go |
| UUID v7 reused generator | 73.95 | 23.59 | Kotlin |
| KSUID millis | 122.80 | 167.80 | Go |
| KSUID seconds | 217.90 | 187.93 | Kotlin |

Concurrent row는 Go 쪽 entropy buffering 효과가 더 잘 보였다.

| Generator | Go ns/id | Kotlin ns/id | Lower row |
|---|---:|---:|---|
| Snowflake synthetic clock | 92.37 | 373.89 | Go |
| ULID monotonic | 180.20 | 408.56 | Go |
| UUID v4 reused generator | 145.00 | 329.69 | Go |
| UUID v7 reused generator | 202.80 | 115.42 | Kotlin |
| KSUID millis | 209.00 | 396.50 | Go |
| KSUID seconds | 244.20 | 388.70 | Go |

이쯤 되면 Kotlin 쪽도 그냥 두기 어렵다. Go를 고쳐놓고 보니, Kotlin implementation에도 줄일 수 있는
object path와 entropy staging이 보였다.

## Kotlin 개선: Snowflake, ULID, KSUID, KsuidMillis

Kotlin 작업은 `bluetape4k-idgenerators`에서 했다. 이쪽의 목표는 public API를 흔들지 않고, 생성 경로의
불필요한 객체와 random payload staging을 줄이는 것이었다.

Snowflake는 `SnowflakeId` 중간 객체를 만들고 다시 `Long`으로 꺼내는 경로가 있었다. 그래서 내부
sequencer에 value fast path를 추가했다. public API는 그대로 두고, `nextId()`와 `nextIds(size)`가
가능하면 `Long` 값을 바로 받도록 했다.

```kotlin
internal interface SnowflakeValueSequencer {
    fun nextValue(): Long
}
```

이 변화는 throughput 표에서 크게 보이지 않는다. 이유가 있다. benchmark가 65,536개 ID를 한 operation에서
만들고, Snowflake sequence는 millisecond마다 4,096개가 한계다. real clock에서는 clock ceiling이 먼저
나온다. 대신 allocation profile은 또렷했다.

| Snowflake profile | Baseline | Candidate 3 | Delta |
|---|---:|---:|---:|
| `gc.alloc.rate.norm` | 14,579,592.553 B/op | 6,970,033.101 B/op | -52.19% |
| `gc.alloc.rate` | 868.813 MB/s | 415.382 MB/s | -52.19% |
| `gc.count` | 6 | 3 | -50.00% |

ULID는 `ByteArray(10)`을 만들고 `Random.nextBytes`로 채우는 staging을 피했다. 80-bit randomness를
직접 `nextBits(16)`과 `nextLong()`으로 받아 value/string path에 넣는다.

KSUID와 `KsuidMillis`는 timestamp를 먼저 명시적으로 쓰고, random payload 부분만 채우도록 바꿨다.
초 단위 KSUID는 4바이트 timestamp 뒤의 16바이트 payload만, millisecond variant는 8바이트 timestamp
뒤의 12바이트 payload만 randomize한다.

Kotlin candidate 3의 decision-relevant row는 다음과 같다.

| Kotlin workload | Baseline | Candidate 3 | Delta |
|---|---:|---:|---:|
| `single.ulidMonotonicString` | 577.327 ops/s | 580.638 ops/s | +0.57% |
| `single.ulidMonotonicValueOnly` | 831.422 ops/s | 847.083 ops/s | +1.88% |
| `single.ulidMonotonicWithUniqueness` | 360.095 ops/s | 365.002 ops/s | +1.36% |
| `single.ksuidSecondsFixedInstantString` | 79.546 ops/s | 88.611 ops/s | +11.40% |
| `single.ksuidSecondsWithUniqueness` | 71.890 ops/s | 74.321 ops/s | +3.38% |
| `single.ksuidMillisFixedInstantString` | 94.588 ops/s | 98.104 ops/s | +3.72% |
| `single.ksuidMillisWithUniqueness` | 82.114 ops/s | 82.655 ops/s | +0.66% |
| `concurrent.ulidMonotonicString` | 38.331 ops/s | 45.414 ops/s | +18.48% |
| `concurrent.ulidMonotonicWithUniqueness` | 35.542 ops/s | 45.857 ops/s | +29.02% |
| `concurrent.ksuidMillisDefaultString` | 68.632 ops/s | 70.704 ops/s | +3.02% |
| `concurrent.ksuidMillisWithUniqueness` | 53.496 ops/s | 56.906 ops/s | +6.37% |
| `concurrent.ksuidSecondsDefaultString` | 60.633 ops/s | 62.924 ops/s | +3.78% |
| `concurrent.ksuidSecondsWithUniqueness` | 52.908 ops/s | 53.445 ops/s | +1.01% |

여기서도 숫자를 너무 예쁘게 포장하면 안 된다. `single.ksuidMillisDefaultString`은 full candidate 3 run에서
잠깐 낮게 나왔지만, 같은 JVM targeted repeat에서는 baseline 대비 -1.74% 수준이었다. KSUID millis code
path가 candidate 2와 candidate 3 사이에서 바뀌지 않았기 때문에, 보고서에는 full-run dip을 benchmark
noise로 남겼다. 성능 글에서 안 좋은 row를 지우기 시작하면 그때부터 benchmark가 아니라 광고가 된다.

## 3차 비교: Go와 Kotlin이 각자 다른 곳에서 앞선다

마지막으로 현재 Go 구현과 Kotlin candidate 3을 다시 비교했다. Kotlin throughput row는 batch size
65,536 기준 `1e9 / (ops/s * 65_536)`으로 `ns/id`로 정규화했다.

| Workload | Go ns/id | Kotlin ns/id | Lower | Note |
|---|---:|---:|---|---|
| Snowflake single | 11.98 | 244.02 | Go | Go synthetic clock; Kotlin real clock/batch ceiling |
| Snowflake concurrent | 90.01 | 243.65 | Go | Go synthetic clock; Kotlin real clock/batch ceiling |
| ULID monotonic single | 64.96 | 26.28 | Kotlin |  |
| ULID monotonic concurrent | 194.80 | 336.00 | Go |  |
| KSUID seconds single | 215.60 | 175.86 | Kotlin |  |
| KSUID seconds concurrent | 256.40 | 242.50 | Kotlin |  |
| KSUID millis single | 123.50 | 167.07 | Go | Kotlin targeted repeat was 157.03 ns/id |
| KSUID millis concurrent | 215.90 | 215.81 | Kotlin | Effectively tied |

`KsuidMillis`를 빼면 그림이 틀어진다. Go 개선 뒤에는 `KSUID millis`가 꽤 큰 Go lead였는데,
Kotlin payload-only randomization 이후 concurrent row는 사실상 동률까지 왔다. single row에서는 Go가
아직 낮다. 이 차이는 timestamp precision variant가 실제 서비스에서 어떤 형태로 쓰이는지에 따라 다시
재야 한다.

`ULID`도 한 줄로 말하기 어렵다. single-thread monotonic row는 Kotlin이 낮고, concurrent monotonic row는
Go가 낮다. monotonic state를 어떻게 보호하고, entropy와 encoding이 어느 쪽에서 더 크게 보이는지가
workload별로 갈린다.

`KSUID seconds`는 Kotlin 개선 뒤 single/concurrent 모두 Kotlin row가 낮았다. 반대로 Snowflake는 여전히
Go 숫자가 낮지만, 이 row는 clock model 차이가 너무 크다. Kotlin에서 이번에 얻은 실질적 개선은
throughput ranking이 아니라 allocation 절감이다.

## 이번 작업의 진짜 결론

이번 비교에서 제일 위험한 결론은 "Go와 Kotlin 중 무엇이 더 빠른가"다. 그 문장은 보기에는 시원하지만,
실제로는 별로 쓸모가 없다.

더 쓸모 있는 결론은 이쪽이다.

- Snowflake는 clock model과 sequence ceiling을 분리해서 봐야 한다.
- Go의 UUID/ULID/KSUID 초기 병목은 generator 재사용보다 entropy read 쪽에 가까웠다.
- Kotlin Snowflake는 throughput보다 allocation profile에서 개선이 크게 보였다.
- Kotlin ULID/KSUID/KsuidMillis는 payload staging을 줄이면 concurrent row가 움직인다.
- `KsuidMillis`는 별도 variant로 봐야 한다. KSUID seconds 결과로 대충 대표시키면 안 된다.

ID generator는 작아 보이는 코드다. 그래서 benchmark도 간단할 것 같지만, 실제로는 clock, random,
encoding, uniqueness set, batch size가 서로 다른 방향으로 끌어당긴다. 이번 작업의 수확은 빠른 row
몇 개가 아니다. 다음에 ID generator를 고칠 때 "어디부터 의심해야 하는지"를 알게 된 점이다.
