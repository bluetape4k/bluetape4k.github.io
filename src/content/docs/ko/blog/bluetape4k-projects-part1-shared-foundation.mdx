이 글은 `bluetape4k-projects` 시리즈의 1편입니다. 전체 시리즈는
[Part 1: 공유 기반](/ko/blog/bluetape4k-projects-part1-shared-foundation/)에서 시작해,
Part 2: core, coroutines, logging, tests, Part 3: I/O, serialization, HTTP, encryption,
Part 4: data와 infrastructure, Part 5: Spring Boot, Ktor, utility, adoption path로 이어질 예정입니다.

`bluetape4k-projects`는 bluetape4k 생태계의 가장 넓은 바닥입니다. Spring Boot나 Ktor 애플리케이션을
만들 때 반복해서 필요한 Kotlin/JVM 유틸리티, coroutine helper, I/O wrapper, data/infra adapter,
testing 기반, BOM을 한곳에 모읍니다.

그렇다고 모든 기능을 이 저장소에 계속 쌓는 구조는 아닙니다. AWS, Exposed, Image, Text, Leader,
JaVers 같은 큰 도메인은 독립 저장소로 분리했습니다. `projects`는 서비스 코드가 가장 먼저 기대는
공통 기반과, 여러 저장소가 공유하는 runtime building block을 담당합니다.

## 왜 이 저장소가 필요한가

Kotlin/JVM 백엔드 개발은 대부분 검증된 Java 라이브러리 위에서 출발합니다. 문제는 그대로 쓰기에는
빈틈이 많다는 점입니다.

- Java API는 Kotlin null-safety와 DSL 감각에 맞지 않는 경우가 많습니다.
- callback, `Future`, blocking API가 coroutine 코드와 어색하게 만납니다.
- 테스트에서는 Redis, Kafka, database, 시간, 동시성 같은 fixture가 계속 반복됩니다.
- 서비스마다 같은 codec, serializer, timeout, retry, logging 관례를 다시 만듭니다.

`bluetape4k-projects`의 역할은 이 반복을 줄이는 것입니다. "새로운 거대한 프레임워크"를 만들기보다,
이미 쓰는 라이브러리를 Kotlin 서비스에서 덜 거칠게 쓰게 만드는 얇은 층에 가깝습니다.

```kotlin
implementation(platform("io.github.bluetape4k:bluetape4k-bom:<version>"))
implementation("io.github.bluetape4k:bluetape4k-core")
implementation("io.github.bluetape4k:bluetape4k-coroutines")
implementation("io.github.bluetape4k:bluetape4k-junit5")
```

루트 README도 같은 방향을 잡고 있습니다. 이 저장소는 idiomatic Kotlin helper, Java library wrapper,
coroutine integration, testing infrastructure, Redis/cache/infra 기반 기능을 제공하고, 더 큰 도메인
기능은 별도 저장소로 나눕니다.

## 모듈 지도

현재 `README.md`의 모듈 구조를 보면 이 저장소의 경계가 드러납니다.

<figure class="bt4k-architecture">
  <img src="/assets/bluetape4k-projects-module-map-01.png" alt="Bluetape4k Projects module structure diagram grouped by core, I/O, data, infra, cache, Spring Boot, Ktor, utilities, testing, and examples" loading="lazy" />
  <figcaption>루트 README의 모듈 구조는 `projects`가 공통 기반과 runtime adapter를 함께 관리한다는 점을 보여줍니다.</figcaption>
</figure>

| 영역 | 대표 모듈 | 쓰기 시작하는 순간 |
|---|---|---|
| Foundation | `core`, `coroutines`, `logging`, `bom` | Kotlin 코드 스타일, 실행 모델, dependency alignment를 맞출 때 |
| I/O | `io`, `okio`, `csv`, `protobuf`, `jackson2/3`, `http`, `grpc` | byte, file, serializer, HTTP/RPC 경계를 다룰 때 |
| Data | `jdbc`, `r2dbc`, `hibernate`, `mongodb`, `cassandra` | persistence helper와 coroutine data access가 필요할 때 |
| Infrastructure | `lettuce`, `redisson`, `kafka`, `nats`, `opentelemetry`, `resilience4j` | 운영 시스템과 붙는 adapter가 필요할 때 |
| Application | `spring-boot/*`, `ktor/*`, `examples/*` | 서비스 entrypoint와 테스트 가능한 예제가 필요할 때 |
| Testing | `assertions`, `junit5`, `testcontainers` | 반복되는 통합 테스트 fixture를 줄일 때 |

이 표에서 중요한 점은 "한 모듈을 쓰면 전체 생태계를 끌고 온다"가 아닙니다. 필요한 조각만 가져가는
방식입니다. BOM은 버전 줄을 맞추고, 각 모듈은 독립적으로 선택됩니다.

## 독립 저장소로 나누는 기준

기능이 커지면 `projects` 안에 계속 두는 것이 오히려 방해가 됩니다. 그래서 bluetape4k는 몇 가지
영역을 독립 저장소로 분리했습니다.

| 독립 저장소 | 분리한 이유 |
|---|---|
| `bluetape4k-aws` | AWS SDK v2/Kotlin SDK 서비스 범위가 넓고 release cadence가 따로 움직입니다 |
| `bluetape4k-exposed` | Exposed 1.2.x 기반 repository/cache/SQL DSL 영역이 자체 생태계입니다 |
| `bluetape4k-image` | pure JVM 이미지 처리와 libvips/JNI/FFM 경계가 별도 검증을 요구합니다 |
| `bluetape4k-text` | 한국어/일본어 tokenizer와 text-search는 dictionary와 품질 기준이 다릅니다 |
| `bluetape4k-leader` | leader election API와 backend parity는 독립적으로 발전해야 합니다 |
| `bluetape4k-javers` | audit/diff persistence는 Redis, Kafka, Exposed와 별도 release 축이 있습니다 |

대략적인 기준은 이렇습니다. 여러 서비스가 공통으로 쓰는 얇은 Kotlin/JVM 기반이면 `projects`에 둡니다.
도메인 자체가 큰 학습 비용과 release 주기를 갖기 시작하면 독립 저장소로 나눕니다.

## BOM이 하는 일

공유 기반 저장소에서 BOM은 작지만 중요합니다. Kotlin, Spring Boot, Exposed, Jackson, Redis client,
testing 도구가 서로 다른 속도로 움직이기 때문입니다.

`bluetape4k-bom`은 `projects`가 게시하는 모듈들의 버전을 맞춥니다. 애플리케이션은 BOM을 먼저
import하고 필요한 모듈만 선언합니다.

```kotlin
dependencies {
    implementation(platform("io.github.bluetape4k:bluetape4k-bom:<version>"))
    implementation("io.github.bluetape4k:bluetape4k-okio")
    implementation("io.github.bluetape4k:bluetape4k-r2dbc")
    testImplementation("io.github.bluetape4k:bluetape4k-testcontainers")
}
```

Gradle Kotlin DSL에서는 `dependencyManagement { imports }`보다 `implementation(platform(...))` 방식이
안전합니다. 루트 README도 KGP 2.3.x 충돌을 피하려면 이 방식을 권장합니다.
