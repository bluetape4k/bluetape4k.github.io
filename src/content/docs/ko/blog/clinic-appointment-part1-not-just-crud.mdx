병원 예약 서비스를 처음 설계하면 화면부터 떠올리기 쉽습니다. 달력에서 날짜를 고르고, 의사를 고르고,
저장 버튼을 누릅니다. 데이터베이스에는 `appointments` row 하나가 추가됩니다. 여기까지만 보면 전형적인
CRUD입니다.

그런데 병원 직원에게 물어보면 질문이 바로 늘어납니다.

- 그 병원은 그날 문을 여는가?
- 점심시간이나 임시휴진과 겹치지 않는가?
- 선택한 의사가 그 진료를 할 수 있고 실제로 근무하는가?
- 진료에 필요한 장비가 있으며 점검 중은 아닌가?
- 같은 시간에 받을 수 있는 환자 수를 넘지 않는가?
- 이미 확정되거나 진료가 시작된 예약을 자동으로 옮겨도 되는가?

이 질문에 답하지 못하면 `INSERT`에는 성공해도 예약에는 실패한 것입니다. 이번 시리즈는 이 간극을
`clinic-appointment` 저장소가 요구사항, 설계와 계획, 구현, 리뷰, 추가 요구사항의 순서로 좁혀 온 과정을
따라갑니다. Part 1에서는 먼저 전체 지도를 잡습니다.

## 예약이 생성되기 전에 이미 결정되어야 하는 것들

요구사항 문서에는 세 종류의 사용자가 등장합니다. 환자는 가능한 시간을 조회하고 예약합니다. 직원은
예약을 확정하고 체크인과 진료 완료를 처리합니다. 관리자는 휴진과 장비 사용불가를 등록하고 영향을 받은
예약을 재배정합니다.

세 사람이 보는 화면은 다르지만 같은 예약을 만집니다. 환자에게는 “오후 2시 예약”이고, 직원에게는
`REQUESTED`에서 `CONFIRMED`로 바꿔야 할 업무이며, 관리자에게는 휴진이나 장비 고장이 생겼을 때 보호하거나
옮겨야 할 일정입니다. 따라서 예약 모델은 날짜와 환자 이름만 저장해서는 부족합니다.

현재 `Appointments` table은 `clinicId`, `doctorId`, `treatmentTypeId`, 선택적인 `equipmentId`, 날짜와 시작·종료
시각, 상태를 함께 가집니다.

```kotlin
object Appointments : LongIdTable("scheduling_appointments") {
    // 참조 삭제 정책과 이 글의 논점과 무관한 column은 생략
    val clinicId = reference("clinic_id", Clinics)
    val doctorId = reference("doctor_id", Doctors)
    val treatmentTypeId = reference("treatment_type_id", TreatmentTypes)
    val equipmentId = optReference("equipment_id", Equipments)
    val appointmentDate = date("appointment_date")
    val startTime = time("start_time")
    val endTime = time("end_time")
    val status = appointmentState("status")
}
```

이것은 단지 foreign key가 많다는 뜻이 아닙니다. 예약의 유효성이 여러 업무 규칙의 교집합이라는 뜻입니다.
[Appointments.kt](https://github.com/bluetape4k/clinic-appointment/blob/main/appointment-core/src/main/kotlin/io/bluetape4k/clinic/appointment/model/tables/Appointments.kt)의
index도 이 특성을 드러냅니다. 의사·날짜 조합은 중복과 슬롯 조회에, 병원·날짜·상태 조합은 활성 예약과
일괄 상태 변경에, 장비·날짜 조합은 장비 사용량 검사에 쓰입니다.

## SaaS의 공통 기능과 병원별 업무 규칙을 나눈다

`clinic-appointment`는 여러 병원이 사용하는 SaaS를 전제로 합니다. 최상위의 `TenantGroup`은 데이터 격리의
소유자이고 그 아래에 여러 `Clinic`이 놓입니다. 하지만 “같은 tenant에 속한다”와 “같은 시간표를 쓴다”는
말은 다릅니다.

각 병원은 자기 `slotDurationMinutes`, timezone, 최대 동시 환자 수, 공휴일 운영 여부를 가집니다. 그 아래에는
병원별 업무시간과 휴식시간, 임시휴진, 의사와 근무·부재 일정, 진료 유형, 장비와 사용불가 일정이 연결됩니다.
같은 날짜와 진료 요청도 A 병원에서는 가능하고 B 병원에서는 불가능할 수 있습니다.

이 그림에서 일부러 두 경계를 구분했습니다.

첫째, `TenantGroup → Clinic`은 소유권과 격리의 경계입니다. 다른 tenant의 병원 데이터를 읽거나 바꾸지 못하게
하는 문제입니다. 둘째, `Clinic → Appointment`는 업무 정확성의 경계입니다. 해당 병원의 시간표와 자원으로
그 예약이 가능한지를 계산하는 문제입니다. 둘을 모두 구현해야 하지만 같은 문제로 합치면 안 됩니다.
병원별 정책을 정확히 계산해도 tenant 검증을 빼먹으면 보안 결함이고, tenant를 완벽히 격리해도 휴진 시간에
예약을 받으면 업무 결함입니다.

현재 소스에서는 [TenantGroups.kt](https://github.com/bluetape4k/clinic-appointment/blob/main/appointment-core/src/main/kotlin/io/bluetape4k/clinic/appointment/model/tables/TenantGroups.kt)가
격리 소유자를 정의하고, [Clinics.kt](https://github.com/bluetape4k/clinic-appointment/blob/main/appointment-core/src/main/kotlin/io/bluetape4k/clinic/appointment/model/tables/Clinics.kt)가
`tenantGroupId`와 병원별 운영 설정을 가집니다. 병원마다 다른 업무시간·의사·장비가 예약 계산에 들어가는
과정은 Part 3에서, tenant 접근 경계는 Part 7에서 더 자세히 다룹니다.

## 요구사항을 모듈 경계로 옮기기

기능이 늘어날 때 모든 코드를 하나의 Spring Boot module에 넣으면 시작은 빠릅니다. 대신 어느 기능이 다른
기능 없이도 동작해야 하는지 알기 어려워집니다. `clinic-appointment`는 업무 책임을 다음처럼 나눴습니다.

| 모듈 | 책임 | 경계를 나눈 이유 |
|---|---|---|
| `appointment-core` | domain model, repository, 상태 머신, 실시간 슬롯 계산 | 병원 예약 규칙의 기준을 API나 배포 방식에서 분리합니다. |
| `appointment-api` | tenant 범위 REST API, 인증, 요청 검증 | 외부 계약과 domain 실행을 연결합니다. |
| `appointment-solver` | Timefold를 이용한 대량 예약 최적화 | 빠른 단건 조회와 전역 최적화의 실행 비용과 목적이 다릅니다. |
| `appointment-event` | 예약 domain event와 event log | 상태 변화의 후속 작업을 core transaction과 느슨하게 연결합니다. |
| `appointment-notification` | reminder와 고가용성 발송 | API가 없어도 독립 process로 실행할 수 있게 합니다. |
| frontend | 직원이 예약과 기준 정보를 관리하는 UI | Node/Angular build와 Kotlin build의 경계를 유지합니다. |

특히 [architecture ADR-4](https://github.com/bluetape4k/clinic-appointment/blob/main/docs/requirements/architecture.md#adr-4-slotcalculationservice-vs-solverservice-역할-분리)는
`SlotCalculationService`와 `SolverService`를 합치지 않기로 결정했습니다. 환자가 보는 한 건의 슬롯 조회는
짧은 응답 시간이 중요하고, 관리자가 여러 예약을 재배치할 때는 전체 조합의 품질이 중요하기 때문입니다.
비슷한 이름의 “스케줄링”이어도 호출 시점과 탐색 범위가 다르면 경계도 달라집니다.

알림도 마찬가지입니다. API는 알림 module에 직접 의존하지 않습니다. 예약 변경 event를 발행하고 알림
component가 구독합니다. 실제 email이나 SMS가 아직 없더라도 예약 생성 자체는 동작해야 하고, 알림 scheduler는
별도 process로 배포할 수 있어야 한다는 요구가 설계 경계를 만들었습니다.

## 기능 목록보다 먼저 문서의 역할을 설계했다

이 저장소에서 흥미로운 점은 기능만 설계하지 않고 문서 체계도 요구사항으로 다뤘다는 것입니다.
2026년 3월의 [Living Documentation 설계](https://github.com/bluetape4k/clinic-appointment/blob/main/docs/superpowers/specs/2026-03-30-living-docs-design.md)는
다음 역할을 나눴습니다.

| 자료 | 답해야 하는 질문 |
|---|---|
| 루트와 module README | 이 저장소는 무엇을 제공하며 어디서 시작하는가? |
| `docs/requirements` | 사용자가 기대하는 동작과 업무 규칙은 무엇인가? |
| spec과 plan | 어떤 선택지를 검토했고 무엇을 어떤 순서로 만들기로 했는가? |
| source와 test | 지금 실제로 동작하는 것은 무엇인가? |
| lessons | 구현과 리뷰에서 무엇을 놓쳤고 다음에는 무엇을 바꿔야 하는가? |

이 구분은 글을 쓰기 위한 장식이 아닙니다. 개발 과정에서 서로 다른 시점의 사실을 보존합니다. 예를 들어
초기 requirements index에는 멀티테넌시가 backlog로 남아 있지만 현재 source에는 `TenantGroups`와 tenant 범위
검증 코드가 있습니다. 어떤 문서에는 domain entity가 16개라고 적혀 있고 더 최신 목록에는 17개가 나옵니다.
프런트엔드 버전 표기도 문서마다 차이가 있습니다.

이 차이를 최신 숫자 하나로 덮어쓰면 기능이 어떻게 발전했는지 알 수 없습니다. 반대로 오래된 문서를 현재
동작처럼 인용하면 틀린 설명이 됩니다. 그래서 이 시리즈에서는 다음 원칙을 사용합니다.

1. requirements는 당시의 업무 계약으로 읽습니다.
2. spec과 plan은 선택과 구현 순서를 설명하는 기록으로 읽습니다.
3. 현재 동작은 source와 test로 다시 확인합니다.
4. 차이가 생긴 이유는 review와 lessons에서 찾고 다음 요구사항으로 연결합니다.

문서가 코드와 달라졌다는 사실 자체가 실패는 아닙니다. 차이를 발견하고도 방치하는 것이 실패에 가깝습니다.
Living documentation은 항상 정확한 문서 한 장을 약속하기보다, 어떤 자료를 어느 판단에 써야 하는지와
언제 다시 검증해야 하는지를 약속합니다.

## 구현 뒤에 생기는 다음 질문

여기까지 오면 예약 서비스의 첫 요구사항은 “예약 CRUD를 만든다”에서 다음과 같이 바뀝니다.

> 한 tenant에 속한 각 병원의 운영 정책과 자원 제약 안에서, 허용된 상태 변화와 이력을 보존하며 예약을
> 생성·운영·재배정한다.

한 문장이 길어진 만큼 설계할 경계도 선명해졌습니다. 병원과 자원을 모델링해야 하고, 가능한 시간을 계산해야
하며, 상태 변화를 제한해야 하고, 운영 중 제약이 바뀌면 기존 예약을 안전하게 다뤄야 합니다. 여러 예약을
동시에 옮길 때는 전역 최적화가 필요하고, 변경 결과는 event와 알림으로 이어집니다.

다음 편에서는 이 가운데 가장 먼저 계약으로 고정해야 할 예약 상태를 다룹니다. `PENDING`, `CONFIRMED`,
`COMPLETED` 같은 enum 값을 나열하는 데서 끝내지 않고, 누가 어떤 event로 상태를 바꿀 수 있는지, 변경 사유와
이력을 왜 함께 남겨야 하는지 살펴봅니다.
