동시성 버그는 테스트가 적어서만 생기지 않습니다. 테스트가 실제 코드와 다른 실행 모델을 사용하거나,
값의 의미를 잘못 비교하거나, 실패와 취소를 정상적인 종료로 삼을 때도 생깁니다. 그래서 테스트 유틸리티를
고를 때는 "몇 번 실행할까?"보다 먼저 두 가지를 정해야 합니다.

1. 이 값은 같은 객체(identity)여야 하는가, 같은 값(structural equality)이면 되는가?
2. 이 코드는 일반 platform thread, virtual thread, 아니면 suspend 함수와 coroutine `Job`에서 실행되는가?

`bluetape4k-assertions`는 첫 번째 질문의 문장을 고정하고, `bluetape4k-junit5`의 tester들은 두 번째 질문의
실행 모델을 반복해서 검증합니다. 이 글은 두 모듈을 한 번에 소개하되, stress test를 성능 benchmark로
오해하지 않도록 각 도구의 계약과 실패 경계를 나눠 설명합니다.

## 시작하기: 테스트 의존성

```kotlin
dependencies {
    testImplementation("io.github.bluetape4k:bluetape4k-assertions:$bluetape4kVersion")
    testImplementation("io.github.bluetape4k:bluetape4k-junit5:$bluetape4kVersion")
}
```

`bluetape4k-junit5`는 `bluetape4k-assertions`를 transitively 포함하므로 JUnit 5 테스트 기반을 함께
가져오는 경우에는 두 번째 의존성만으로 assertion 모듈을 사용할 수 있습니다. assertion만 필요한 모듈은
첫 번째 의존성을 직접 선언하면 됩니다.

## 1. `bluetape4k-assertions`: 값의 의미를 문장으로 고정하기

### `shouldBe`와 `shouldBeEqualTo`는 서로 바꿔 쓰지 않는다

가장 중요한 구분은 이름이 비슷한 두 assertion입니다.

| assertion | 비교 의미 | 사용할 때 |
|---|---|---|
| `shouldBe` | 참조 동일성(`===`) | 반드시 같은 객체 인스턴스여야 하는가를 검증할 때 |
| `shouldBeEqualTo` | 구조적/값 동등성(`==`) | data class, 문자열, 숫자처럼 값이 같으면 되는 경우 |

```kotlin
data class Token(val value: String)

val expected = Token("ready")
val actual = Token("ready")

actual shouldBeEqualTo expected // 값이 같으면 통과
// actual shouldBe expected     // 서로 다른 인스턴스이므로 실패
```

이 구분을 놓치면 동시성 테스트에서 더 큰 문제가 생깁니다. 공유 캐시가 같은 인스턴스를 반환해야 하는지,
새로 만든 결과가 같은 내용이면 되는지를 assertion이 정확히 말해 주지 못하기 때문입니다.

### Java 스타일 호출보다 읽기 쉬운 `infix` assertion

`bluetape4k-assertions`의 핵심 assertion은 `infix fun`으로 제공됩니다. Java/JUnit의
`assertEquals(expected, actual)`처럼 인자 순서를 기억하는 호출보다 `actual shouldBeEqualTo expected`가
검증 대상을 먼저 보여줍니다. 왼쪽의 대상, 가운데의 판정 규칙, 오른쪽의 기대값을 왼쪽에서 오른쪽으로
읽을 수 있어 테스트의 의도를 빠르게 이해할 수 있습니다. 단순히 코드 길이를 줄이는 문법이 아니라
검증 문장을 만드는 방식입니다.

```kotlin
// Java/JUnit 스타일: expected가 먼저 오므로 인자 순서를 확인해야 한다
assertEquals("clinic-1", response.id)
assertEquals(200, response.status)
assertTrue(response.tags.containsAll(listOf("booking", "stable")))

// Kotlin + bluetape4k-assertions: 대상 -> 규칙 -> 기대값 순서로 읽는다
response.id shouldBeEqualTo "clinic-1"
response.status shouldBeEqualTo 200
response.tags shouldContainAll listOf("booking", "stable")
```

`response.id.shouldBeEqualTo("clinic-1")`도 동작하지만, 두 값의 관계를 표현하는 이항 assertion은
infix 표기를 우선하면 테스트가 문장처럼 읽힙니다. `shouldNotBeNull()`처럼 인자가 없는 검증이나
`shouldBeNear(expected, tolerance)`처럼 여러 인자가 필요한 함수는 일반 호출이 더 자연스럽습니다.

#### API 응답을 한 줄씩 읽는 검증

실제 응답을 검증할 때는 assertion을 값의 나열이 아니라 응답 계약으로 읽을 수 있습니다.

```kotlin
val response = loadResponse()
val requiredTags = listOf("booking", "stable")

response.status shouldBeEqualTo 200
response.body shouldStartWith "{"
response.body shouldContain "\"status\":\"ready\""
response.tags shouldContainAll requiredTags
response.tags shouldNotContain "error"
```

이 코드는 `status`의 정확한 값, JSON body의 형태, 필수 tag 집합, 금지된 tag를 각각 분리해 보여줍니다.
특히 `response.tags shouldContainAll requiredTags`는 `containsAll`의 반환값을 다시 `assertTrue`로 감싸는
코드보다 “응답 tag가 이 목록을 모두 포함해야 한다”는 요구사항을 그대로 읽게 해 줍니다.

#### 실패 타입과 메시지도 분리해서 읽기

실패 타입은 `assertFailsWith`로 고정하고, 반환된 예외의 메시지는 다시 infix assertion으로 검증할 수
있습니다.

```kotlin
val error = assertFailsWith<IllegalArgumentException> {
    repository.find("missing")
}

error.message shouldContain "missing"
```

이렇게 쓰면 “어떤 예외인가”와 “메시지에 어떤 단서가 있어야 하는가”가 서로 섞이지 않습니다. suspend
블록의 메시지·cause 검증은 `coInvoking` DSL을 그대로 사용합니다.

### API를 종류별로 선택하기

`bluetape4k-assertions`는 하나의 거대한 assertion보다 테스트에서 반복되는 판단을 종류별로 나눕니다.

| 종류 | 대표 기능 | 확인할 계약 |
|---|---|---|
| 기본/널 | `shouldBe`, `shouldBeEqualTo`, `shouldBeNull`, `shouldNotBeNull` | identity, 값 동등성, null 이후 smart cast |
| 수치 | 크기 비교, 범위, 양수/음수, signed/unsigned, `shouldBeNear` | 허용 오차와 경계값 |
| 컬렉션·배열·맵 | empty/non-empty, contains all/none, 크기, primitive/object array 비교 | 원소 포함, 순서, 중복, deep equality |
| 문자열 | starts/ends/contains, 대소문자 무시 비교 | 문자열 경계와 normalization |
| 날짜·시간 | `java.time` 타입의 after/before/on-or-after/on-or-before | 시간 순서와 포함 여부 |
| reflection | `shouldBeInstanceOf<T>`, `shouldNotBeInstanceOf<T>` | 런타임 타입 계약 |
| 예외 | `invoking`, `coInvoking`, 메시지·cause matcher | 동기/정지 함수의 실패 종류와 내용 |
| 집계 | `assertSoftly` | 여러 assertion을 한 번에 보고하기 |
| Flow/Turbine | 순서 있는 결과, 순서 무시 결과 집합, failure/error, Turbine item | 스트림 순서·중복·취소 계약 |

BigDecimal 비교처럼 표현상의 차이(scale)를 값의 차이로 취급하지 않는 helper도 있습니다. 중요한 것은
함수 이름을 외우는 것이 아니라, 테스트가 검증하려는 의미에 맞는 함수를 고르는 것입니다.

### 예외 assertion은 취소를 삼키지 않는다

동기 예외 타입은 `assertFailsWith`로, 메시지와 cause는 `invoking` 또는 `coInvoking`으로 검증할 수
있습니다.

```kotlin
val error = assertFailsWith<IllegalArgumentException> {
    repository.find("missing")
}
error.message shouldContain "missing"

coInvoking { client.fetch() }
    .withCause(IOException::class)
```

`coInvoking`은 예상한 예외가 아닌 `CancellationException`을 정상적인 assertion 실패로 바꾸지 않고 다시
던집니다. 테스트 runner가 취소된 작업을 계속 기다리거나, 취소를 비즈니스 예외로 오인하지 않게 하는
경계입니다. `shouldNotThrow`, `withMessage`, `withMessageMatching`, `withCause`를 조합해 실패 계약을
구체화할 수도 있습니다.

### 여러 실패와 Flow 결과

`assertSoftly`는 각 검증을 등록해 한 번에 `MultipleFailuresError`로 보고합니다.

```kotlin
assertSoftly {
    add { response.status shouldBeEqualTo 200 }
    add { response.body.shouldNotBeNull() }
    add { response.headers shouldContainAll expectedHeaders }
}
```

scope는 `assertSoftly` 호출마다 생기는 인스턴스 단위입니다. 같은 assertion collector를 여러 테스트
스레드가 공유하지 않으면 병렬 실행에서도 실패 목록이 섞이지 않습니다. 저장소 README가 설명하는
virtual-thread-safe 성질도 이 사용 경계에서 이해해야 합니다.

Flow에서는 목적에 맞게 순서를 선택합니다.

- `assertResult`는 방출 순서를 그대로 비교합니다.
- `assertResultSet`은 순서를 무시하지만 중복 개수는 보존합니다.
- `assertFailure`, `assertError`는 실패 신호를 검증합니다.
- Turbine을 함께 사용할 때는 `awaitItemAndAssert`, `awaitItemMatching`, `awaitErrorOfType`을 사용할 수 있습니다.

Flow assertion도 `CancellationException`을 삼키지 않습니다. 순서를 무시하는 assertion이 필요하더라도
취소 전파라는 실행 계약까지 무시해서는 안 됩니다.

## 2. `bluetape4k-junit5`: 실행 모델을 바꿔가며 반복하기

이 모듈의 stress tester는 throughput이나 latency를 측정하는 benchmark 도구가 아닙니다. 같은 테스트 블록을
여러 worker와 round로 반복해, 공유 상태·실패 전파·취소·정리 계약이 여러 실행에서 계속 유지되는지를
확인하는 도구입니다.

세 tester는 공통 fluent 설정을 제공하지만, `workers`와 `rounds`의 결합 방식은 실행 모델별로 다릅니다.

| 설정 | 현재 계약 |
|---|---|
| `workers` | `1..2000`; `MultithreadingTester`/`SuspendedJobTester`는 worker 실행자 수, `StructuredTaskScopeTester`는 동시에 살아 있는 작업 수 상한 |
| `rounds` | `1..1_000_000`; `MultithreadingTester`는 worker당 라운드, 나머지는 등록 블록당 라운드 |
| 블록 미등록 | `run()` 시 `IllegalStateException` |
| 자원 정리 | executor, dispatcher, structured scope를 실행 종료 시 닫음 |
| 실행량 | `MultithreadingTester`는 `workers * rounds`, 나머지는 `등록 블록 수 * rounds` |

### `MultithreadingTester`: 고정 platform thread pool

일반 동기 API, 캐시, memoizer, lock, atomic 연산처럼 platform thread 경쟁을 확인하려면
`MultithreadingTester`가 첫 선택입니다.

```kotlin
val counter = AtomicInteger()

MultithreadingTester()
    .workers(8)
    .rounds(100)
    .add { counter.incrementAndGet() }
    .run()

counter.get() shouldBeEqualTo 8 * 100
```

고정 크기 platform-thread pool을 만들고, 등록한 블록을 `workers * rounds`회 round-robin으로 실행합니다. 한
블록의 실행에서 `Throwable`이 발생하면 thread-safe한 `MultiException` collector에 넣고, executor를 종료한
뒤 실패를 다시 보고합니다. 실패가 하나면 원래 예외를, 둘 이상이면 수집된 `MultiException`을 던지는
방식이라 실패의 원인을 잃지 않습니다.

`workers`가 등록한 runnable 수보다 작으면 실행을 시작하지 않는 precondition도 있습니다. 여러 블록을
등록할 때는 이 조건을 먼저 확인해야 합니다.

### `StructuredTaskScopeTester`: Java 21/25 virtual thread

질문에 자주 등장하는 `StructuredScopedTaskTester`라는 표기는 현재 클래스 이름이 아닙니다. 소스의 정확한
이름은 `StructuredTaskScopeTester`입니다.

이 tester는 기본 virtual-thread factory와 `StructuredTaskScope`를 사용합니다. virtual thread에서는 고정
worker 수를 전체 실행량을 표현하는 데 사용할 필요가 없습니다. 이 예제는 등록한 블록을 800번 실행하도록
`rounds(8 * 100)`으로 표현합니다. `workers`는 필요할 때 동시에 살아 있는 작업 수를 제한하는 내부
`Semaphore` 상한으로 사용할 수 있고, 기본 상한으로 충분하면 생략해도 됩니다.

```kotlin
import kotlin.time.Duration.Companion.seconds

StructuredTaskScopeTester()
    .rounds(8 * 100)
    .withTimeout(5.seconds)
    .add { processRequest() }
    .run()
```

timeout을 설정하면 fork loop 전에 deadline을 계산하고, `joinUntil`이 기한을 넘길 때
`TimeoutException`을 보고합니다. scope가 join된 뒤에는 `throwIfFailed`로 작업 실패를 전파하고 scope와
thread 자원을 닫습니다. virtual thread 전용 경로, `ScopedValue` 전파, 구조화된 실패 전파와 timeout을
검증할 때 이 tester가 의미가 있습니다. 다른 실행 모델을 검증하는 테스트를 단지 더 빠르게 만들기 위한
대체재는 아닙니다.

`withFactory`로 custom `ThreadFactory`를 주입할 수 있으므로, 이름이나 생성 정책이 중요한 테스트도 같은
계약 안에서 확인할 수 있습니다.

### `SuspendedJobTester`: suspend 함수와 coroutine `Job`

호출 대상이 suspend 함수라면 coroutine 경계를 그대로 테스트해야 합니다.

```kotlin
runSuspendTest {
    val results = ConcurrentLinkedQueue<Int>()

    SuspendedJobTester()
        .workers(16)
        .rounds(100)
        .add {
            delay(10)
            results.add(1)
        }
        .run()

    results.size shouldBeEqualTo 100
}
```

고정 크기 thread-pool dispatcher에서 worker `Job`을 만들고, atomic index로 전체 실행 단위를 나눕니다.
각 block의 예외는 `MultiException`에 모읍니다. `CancellationException`은 별도로 다시 던져 coroutine
취소를 정상 결과로 만들지 않습니다. 모든 `Job`이 join되고 dispatcher가 닫힌 뒤에 수집된 실패를 보고하는
구조입니다.

### `bluetape4k-projects` core 모듈에서 가져온 실전 시나리오

가상의 서비스보다 실제 소스와 테스트를 기준으로 예제를 읽는 편이 정확합니다. `bluetape4k-projects`의
`bluetape4k/core` 모듈은 이미 concurrency 유틸리티를 이 tester들로 검증하고 있습니다. 아래 코드는
[`AtomicIntRoundrobinTest`](https://github.com/bluetape4k/bluetape4k-projects/blob/develop/bluetape4k/core/src/test/kotlin/io/bluetape4k/concurrent/AtomicIntRoundrobinTest.kt)와
[`LockSupportTest`](https://github.com/bluetape4k/bluetape4k-projects/blob/develop/bluetape4k/core/src/test/kotlin/io/bluetape4k/concurrent/LockSupportTest.kt)를
따르므로 실행량과 최종 assertion이 실제 계약에 근거합니다.

#### 1. platform thread에서 atomic round-robin counter 검증하기

[`AtomicIntRoundrobin`](https://github.com/bluetape4k/bluetape4k-projects/blob/develop/bluetape4k/core/src/main/kotlin/io/bluetape4k/concurrent/AtomicIntRoundrobin.kt)은
카운터를 atomic하게 증가시키고 `maximum`에서 다시 처음으로 돌아옵니다. core 테스트는 사용 가능한 processor 수를
ring 크기로 정한 뒤 platform thread로 경쟁을 만듭니다.

```kotlin
val atomic = AtomicIntRoundrobin(Runtimex.availableProcessors)

MultithreadingTester()
    .workers(Runtimex.availableProcessors * 2)
    .rounds(4)
    .add { atomic.next() }
    .run()

atomic.get() shouldBeEqualTo 0
```

tester는 `availableProcessors * 2 * 4`번 증가시킵니다. 이 값은 ring 크기의 배수이므로 counter는 0으로
돌아와야 합니다. `atomic.get() shouldBeEqualTo 0`은 `assertEquals(0, atomic.get())` 안에 같은 계약을 넣는
것보다 subject -> rule -> expected value 순서가 드러나 읽기 쉽습니다.

#### 2. virtual thread에서도 같은 실행량 유지하기

같은 core 클래스를 Java 21+ virtual thread에서 검증합니다. 소스 테스트는 `workers`를 생략하고 전체 실행량을
`rounds`에 직접 표현합니다.

```kotlin
val atomic = AtomicIntRoundrobin(Runtimex.availableProcessors)

StructuredTaskScopeTester()
    .rounds(4 * Runtimex.availableProcessors * 2)
    .add { atomic.next() }
    .run()

atomic.get() shouldBeEqualTo 0
```

여기서 `rounds(4 * availableProcessors * 2)`가 전체 실행 횟수입니다. virtual thread가 실행 모델을 제공하므로
`workers`는 필요하지 않습니다. 동시에 살아 있는 작업 수를 제한하는 semaphore 상한 자체가 계약일 때만
`workers`를 추가합니다. 이는 benchmark용 배수가 아니라 실제 core 테스트와 같은 실행량 계산입니다.

#### 3. 하나의 read/write lock 계약을 세 실행 모델에서 검증하기

[`LockSupportTest`](https://github.com/bluetape4k/bluetape4k-projects/blob/develop/bluetape4k/core/src/test/kotlin/io/bluetape4k/concurrent/LockSupportTest.kt)는
`ReentrantReadWriteLock`을 사용하고, platform thread·virtual thread·coroutine Job에서 같은 invariant를
검증합니다. write section 16회가 실행되면 `counter`는 16이어야 합니다.

```kotlin
val lock = ReentrantReadWriteLock()
var counter = 0

MultithreadingTester()
    .workers(16)
    .rounds(2)
    .add {
        lock.read {
            Thread.sleep(10)
            val current = counter
            log.trace { "current=$current" }
        }
    }
    .add {
        lock.write {
            Thread.sleep(20)
            counter++
        }
    }
    .run()

counter shouldBeEqualTo 16
```

소스 테스트는 lock body와 마지막 infix assertion은 유지하고 tester 설정만 바꿉니다.

| 실행 모델 | 소스 설정 | 실행량 의미 |
|---|---|---|
| Platform thread | `workers(16).rounds(2)` | 등록한 두 block을 포함해 32회 실행, write는 16회 |
| Virtual thread | `rounds(16)` | 등록한 두 block × 16 rounds, 고정 worker pool 없음 |
| Coroutine Job | `workers(16).rounds(16)` | 등록한 두 suspend block × 16 rounds, workers는 동시성만 제한 |

핵심은 모든 tester에 같은 `workers` 값을 복사하는 것이 아닙니다. 실행 모델만 바꾸고 lock invariant는 그대로
검증하는 것입니다.

#### 4. `CountDownLatch` timeout을 명시적인 실패 계약으로 만들기

같은 core 테스트 suite는 느린 작업을 flaky test로 취급하지 않고 `withLatch`의 timeout 경로를 검증합니다.

```kotlin
assertFailsWith<TimeoutException> {
    withLatch(1, 100.milliseconds) {
        Thread.sleep(200)
        countDown()
    }
}
```

`assertFailsWith`는 실패 타입을 고정하고, 바깥 테스트는 `withLatch`의 deadline 동작을 명시합니다. 이 패턴은
처리량 측정이 아니라 문서화된 timeout 경로를 검증할 때 사용해야 합니다.

## 3. 실행 모델 선택표

세 tester를 모두 붙이는 것이 목표는 아닙니다. 테스트 대상의 실제 실행 모델과 같은 도구를 선택해야 합니다.

| 테스트 대상 | 선택 | 이유 |
|---|---|---|
| 일반 동기 함수, thread-safe cache, lock/atomic 조합 | `MultithreadingTester` | 고정 platform thread 경쟁을 직접 재현 |
| Java 21/25 virtual thread 경로, structured scope, timeout | `StructuredTaskScopeTester` | virtual thread와 scope lifecycle을 그대로 실행 |
| suspend 함수, dispatcher 전환, cancellation | `SuspendedJobTester` | coroutine `Job`과 취소 전파를 보존 |
| 처리량·지연시간 숫자 비교 | 별도 benchmark 도구 | tester의 목적은 안정성 계약 반복이지 성능 측정이 아님 |

예를 들어 `suspend fun`을 `MultithreadingTester` 안에서 blocking wrapper로 감싸면 테스트가 통과할 수는
있습니다. 하지만 그 결과는 coroutine cancellation, dispatcher 종료, structured child 관계를 증명하지
않습니다. 실행 모델이 바뀌면 테스트가 증명하는 사실도 바뀝니다.

## 4. 실패를 읽는 순서

동시성 테스트가 실패했을 때 round 수를 무작정 늘리기보다 다음 순서로 원인을 좁히는 편이 낫습니다.

1. assertion 의미를 확인합니다. 동일한 인스턴스를 요구했는지, 값만 같으면 되는지부터 봅니다.
2. 실패가 `CancellationException`인지 비즈니스 예외인지 구분합니다. 취소가 collector에 잘못 들어갔는지 확인합니다.
3. `MultiException`에 모인 원래 예외들을 각각 읽습니다. 첫 번째 stack trace만 보고 race를 추측하지 않습니다.
4. tester의 실행 모델이 실제 API와 같은지 확인합니다. platform thread 테스트로 virtual thread나 coroutine 계약을 대신하지 않습니다.
5. 마지막으로 `workers`와 `rounds`를 조절합니다. 반복 수를 늘리는 것은 원인을 찾은 뒤 재현 확률을 높이는 단계입니다.

이 순서를 지키면 stress test는 "가끔 실패하는 랜덤 테스트"가 아니라, 어떤 계약이 깨졌는지를 알려주는
작은 재현기가 됩니다.

## 마무리

`bluetape4k-assertions`는 테스트 문장의 의미를 통일하고, `bluetape4k-junit5` tester는 실제 실행 모델의
경쟁과 lifecycle을 반복해서 드러냅니다. 둘을 함께 사용하면 "값을 어떻게 비교했는가"와 "어디에서 어떻게
실행했는가"를 같은 테스트 안에서 분리해 읽을 수 있습니다.

안정성 테스트의 목표는 가장 큰 `rounds` 숫자가 아닙니다. 실패와 취소를 보존하고, 자원을 닫고, 올바른
실행 모델에서 같은 계약을 다시 증명하는 것입니다.
