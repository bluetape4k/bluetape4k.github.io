<p class="bt4k-post-meta">2026-05-31 · bluetape4k-leader series · Part 1</p>

이 글은 `bluetape4k-leader` 시리즈의 1편입니다. 전체 시리즈는 저장소의 큰 그림에서 시작해
core API, multi-leader/전략 선출, Spring Boot/Ktor 통합, backend와 운영 기능으로 이어집니다.

분산 리더 선출은 이름만 보면 거창합니다. 실제로는 훨씬 생활형 문제입니다. 서버를 3대 띄웠는데
야간 정산 job도 3번 돌고, schema migration도 3번 시도하고, webhook poller도 3개가 같은 이벤트를
잡으려고 달려듭니다. 서비스가 수평 확장된 순간, "한 번만 해야 하는 일"은 자동으로 한 번만 되지
않습니다. 누군가 한 명만 실행하도록 정해야 합니다.

`bluetape4k-leader`는 이 결정을 Kotlin/JVM 서비스 코드에서 일관된 모양으로 쓰기 위한 독립 라이브러리입니다.
Redis, Exposed JDBC/R2DBC, MongoDB, DynamoDB, etcd, Kubernetes Lease, Hazelcast, ZooKeeper 같은 backend를
제공하고, blocking, `CompletableFuture`, coroutine, virtual thread API를 나란히 제공합니다.

## 문제: replica는 많은데 일은 하나만

가장 흔한 예는 scheduled job입니다. `@Scheduled`는 각 JVM에서 잘 동작합니다. 너무 잘 동작해서 문제입니다.
pod가 3개면 tick도 3개입니다.

```kotlin
val result = leaderElector.runIfLeader("nightly-settlement") {
    settlementService.processYesterday()
}

if (result == null) {
    log.info { "다른 인스턴스가 실행 중이므로 skip" }
}
```

여기서 핵심은 `null`입니다. 리더가 아니면 예외를 던지지 않고 조용히 건너뜁니다. 이는 ShedLock을 써 본
사람에게 익숙한 skip semantics입니다. 실패가 아니라 경합에서 진 것입니다. 경합에서 졌다고 error log를
쌓으면, 다음 장애 때 진짜 error가 로그 더미에서 손을 흔들어야 합니다.

`runIfLeader`의 기본 계약은 단순합니다.

- lock을 얻은 호출만 action을 실행합니다.
- lock을 얻지 못하면 `null`을 반환합니다.
- action이 예외를 던지면 호출자에게 전파합니다.
- lease가 끝나거나 실행이 끝나면 backend 정책에 따라 leadership을 해제하거나 만료시킵니다.

정확한 결과 구분이 필요하면 `LeaderRunResult`를 씁니다. action 자체가 `null`을 반환할 수 있는 코드에서는
단순 `T?`보다 명시적인 결과 타입이 낫습니다.

```kotlin
when (val result = leaderElector.runIfLeaderResult("daily-job") { runJob() }) {
    is LeaderRunResult.Elected -> log.info { "executed=${result.value}" }
    LeaderRunResult.Skipped -> log.info { "another node is leader" }
    is LeaderRunResult.ActionFailed -> log.warn(result.cause) { "leader action failed" }
}
```

관련 소스:
[LeaderElector.kt](https://github.com/bluetape4k/bluetape4k-leader/blob/develop/leader-core/src/main/kotlin/io/bluetape4k/leader/LeaderElector.kt),
[LeaderRunResult.kt](https://github.com/bluetape4k/bluetape4k-leader/blob/develop/leader-core/src/main/kotlin/io/bluetape4k/leader/LeaderRunResult.kt)

## 저장소 지도

`bluetape4k-leader`가 `bluetape4k-projects` 안에 머무르지 않고 독립 저장소가 된 이유는 범위가 꽤 넓기
때문입니다. core API만 있으면 단순하지만, 실제 운영에서는 backend parity, lease semantics, Spring/Ktor 통합,
metrics, examples, benchmark가 같이 따라옵니다.

  <figcaption>core API는 작게 유지하고, backend와 framework integration은 독립 모듈로 분리합니다.</figcaption>

| 영역 | 대표 모듈 | 읽어야 하는 순간 |
|---|---|---|
| Core API | `leader-core` | `LeaderElector`, `SuspendLeaderElector`, group election, result type을 이해할 때 |
| Redis | `leader-redis-lettuce`, `leader-redis-redisson` | 가장 빠르게 분산 lock/lease를 붙이고 싶을 때 |
| SQL/Coroutine | `leader-exposed-jdbc`, `leader-exposed-r2dbc` | 이미 RDB를 운영 중이고 row 기반 lease가 자연스러울 때 |
| Infra-native | `leader-etcd`, `leader-k8s`, `leader-consul` | platform의 lease/session 기능을 직접 쓰고 싶을 때 |
| Framework | `leader-spring-boot`, `leader-ktor`, `leader-micrometer` | annotation, scheduler, actuator/metrics와 연결할 때 |
| Examples/Benchmark | `examples/*`, `benchmark` | 운영 시나리오와 backend 비용을 같이 볼 때 |

현재 README 기준으로 stable backend에는 Redis Lettuce/Redisson, Exposed JDBC/R2DBC, MongoDB, Hazelcast,
ZooKeeper가 있고, DynamoDB, etcd, Consul, Kubernetes Lease는 preview로 정리되어 있습니다.

## 실행 모델이 중요한 이유

ShedLock 스타일의 annotation skip semantics만 필요하면 선택지는 많습니다. `bluetape4k-leader`가 더 신경 쓰는
부분은 "서비스 코드의 실행 모델을 억지로 바꾸지 않는 것"입니다.

Kotlin 서비스에서는 같은 leader election이라도 호출 지점이 다릅니다.

| 실행 모델 | API | 어울리는 코드 |
|---|---|---|
| Blocking | `LeaderElector` | 기존 MVC, batch, plain JVM job |
| Async | `AsyncLeaderElector` | `CompletableFuture` 기반 adapter |
| Coroutine | `SuspendLeaderElector` | suspend service, R2DBC, Ktor handler |
| Virtual thread | `VirtualThreadLeaderElector` | Java 21 virtual-thread 실행 경계 |

Coroutine API는 action이 `suspend`입니다. 취소가 들어오면 `CancellationException`을 감추지 않고 다시 던져야
합니다. 이것은 작은 구현 디테일처럼 보이지만, long-running worker에서는 생명줄입니다. 취소를 삼킨 리더는
종료 중인 서비스에서 일을 계속 붙잡고 있을 수 있습니다.

```kotlin
val result = suspendLeaderElector.runIfLeader("tenant-aggregator") {
    metricsService.aggregateTenant(tenantId)
}
```

관련 소스:
[SuspendLeaderElector.kt](https://github.com/bluetape4k/bluetape4k-leader/blob/develop/leader-core/src/main/kotlin/io/bluetape4k/leader/coroutines/SuspendLeaderElector.kt),
[LeaderElectionOptions.kt](https://github.com/bluetape4k/bluetape4k-leader/blob/develop/leader-core/src/main/kotlin/io/bluetape4k/leader/LeaderElectionOptions.kt)

## ShedLock과 비교하면

ShedLock은 scheduled job 중복 실행을 막는 실전적인 도구입니다. `bluetape4k-leader`도 그 핵심 동작을 공유합니다.
락을 못 얻으면 조용히 skip하는 동작은 일부러 익숙하게 둡니다. 다만 목표가 "Spring scheduled method 보호"에서
멈추지 않습니다.

| 항목 | ShedLock 방식 | bluetape4k-leader 방식 |
|---|---|---|
| 경합 처리 | lock 미획득 시 skip | `runIfLeader`가 `null`, result API는 `Skipped` |
| Spring annotation | 주 사용 경로 | 지원하지만 core API와 분리 |
| Coroutine | 별도 적응 필요 | `SuspendLeaderElector` 제공 |
| Async | 제한적/adapter 필요 | `AsyncLeaderElector` 제공 |
| Virtual thread | 일반 blocking 코드로 가능 | 별도 virtual-thread elector 계층 제공 |
| Multi-leader | 주 목적 아님 | `LeaderGroupElector`로 N개 동시 리더 |
| Strategy election | 주 목적 아님 | FIFO, random, scored, weighted 전략 선출 |
| Backend 폭 | 여러 lock provider | Redis, SQL/R2DBC, MongoDB, DynamoDB, etcd, Kubernetes, Hazelcast, ZooKeeper |

따라서 "Spring scheduled job 하나를 막고 싶다"면 ShedLock과 문제의식이 겹칩니다. 반대로 coroutine worker,
테넌트별 polling, 여러 노드가 N개 슬롯을 나눠 쓰는 작업, Kubernetes Lease 기반 operator, Ktor scheduler까지
같은 언어로 묶고 싶다면 `bluetape4k-leader` 쪽이 더 넓은 모델입니다.

## 선택 기준

처음부터 모든 backend를 비교하려고 하면 금방 지칩니다. Part 5에서 backend picker를 따로 다루겠지만,
첫 글에서는 아래 정도만 잡으면 충분합니다.

- Redis를 이미 운영하고 있으면 Lettuce/Redisson이 가장 빠른 시작점입니다.
- RDB만 있는 서비스라면 Exposed JDBC/R2DBC가 운영 부담을 줄입니다.
- Kubernetes operator나 platform-native controller라면 Kubernetes Lease가 자연스럽습니다.
- etcd/Consul/ZooKeeper를 이미 control plane으로 쓰고 있다면 해당 session/lease 모델을 검토할 만합니다.
- 같은 작업을 N개까지 허용해야 하면 단일 leader가 아니라 `LeaderGroupElector`를 봅니다.
- "가장 오래 쉰 노드", "가중치가 높은 후보"처럼 선택 규칙이 필요하면 strategic election을 봅니다.

## 마무리

리더 선출은 "분산 시스템"이라는 큰 말보다 "한 번만 해야 하는 일을 진짜 한 번만 하자"에 가깝습니다.
scheduled job, migration, poller, cache warmer, operator reconcile loop는 모두 같은 질문을 던집니다.
지금 이 replica가 실행해도 되는가?

`bluetape4k-leader`는 그 질문을 backend별 API가 아니라 공통 실행 모델로 다룹니다. Part 2에서는 이 공통
실행 모델의 중심인 `LeaderElector`, `SuspendLeaderElector`, `LeaderElectionOptions`, `LeaderRunResult`를
조금 더 깊게 보겠습니다. 여기서부터는 "누가 왕관을 쓰는가"보다 "왕관을 못 쓴 노드는 조용히 무엇을 해야
하는가"가 중요해집니다.
