<p class="bt4k-post-meta">2026-08-14 · 병원 예약 서비스 개발기 · 대기 목록 핵심과 빈자리 회복</p>

환자 A가 오전 10시 예약을 취소했습니다. 환자 B는 같은 시간대를 기다리고 있었고, 환자 C는 VIP 우선순위가 있지만 의사와 진료 항목이 맞지 않습니다. 알림 발송은 한 번 실패했고, 그 사이 두 개의 scheduler 인스턴스가 같은 빈자리를 발견했습니다.

`waitlist.sortBy { it.createdAt }`와 `notification.send()`만으로 이 흐름을 만들면 곧 네 가지 질문에 막힙니다.

- B가 정말 이 병원·진료·의사·시간대에 적격한가?
- 제안이 만들어졌지만 알림이 실패하면 빈자리는 누구에게 남아 있는가?
- 두 worker가 동시에 같은 후보를 승격할 때 capacity hold는 몇 개가 생기는가?
- B가 같은 claim을 재전송하거나 만료된 링크를 누르면 어떤 응답을 재현할 수 있는가?

이 글의 결론은 간단합니다.

> **대기 목록은 이름 목록이 아니라 상태 머신입니다. `WAITING` 후보를 hard eligibility와 결정적 순서로 줄인 뒤, 빈자리 하나에 `OFFERED`·durable hold 하나를 만들고, claim은 예약 생성과 분리된 `ACCEPTED` command handoff로 기록해야 합니다.**

## 빈자리를 다시 예약하는 문제는 후보 조회가 아니라 상태 문제다

대기 후보를 읽는 일과 후보를 승격하는 일은 같은 트랜잭션이 아닙니다. 현재 `clinic-appointment` 구현도 이 경계를 분리합니다. `WaitlistCandidateMatcher`는 bounded keyset page로 후보를 읽고 `BookingReliabilityDecision`을 batch로 결합하지만 row lock을 잡지 않습니다. 실제 승격은 `WaitlistOfferService`가 entry와 자원을 다시 잠그고 재검증하는 단계에서 일어납니다.

  <img src="/assets/clinic-appointment-waitlist-state-01-ko.png" alt="WAITING에서 hard eligibility와 결정적 순서를 거쳐 OFFERED가 되고, claim 뒤 ACCEPTED command handoff로 이어지며, 거절·만료·철회는 별도 terminal 상태로 남는 대기 목록 상태 머신" loading="lazy" />
  <figcaption>수락은 예약 행을 곧바로 생성하는 일이 아닙니다. durable hold와 command receipt를 남긴 뒤 별도 replacement command가 appointment를 만들도록 경계를 유지합니다.</figcaption>
</figure>

상태를 명시하면 알림과 데이터베이스의 책임도 분리됩니다.

| 상태 | 의미 | 다음 책임 |
| --- | --- | --- |
| `WAITING` | 아직 concrete offer를 받지 않은 적격 대기 항목 | 빈자리와 정책이 맞는지 다시 평가 |
| `OFFERED` | 만료 시각과 capacity hold가 연결된 제안 | 후보의 응답·만료·재전송을 기록 |
| `ACCEPTED` | 후보가 claim했고 후속 예약 명령이 소비할 durable hold | appointment 생성 command로 handoff |
| `DECLINED` | 후보 또는 운영자가 거절한 terminal offer | 사유·억제 정책·다음 후보 진행 |
| `EXPIRED` | 제안·hold 또는 시작 시각이 지나 닫힌 상태 | reconcile 후에만 재시도 |
| `WITHDRAWN` | 운영자나 recovery가 철회한 상태 | 원인과 correlation을 보존 |

특히 `ACCEPTED`를 `CONFIRMED`와 같은 말로 쓰면 안 됩니다. 현재 `WaitlistOfferClaimService`가 반환하는 것은 `holdId`와 만료 정보이며, appointment 생성은 이 서비스의 책임이 아닙니다. 이렇게 해야 claim 처리와 예약 생성 command를 독립적으로 재시도할 수 있습니다.

## 후보를 먼저 줄이고, 그 다음 정책을 적용한다

대기 목록의 순서를 먼저 만들고 나중에 권한을 검사하면, 자격이 없는 후보가 빈자리를 잠시 점유할 수 있습니다. 순서는 다음처럼 고정합니다.

1. **hard eligibility**: `tenant`, `clinic`, treatment, doctor, 시간 창, 자원 요구를 확인합니다.
2. **정책 입력**: 병원 정책 버전과 `BookingReliabilityDecision`을 읽기 전용으로 batch 결합합니다. decision을 계산하거나 고객 등급을 복사하지 않습니다.
3. **결정적 keyset 순서**: `slotFit DESC → priorityRank DESC → waitingSince ASC → entryId ASC`를 사용합니다. 마지막 `entryId`가 있어야 같은 시각·같은 우선순위에서 순서가 흔들리지 않습니다.
4. **bounded page와 시간 예산**: 후보를 무한히 스캔하지 않고 page·candidate 수·시간 예산을 제한합니다.
5. **재검증**: 후보를 승격하기 직전에 같은 트랜잭션에서 entry, policy stamp, resource를 다시 확인합니다.

VIP 신호가 있더라도 이 순서를 무시할 수 없습니다. VIP는 적격 후보의 `priorityRank`를 정하는 정책 입력일 뿐이고, 다른 tenant의 후보를 보거나 이미 `CONFIRMED`인 예약을 빼앗는 권한이 아닙니다. `BookingReliabilityDecision`이 `STALE`이거나 `UNAVAILABLE`이면 자동 승격을 확정하지 않고 staff review·재조회·다음 후보 중 정책에 맞는 경로로 보냅니다.

## 빈자리에는 active offer만 남긴다

두 scheduler가 동시에 취소 이벤트를 읽으면 Redis lock 하나만으로는 충분하지 않습니다. Redis는 advisory deduplication을 줄이는 보조 수단일 수 있지만, 최종 상태·소유자·capacity는 PostgreSQL/MySQL/H2가 참여한 DB 트랜잭션과 version/CAS fence가 결정해야 합니다.

현재 설계의 핵심 불변식은 세 가지입니다.

- 같은 `vacancyKey`에 active `OFFERED` 또는 `ACCEPTED` offer를 하나만 둡니다.
- `OFFERED`와 `ACCEPTED`는 availability의 capacity hold와 연결되어야 합니다.
- 후보 조회는 낙관적이고 재현 가능하게, 승격·claim은 resource-first lock과 CAS로 수행합니다.

그래서 `WaitlistOfferService`는 빈자리 fence를 얻은 뒤 hard eligibility, policy stamp, 후보 버전을 같은 caller-owned Exposed transaction에서 확인하고, offer·hold·event를 함께 commit합니다. 다른 worker가 먼저 commit했다면 중복 알림을 보내기 전에 DB 결과를 읽고 멈춰야 합니다.

## claim은 알림 수신이 아니라 durable handoff다

알림이 도착했다는 사실은 후보가 빈자리를 소유했다는 뜻이 아닙니다. claim API는 공개 식별자, tenant·clinic scope, `expectedVersion`, idempotency key를 받아 다음을 확인합니다.

- offer와 entry가 같은 scope인지 확인합니다. 다른 scope의 opaque ref는 존재 여부를 추측할 수 있는 오류를 주지 않습니다.
- offer·hold·entry를 필요한 순서로 잠그고 owner, 상태, version, expiry, 시작 시각, resource 점유를 검증합니다.
- `OFFERED → ACCEPTED`와 hold 상태 전이를 CAS로 수행하고 command receipt를 append합니다.
- 같은 idempotency key를 다시 보내면 새 hold를 만들지 않고 같은 결과를 replay합니다.
- stale decision, expired offer, 이미 점유된 slot, version 충돌은 성공으로 위장하지 않고 재현 가능한 conflict로 반환합니다.

## tenant 경계와 개인정보는 저장 모델에서 강제한다

대기 항목은 고객 이름이나 전화번호를 검색하는 기능이 아닙니다. 내부 DB에는 scope와 opaque ID만 저장하고, 공개 API도 예측하기 어려운 public ref를 사용합니다.

| 경계 | 설계 규칙 |
| --- | --- |
| `tenant`·`clinic` | 모든 entry, offer, hold, event 조회에 같은 `WaitlistScope`를 전달 |
| 후보 식별자 | 내부 정수 ID 대신 opaque public ref와 짧은 수명의 claim token 사용 |
| 정책 provenance | `policyVersion`, digest, decision ID, expiry를 offer와 event에 기록 |
| 관측 로그 | 이름·전화번호·원문 상담 메모 대신 상태, reason code, correlation ID를 기록 |
| scope 오류 | 다른 tenant·clinic ref를 404처럼 처리해 존재 여부를 노출하지 않음 |

이 경계가 있어야 운영자가 “왜 이 후보가 먼저였는가”를 설명하면서도 다른 환자의 개인정보를 검색 결과나 로그에 섞지 않습니다. provenance는 장식이 아니라 replay·이의제기·복구에 필요한 데이터입니다.

## 알림 실패와 rollout off에서도 회복한다

대기열 기능을 끄는 것은 이미 만들어진 상태를 삭제하는 일이 아닙니다. `enabled=false` 또는 allowlist 밖인 경우 새 dispatch와 알림을 멈출 수 있지만, 다음 작업은 계속 가능해야 합니다.

- 만료된 offer와 hold를 닫습니다.
- delivery outbox의 lease와 retry를 정리합니다.
- stale offer, missing hold, stuck command를 bounded reconcile합니다.
- 억제 정책과 event history를 지우지 않습니다.
- 다시 켰을 때 같은 vacancy에 중복 offer를 만들지 않습니다.

rollback도 마찬가지입니다. 수동 SQL로 offer나 hold를 삭제하지 않고, 운영 command와 recovery service가 상태 전이·reason·correlation을 남기도록 해야 합니다. 이 규칙이 없으면 알림 장애를 고치다가 capacity를 다시 열어 두 후보에게 같은 시간을 제안하게 됩니다.

## 현재 구현, 승인된 설계, 운영 준비를 구분한다

이 글은 `clinic-appointment`의 `develop` 소스와 Issue #170 설계·runbook을 2026-08-14에 대조해 작성했습니다. 코드가 존재한다는 사실과 모든 병원이 해당 기능을 켰다는 사실은 다릅니다.

| 구분 | 이 글에서 확인한 범위 |
| --- | --- |
| **현재 구현** | `WaitlistCandidateMatcher`의 bounded candidate/decision batch, `WaitlistOfferService`의 offer·hold 전이, `WaitlistOfferClaimService`의 owner/version/expiry 검증, `WaitlistRecoveryService`의 만료·stale 복구, delivery API 모델 |
| **승인된 설계** | hard eligibility 선행, vacancy당 active offer 하나, DB fence/CAS 권위, opaque ref, notification과 acceptance 분리, appointment command handoff |
| **운영 준비** | migration V18/V19, contention·scope·PII·replay 테스트, feature flag false→allowlist rollout, reconcile 상한과 alert/runbook |
| **로드맵** | 후보별 공정성 지표, 운영자 bulk review, 채널별 알림 provider 확장, 실제 병원 정책의 shadow 관찰과 ENFORCE 전환 |

따라서 “대기 목록 core가 구현됐다”는 말은 서비스 경계와 테스트가 준비됐다는 뜻이지, 특정 병원의 production allowlist와 운영 증거가 완료됐다는 뜻이 아닙니다. 배포 전에는 `OFF`에서 expiry·suppression·reconcile이 계속 도는지, notification provider 장애가 claim 상태를 바꾸지 않는지, 동일 vacancy contention에서 한 offer만 남는지를 별도로 확인해야 합니다.

## 핵심은 먼저 연락하는 속도가 아니라 상태의 소유권이다

빈자리를 빨리 채우는 것은 중요합니다. 그러나 더 중요한 질문은 “누가 먼저 문자를 받았는가?”가 아니라 다음과 같습니다.

> “이 후보는 같은 tenant·clinic의 hard eligibility를 통과했고, 이 정책 버전으로 이 순서에 놓였으며, 이 vacancy의 hold를 이 version fence 안에서 claim했습니다. 알림이 실패하거나 요청이 replay되어도 같은 상태와 receipt를 설명할 수 있습니다.”

이 문장을 말할 수 있다면 대기 목록은 단순한 연락처 배열이 아니라 운영 가능한 예약 도메인 모델입니다. 다음 글에서는 이 core 상태를 공개 delivery API와 staff 운영 화면에 어떻게 노출할지 살펴보겠습니다.
