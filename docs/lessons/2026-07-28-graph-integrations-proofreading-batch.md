# Graph Part 4~5 교정 배치 교훈

## 배경

Graph 시리즈 Part 4~5는 그래프 기능을 서비스에 통합하는 경계와 가상 스레드
어댑터의 비용을 설명한다. 이번 교정에서는 예제 코드가 실제 생성자·초기화·종료
계약을 따르는지 확인하고, 공통 API의 계약과 백엔드별 운영 특성을 구분했다.
2026-04-17에 보존된 JMH 결과는 현재 성능 보장이 아니라 당시 조건의 측정값으로
범위를 한정했다.

## 확인한 교정 원칙

### 프레임워크 예제도 실행 계약을 정확히 반영한다

- 서비스 생성자 인자, `initialize()` 호출, 종료 시 delegate 정리는 설명용
  코드에서도 생략하지 않는다.
- 코루틴 요청 처리기는 동기 API를 임의로 감싸지 않고, 저장소가 제공하는
  suspend 파사드와 실제 서비스 구현을 확인한다.
- 호출자가 주입한 자원과 플러그인이 생성한 자원의 소유권을 구분한다. 종료
  책임을 명시하지 않으면 예제의 수명 주기 계약이 모호해진다.

### 초기화와 백엔드 동등성을 과장하지 않는다

- `graphExists()` 확인 뒤 `createGraph()`를 호출하는 순서는 단일 프로세스의
  편의 코드일 뿐이다. 다중 인스턴스에서 원자적이거나 멱등적이라고 표현하려면
  upsert, 잠금 또는 동일한 보장이 필요하다.
- 공통 서비스 계약이 같아도 색인, 질의 계획, 트랜잭션, 실패 동작까지 같다고
  단정하지 않는다. 실제 백엔드별 통합 시험과 대표 부하 시험이 필요하다.
- 반복 탐색이 N+1 질의를 만들 수 있는 지점과 `limit` 적용 위치를 구현에서
  확인한다. 관계 방향만 보고 ERD의 카디널리티·소유권·유일성을 추정하지 않는다.

### 가상 스레드 벤치마크는 측정 대상을 먼저 밝힌다

- 작업 제출 직후 `Future.join()`을 호출한 측정은 동시 처리량이 아니라
  스레드 생성·스케줄링·대기까지 포함한 종단 간 어댑터 비용을 보여준다.
- 수 마이크로초의 차이는 해당 TinkerGraph 픽스처와 JMH 조건에 한정한다.
  네트워크 백엔드, 커넥션 풀, 서버 부하가 달라지면 결과도 달라진다.
- 가상 스레드는 블로킹 작업의 동시성 확장을 돕지만, 개별 작업을 더 빠르게
  만드는 기능은 아니다. 이 경계는 OpenJDK JEP 444의 설명과 함께 제시한다.

### 다이어그램은 관계 의미와 측정 범위를 시각적으로 보존한다

- ERD 연결선이 다른 카드나 관계선을 관통하면 의미가 바뀔 수 있다. 자동 생성
  성공 뒤에도 원본 크기 PNG에서 경로를 확인하고, 필요한 관계는 명시적 우회
  경로를 지정한다.
- 한영 다이어그램은 구조와 수치를 같게 유지하면서 제목·라벨·보충 설명을
  언어별 자산으로 분리한다.
- ERD의 관계 방향은 소스에서 확인하되, 근거가 없는 카디널리티 표시는
  추가하지 않는다.

## 체크리스트 반영

이번 배치에서 반복 적용할 수 있는 규칙을 chezmoi 원본
`bluetape-writer` 한국어 교정 체크리스트에 추가했다.

- 생성자·설정·초기화·종료 계약을 포함한 프레임워크 예제 검증
- 코루틴 요청 처리기의 소스 기반 suspend 파사드 확인
- `exists -> create` 순서와 다중 인스턴스 멱등성의 분리
- 즉시 `Future.join()` 벤치마크의 증거 범위와 가상 스레드의 scale/speed 구분
- 관계 방향만으로 ERD 카디널리티·소유권·유일성을 추정하지 않는 규칙

chezmoi apply 후 원본과 live skill의 byte parity를 확인했고, dotfiles
commit `02c6573`을 upstream에 push했다. 별도로 존재하던 live-owned
`config.toml`과 native subagent watchdog drift는 이번 범위 밖이므로
변경하지 않았다.

가상 스레드의 공식 근거는 bluetape4k-wiki에 한국어 연구 노트로 보존했고,
commit `57c8ffd`을 upstream에 push했다.

## 다음 작업에 적용할 지침
