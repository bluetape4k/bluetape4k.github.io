## 교정에서 확인한 경계

### 데이터베이스 커밋과 애플리케이션 이벤트 발행은 같은 보장이 아니다

현재 `AppointmentService`는 예약 상태와 변경 이력을 하나의 Exposed
트랜잭션으로 커밋한 뒤 Spring `ApplicationEventPublisher`로 이벤트를
발행한다. 따라서 이벤트 수신부가 실패해도 이미 커밋한 상태와 이력은
되돌아가지 않는다. 프로세스 내부의 후속 반응과 내구성 있는 전달을 구분하고,
후자가 필요하면 아웃박스·재시도·재처리 경계를 별도로 설명해야 한다.

### 제약 조건의 존재만으로 운영 규칙 적용을 주장할 수 없다

Solver 도메인에 `EquipmentUnavailabilityFact`가 있고 H11 제약이 정의돼
있더라도 실행 진입점이 그 사실을 읽어 `ScheduleSolution`에 공급하지 않으면
해당 규칙은 평가되지 않는다. 문제 정보의 자료형, 제약 정의, 실행 입력 적재
경로를 함께 추적해야 한다. `isFeasible`도 그 실행에서 실제로 공급된 문제
정보에 대해서만 의미가 있다.

### 복수 자원은 AND·OR·수량 의미를 먼저 정해야 한다

한 진료에 여러 장비를 연결할 수 있다는 자료 구조만으로 복수 장비 요구사항이
완성되지는 않는다. 모든 장비가 필요한지, 대체 장비 중 하나만 있으면 되는지,
각 장비가 몇 대 필요한지를 정해야 가용성·사용 불가 시간·수량·Solver 제약을
같은 의미로 구현할 수 있다. 단일 장비 테스트는 복수 장비 의미를 증명하지
못한다.

### 다이어그램의 결론 문구도 구현 범위를 넘지 않아야 한다

예약 가능 시간 파이프라인의 `모든 조건을 통과한 시간만 반환`은 아직 정의되지
않은 복수 장비 의미까지 완료된 것처럼 읽힐 수 있었다. 이를 `현재 구현의
조건을 통과한 시간만 반환`으로 바꾸고 영어 자산도 같은 범위로 맞췄다.
다이어그램의 짧은 결론도 본문의 사실 경계와 같은 수준으로 검증해야 한다.

## 체크리스트 반영

위 교훈 가운데 재사용 가능한 세 규칙을 chezmoi 원본의
`bluetape-writer` 한국어 자연스러움 체크리스트에 추가했다.

1. 프로세스 내부 이벤트와 내구성 있는 전달을 트랜잭션 경계로 구분한다.
2. Solver 제약은 실제 실행 입력의 문제 정보 적재 경로까지 확인한다.
3. 복수 자원 요구사항은 AND·OR·수량 의미와 테스트를 함께 검증한다.

`chezmoi apply`, 원본·실제 파일 SHA-256 일치, Codex 자체 점검, dotfiles
`main` 푸시까지 완료했다.

## 다음 배치에 적용할 항목

1. 작업 전에 갱신된 실제 writer 체크리스트를 다시 읽는다.
2. 데이터베이스 커밋과 후속 이벤트·메시지 발행의 실패 경계를 확인한다.
3. 자료형이나 제약 정의뿐 아니라 실행 진입점의 입력 적재 경로를 추적한다.
4. 여러 자원을 다루면 AND·OR·수량 의미가 명시됐는지 확인한다.
5. 본문뿐 아니라 다이어그램의 요약 문구도 같은 구현 범위로 제한한다.
