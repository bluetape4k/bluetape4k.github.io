# Dependencies 운영 글 교정 배치 교훈

## 배경

이번 배치는 `bluetape4k-dependencies` 사용 가이드와 1.3.0 활용기 Part 2·3을
교정했다. 세 글은 BOM 사용법, 서비스 경계별 모듈 선택, 운영 신호를 하나의
흐름으로 설명하지만, 코드와 상태 응답 일부가 현재 소스와 특정 릴리스의 API를
혼합하고 있었다. 문체 교정에 그치지 않고 독자가 실제 계약과 설명용 예제를
구분할 수 있도록 사실 경계를 다시 세우는 것이 핵심이었다.

## 확인한 교정 원칙

### 릴리스 상태 응답은 태그 소스로 검증한다

- `Exposed 1.11.0`의 JDBC 캐시 상태 표시기는 `reports` 배열과
  `mode`, `queueDepth`, `flushJobRunning`, `lastFlushError`를 제공한다.
- 현재 기본 브랜치의 후속 구조나 존재하지 않는 필드를 과거 릴리스 예제에
  섞지 않는다.
- 과거 릴리스 활용기라면 예제가 어느 태그의 계약인지 본문에 명시한다.

### 라이브러리 API와 애플리케이션 소유 예제를 분리한다

- CloudWatch 예제는 `aws 0.4.0`의 실제 `CloudWatchKtorPlugin`,
  `CloudWatchLogsKtorPlugin` 이름과 설정 속성을 사용한다.
- 애플리케이션이 정한 YAML 이름 정책이나 입력 길이 검사 도우미는 라이브러리
  자동 구성·공개 API처럼 제시하지 않는다.
- 의사코드가 필요하면 본문이나 코드 주석에서 애플리케이션 소유 경계임을
  표시한다.

### 플러그인 설치와 데이터 발행을 구분한다

- 플러그인 설치는 통합 기능과 수명 주기 등록을 의미한다.
- 메트릭 게시와 로그 이벤트 추가는 애플리케이션이 명시적으로 수행한다.
- 클라이언트 생성 주체에 따라 종료 책임도 달라지므로 등록, 발행, 버퍼,
  flush, 소유권을 하나의 자동 동작으로 축약하지 않는다.

### 다이어그램은 글의 판단 구조를 보강해야 한다

- 사용 가이드는 중앙 BOM과 문서화된 임시 예외를 분리했다.
- 서비스 조합 글은 같은 BOM 아래에서도 워커, 검색 API, 이미지 API가 서로
  다른 모듈을 선택하는 이유를 보여 준다.
- 운영 신호 글은 통합 기능의 상태·이벤트가 명시적 발행, 관측, 진단·복구
  결정으로 이어지는 경계를 보여 준다.
- 한영 SVG를 별도로 렌더링하고 영어 글꼴에서 지원하지 않는 구분 문자를
  `/`로 바꿔 대체 글리프를 제거했다.

## 체크리스트 반영

이번 배치에서 재사용할 수 있는 다음 규칙을 chezmoi 원본
`bluetape-writer` 한국어 교정 체크리스트에 추가했다.

- 릴리스 운영 응답·설정 객체의 필드를 해당 태그 소스로 검증하는 규칙
- 애플리케이션 소유 도우미·설정·이름 정책과 라이브러리 API의 구분
- 플러그인 등록과 명시적 데이터 발행·버퍼·수명 주기 책임의 구분
- 공개 BOM 버전과 저장소 내부 카탈로그 메타데이터의 구분

chezmoi apply 후 원본과 live skill의 byte parity를 확인했고, dotfiles
commit `f25b110`을 upstream에 push했다. self-audit는 `PASS=7`,
`WARN=0`, `FAIL=0`으로 통과했다.
