## 사실 검증 lessons

- 비교 글에서는 현재 구현과 공식 호환성 표로 확인할 수 있는 범위만 설명해야 한다. 아직 구현하지 않은 기능이나
  로드맵을 경쟁 제품과의 차이로 제시하면 독자가 현재 제공 기능으로 오해할 수 있다.
- 한 프로젝트 안에서도 모듈별 의존성 공개 정책은 다를 수 있다. `api`, `implementation`, `compileOnly`를
  프로젝트 전체의 단일 정책으로 일반화하지 않고 실제로 선택한 모듈의 빌드 파일을 확인해야 한다.
- 메시지 파서의 입력 형식 검증과 인증서 체인·암호학적 서명 검증은 서로 다른 신뢰 경계다. 파서가 필드와
  인증서 URL 형식을 확인한다는 이유만으로 메시지 인증까지 완료된 것으로 설명하면 안 된다.
- 실행 예제는 README의 설명만 확인하지 않는다. 빌드 의존성, 프로필, 라우팅, 명령, 대표 구현을 함께 대조해야
  서비스 경계와 실행 절차를 정확히 설명할 수 있다.

## 한국어 교정 lessons

- 기술 문서에서는 `확인 응답`, `제한 시간 URL`, `사용감`, `돌리다` 같은 직역·구어 표현을 피하고,
  문맥에 따라 `승인 처리`, `유효 기간이 제한된 URL`, `개발 방식`, `실행하다`로 구체화한다.
- 한국어 참고 자료의 절 제목과 링크 설명은 독자가 목적을 바로 파악하도록 한국어로 작성한다.
  파일명, 모듈명, API, 설정 키처럼 검색과 대조에 필요한 식별자는 원문을 유지한다.

## 다이어그램 lessons

- 기존 Graphviz 중간 산출물이 최종 자산과 함께 남아 있으면 어떤 파일이 편집 원본인지 모호해진다. 생성기가
  완결된 KO/EN SVG와 CairoSVG PNG를 직접 만들면 `.dot`, `.plain`, `-sketch` 자산은 제거한다.
- 정적 감사가 CSS marker를 사용하는 실제 연결선을 모두 집계하지 못하면 통과 여부만 신뢰하지 않는다.
  이번 배치에서는 카드·직교 연결선·14×14 화살촉·캔버스 경계를 별도 불변식으로 검증했다.
- SVG에서 색상을 바꾼 뒤에는 반드시 최종 PNG를 원본 크기로 확인해야 한다. S3와 SQS 다이어그램의 푸터는
  이 단계에서 흰 배경과 흰 글자 문제를 찾아 dark 배경으로 수정했다.
