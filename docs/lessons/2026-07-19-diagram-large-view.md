# 기술 다이어그램 확대 UI에서 콘텐츠 의미와 클릭 표면을 분리하기

## 맥락

블로그와 매뉴얼은 기술 다이어그램을 표시하는 방식이 다르다. 블로그는 의미가 있는 `figure` 클래스를 사용하고, 매뉴얼은 관리되는 `/manual-assets/` 경로를 사용한다. 모든 본문 이미지를 하나의 선택자로 확대하면 대표 이미지와 일반 스크린샷까지 기능 대상이 된다.

## 결정

대상 감지는 블로그와 매뉴얼별로 분리하고, 확대 대화상자의 UI와 접근성 동작만 통일했다. 블로그 제목, 캡션과 대체 텍스트는 각각 `data-diagram-title`, `figcaption`, `alt`로 역할을 분리했다. 전체 화면 패널에서는 `<dialog>` 자체뿐 아니라 패널 여백과 이미지 viewport의 빈 영역도 명시적인 닫기 표면으로 취급했다.

## 구현 중 확인한 점

전체 화면 자식 패널이 dialog 영역을 모두 덮으면 `event.target === dialog`만으로는 사용자가 보는 어두운 빈 영역 클릭을 감지하지 못한다. 보이는 클릭 표면과 이벤트 대상이 같은지 브라우저에서 확인해야 한다.

확대 버튼의 위치 기준 요소가 본문 전체 폭을 차지하면 원본 폭이 작은 다이어그램에서 버튼이 이미지와 떨어진다. 위치 기준 요소는 이미지 폭에 맞추되 본문 폭을 넘지 않도록 제한해야 한다.

## 결과

기존 Markdown과 MDX 이미지 문법을 대량 변경하지 않고 기술 다이어그램만 확대한다. 대표 이미지와 일반 스크린샷은 제외하며, JavaScript가 없어도 기존 콘텐츠는 유지된다.

초기 배포 뒤에는 두 가지 콘텐츠 계약 누락이 드러났다. 첫째, 기술 그림이어도 `post-figure`, class 없는 `figure`, Markdown 이미지처럼 의미가 명시되지 않으면 블로그 선택자가 찾을 수 없었다. 둘째, 매뉴얼의 릴리스 README 공유 다이어그램은 `/manual-assets/`가 아니라 immutable `raw.githubusercontent.com` PNG와 GitHub SVG 링크 쌍을 사용했다. 기능 테스트만으로는 이 전체 콘텐츠 표면을 증명할 수 없었다.

보완에서는 블로그 전체 로컬 이미지를 기술 다이어그램, Hero, 스크린샷 중 하나로 명시하도록 계약 테스트를 추가했다. 매뉴얼은 조직, 저장소, 40자리 커밋, 안전한 `readme-diagrams` 상대 경로와 파일 stem이 같은 PNG/SVG 쌍만 허용한다. `benchmark/` 같은 실제 하위 디렉터리도 허용하되 `.`·`..` 또는 쿼리·fragment가 섞인 경로는 거부한다.

README 이미지가 가진 GitHub 링크는 확대 기능과 중복되는 이동 경로였다. 검증을 통과한 경우 링크를 DOM에서 제거하고, 미리보기 PNG는 그대로 표시하되 확대 화면에는 같은 배포 커밋의 SVG를 사용하도록 단순화했다. 이 방식은 버튼을 링크 안에 중첩하지 않으면서 이미지와 아이콘의 동작을 하나로 맞춘다.

## 검증

- 대상과 제목 규칙 Node 테스트
- 전체 `npm test`
- 프로덕션 `npm run build`
- 한국어·영어 블로그와 매뉴얼의 데스크톱·모바일 브라우저 확인
- 작은 원본 다이어그램을 가정한 버튼 위치 확인
- 한국어·영어 매뉴얼 전체 README 공유 PNG/SVG 쌍 검사
- 블로그 전체 로컬 이미지의 명시적 대상·비대상 분류 검사

## 향후 가드

새 블로그 다이어그램은 짧은 현지화 제목을 `data-diagram-title`에 작성한다. 확대 UI를 수정할 때는 버튼이 이미지 우측 상단에 붙어 있는지와 함께 이미지 클릭, `Escape`, 닫기 버튼, 패널과 viewport의 빈 영역 클릭, 포커스 복원을 검증한다.

페이지 하나의 대표 사례만 확인해서 전체 콘텐츠 지원을 주장하지 않는다. selector가 콘텐츠 저작 규칙에 의존한다면 저장소 전체를 순회하는 테스트가 그 규칙을 검증해야 한다. 외부 원본을 지원할 때도 host prefix만으로 신뢰하지 말고 조직·저장소·revision·경로·파일 대응 관계를 하나의 계약으로 확인한다.
