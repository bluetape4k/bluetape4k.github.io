# 요청 제한·OCR·Skills 교정 배치 Lessons

## 범위

- `bucket4j-rate-limiting-proxy-aware-headers`
- `ocr-api-fallback-contract-bluetape4k-image`
- `bluetape-skills-sharing`
- 한국어·영어 글과 기술 다이어그램 7종의 KO/EN SVG·PNG

## 사실과 경계 검증

- `bucket4j-advanced` 필터는 제한기가 반환한 비성공 결과와 `consume` 호출에서 발생한 예외를 다르게 처리한다. 토큰 부족은 `429`로 거부하지만, 예외는 요청을 통과시키는 실패 시 허용 정책을 적용한다.
- 요청 제한기의 저장소가 Redis인지 Caffeine인지보다 호출자 식별 기준이 먼저다. 프록시 헤더 신뢰 범위를 잘못 정하면 분산 버킷을 사용해도 다른 호출자의 토큰을 차감할 수 있다.
- OCR 대체 응답은 잘못된 업로드를 정상화하지 않는다. 콘텐츠 유형, 매직 바이트, 디코딩 픽셀 예산을 통과한 이미지가 네이티브 런타임 문제로 처리되지 못한 경우에만 `UNAVAILABLE` 또는 `FAILED`로 표현한다.
- Bluetape Skills 안정 버전 설치는 변경 가능한 기본 브랜치가 아니라 현재 공개 태그 `v1.2.1`을 기준으로 설명했다. 기존 체크아웃에서 `git pull`을 실행하는 절차와 안정 버전 교체 절차를 구분했다.
- 과거 OCR 글의 미래 계획 문구는 이미 공개된 Image Intelligence Part 1의 한국어·영어 경로로 교체했다. 글의 최초 발행일과 정렬 값은 변경하지 않았다.

## 한국어 교정 교훈

- `bucket`, `identity`, `proxy trust`, `native path`, `managed allocation`처럼 코드 식별자가 아닌 설명 용어는 `버킷`, `호출자 식별`, `프록시 신뢰`, `네이티브 경로`, `관리 힙 할당량`으로 정리했다.
- `fail-open`은 첫 등장에 `실패 시 허용`을 병기하고, 이후 문장에서는 실제 예외 처리 경계를 직접 설명했다. 상태 이름과 정책 이름을 번역하는 것만으로는 구현 차이를 전달할 수 없다.
- 벤치마크 표의 `latency win`, `staging`, `snapshot`, `row` 같은 표현은 `지연 시간 감소`, `임시 저장`, `측정`, `항목`처럼 기술 보고서에서 사용하는 용어로 바꿨다.
- 스킬 이름과 파일 경로는 식별자로 유지하되 일반 명사는 `스킬`, `참조 자료`, `훅`, `푸시`, `프런트매터`로 현지화했다.

## 다이어그램 교훈

- 한국어 다이어그램은 본문 캡션뿐 아니라 제목, 카드, 범례, 설명 문장까지 현지화했다. 명령과 클래스명, 상태값처럼 정확성이 필요한 식별자만 원문을 유지했다.
- 밝은 배경이던 기존 자산을 어두운 배경과 고대비 카드로 통일하고, 한국어와 영어 SVG·PNG를 각각 생성했다.
- 원본 크기 시각 검수에서 Spring 클래스명의 잘림과 범례 대비 부족을 발견해 글꼴 크기와 배치를 조정했다. 축소한 연락처 시트만으로는 확인하기 어려운 결함이었다.
- 최종 자산은 XML 14/14, connector·geometry `--fail-diagonal`·endpoint·mixed-corner 14/14 검사를 통과했으며 PNG 14개가 SVG 기준 2배 크기임을 확인했다.

## 체크리스트 반영

- 요청 제한 글에서 비성공 결과와 예외 경로를 구분하고, 실제 예외 처리기가 요청을 계속 진행할 때만 실패 시 허용이라고 설명하도록 추가했다.
- 안정 버전 설치·갱신 문서에서는 불변 릴리스 태그와 변경 가능한 기본 브랜치 추적 절차를 구분하도록 추가했다.
- 이미 공개된 후속 글을 미래 계획으로 남기지 않고 같은 언어의 실제 글로 연결하되, 최초 발행일은 보존하도록 추가했다.
- chezmoi 원본을 실제 스킬에 적용하고 SHA-256 일치와 자체 점검을 확인한 뒤 dotfiles 커밋 `ebc9d20`을 원격 저장소에 반영했다.
