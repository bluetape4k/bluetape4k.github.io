# 병원 예약 운영 경계 교정 교훈

## 범위

- 병원 예약 Part 5: Timefold 제약 조건과 점수 해석
- 예약 제어 영역: PostgreSQL 최종 권한과 보조 진입 제어
- 리더 선출: 테넌트 작업, 마이그레이션 게이트, 장애 인계
- 한영 기술 다이어그램 7종의 문구 교정과 2배 PNG 재생성

## 교정에서 확인한 경계

### 모델이 표현할 수 있는 정보와 현재 실행이 공급하는 정보는 다르다

`ScheduleSolution`은 장비 사용 불가 시간을 표현할 수 있고 H11 제약도 이를
평가할 수 있다. 그러나 현재 `SolverService.loadSolution()`은 그 정보를
조회해 전달하지 않는다. 따라서 제약 정의와 단위 테스트만으로 운영 경로에서
H11이 적용된다고 설명할 수 없다. 벤치마크의 `0hard`도 Solver에 실제로 공급한
문제 정보에 대해서만 필수 제약 위반이 없다는 뜻이다.

### 보조 진입 제어와 최종 저장 권한을 분리해야 한다

노드 로컬 벌크헤드나 Redis 기반 진입 제어는 정상 동작 중 과도한 요청을
거절할 수 있다. 반면 보조 저장소 자체의 오류에서는 가용성을 위해 해당
검사를 건너뛸 수도 있다. 두 경우를 모두 단순한 `fallback`으로 묶지 말고,
정상적인 용량 초과 거절과 보조 저장소 장애 시의 우회 정책을 구분해야 한다.
좌석 수와 최종 예약 결과를 확정하는 권한은 PostgreSQL 트랜잭션과 행 잠금에
남는다.

### 리스 소유권은 작업 결과의 내구성을 보장하지 않는다

리더 선출은 특정 시점에 어느 인스턴스가 작업할지 조정하고 리스 만료 뒤
장애 인계를 가능하게 한다. 하지만 외부 부수 효과의 정확히 한 번 실행이나
작업 완료 여부까지 보장하지는 않는다. 체크포인트, 멱등 키, 아웃박스,
펜싱 토큰, 재조정 절차처럼 결과를 보호하는 별도 경계를 함께 설명해야 한다.

### 닫힌 이슈를 구현 완료나 향후 약속으로 해석하면 안 된다

Issue #548은 요구사항을 기록했지만 현재 닫혀 있고 통합 실험실 구현도 없다.
이슈의 존재만 보고 미래형 문장을 유지하지 않고, 현재 이슈 상태와 저장소의
실제 구현을 함께 확인해 미구현 범위를 명시했다.

### 다이어그램도 같은 사실 경계를 전달해야 한다

본문에서 제한한 보조 진입 제어, PostgreSQL 최종 권한, 리스 장애 인계의
범위를 다이어그램의 짧은 라벨과 설명에도 반영했다. 그림이 간결하다는 이유로
조건부 동작을 무조건적인 성공 경로처럼 축약하면 안 된다.

## 생성기와 검증에서 얻은 교훈

한국어 문자열 치환 대상이 치환 결과에도 포함되면 생성기를 다시 실행할 때
문구가 중복될 수 있다. `사용 불가 시간`을 `사용 불가 시간(모델)`로 바꾸는
치환이 대표 사례였다. 치환 조건을 정확히 제한하고 생성기를 두 번 실행한 뒤
체크섬이 같은지 확인해야 재현 가능한 자산 생성을 증명할 수 있다.

## 체크리스트 반영

이번 배치에서 반복 적용할 가치가 있는 다음 항목을 chezmoi 원본의
`bluetape-writer` 한국어 자연스러움 체크리스트에 추가했다.

1. 보조 진입 제어의 정상 거절과 저장소 오류 시 우회 정책을 구분한다.
2. 리스 소유권과 내구성 있는 작업 결과·외부 부수 효과를 구분한다.
3. 이슈 상태와 실제 구현을 함께 확인하고 닫힌 이슈를 완료나 약속으로
   해석하지 않는다.
4. 예약·조정 영역의 반복 용어를 한국어 기술 문서 표현으로 통일한다.

## 다음 배치에 적용할 항목

1. 작업 전에 갱신된 실제 writer 체크리스트를 다시 읽는다.
2. 보조 제어와 최종 권한의 정상·장애 경로를 각각 확인한다.
3. 리스나 잠금의 소유권과 작업 결과의 내구성을 분리해 설명한다.
4. 이슈·계획을 언급하면 현재 상태와 구현 존재 여부를 다시 확인한다.
5. 다이어그램 생성기를 두 번 실행해 자산 생성의 멱등성을 검증한다.
