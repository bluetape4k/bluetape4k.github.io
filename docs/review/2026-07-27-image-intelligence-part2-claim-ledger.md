# 이미지 인텔리전스 Part 2 주장 원장

## 목적

Part 2는 OCR·객체 탐지·바코드 분석을 설명하기 전에, 업로드된 이미지가 분석 가능한 입력인지 한 번 판정하고 한 번만 디코딩하는 경계를 다룬다. 아래 표는 글에서 사용할 주장을 `bluetape4k-image`의 실제 구현과 테스트에 연결한다.

## 핵심 주장

| 주장 | 구현 근거 | 테스트 근거 | 글에서의 표현 | 상태 |
| --- | --- | --- | --- | --- |
| 입력 판정은 개별 분석기보다 앞에 있어야 한다. | `ImageIntelligenceService.analyze`는 `qualifier.qualify(file)`이 성공한 뒤에만 `workflow.analyze(qualified.image)`를 호출한다. | 잘못된 형식·크기·해상도 입력은 컨트롤러 테스트에서 분석 결과 대신 400 또는 413으로 종료된다. | “분석기가 무엇을 찾을지 묻기 전에, 이 입력으로 분석을 시작해도 되는지 먼저 판정한다.” | 확인 |
| 선언된 MIME 형식만 믿지 않는다. | `ImageUploadQualifier`는 선언된 콘텐츠 형식과 바이트 시그니처로 판별한 실제 형식을 비교한다. | PNG 바이트를 JPEG로 선언한 입력은 `media_type_mismatch`로 거부되고 디코더 호출 횟수는 0이다. | 클라이언트가 보낸 이름표와 실제 파일 형식을 함께 확인한다고 설명한다. | 확인 |
| 업로드 스트림은 한 번 읽고, 읽은 바이트를 이후 검사에 재사용한다. | `qualify`는 `file.bytes`를 한 번 읽은 뒤 실제 크기, 시그니처, 크기 정보, 디코딩에 같은 `ByteArray`를 사용한다. | 보고된 크기와 실제 크기 초과가 모두 디코딩 전에 거부된다. | “보고된 크기와 실제 바이트 크기를 모두 확인하되, 파일을 검사 단계마다 다시 읽지 않는다.” | 확인 |
| 완전한 디코딩은 값싼 검사들이 통과한 뒤 한 번만 수행한다. | 빈 입력, MIME, 크기, 시그니처, 형식 일치, 이미지 크기, 픽셀 예산 검사가 `imageDecoder(bytes)`보다 앞선다. | 정상 PNG는 디코더를 정확히 한 번 호출하며, 거부된 입력은 디코더를 한 번도 호출하지 않는다. | “싼 거절을 앞에 두고 비싼 디코딩은 마지막에 한 번만 수행한다.” | 확인 |
| 같은 디코딩 결과가 세 분석기에 전달된다. | `QualifiedImage.image`가 `ImageIntelligenceWorkflow.analyze(image)`에 전달되고, 동일한 `ImmutableImage`를 OCR·객체 탐지·바코드 공급자 호출에 사용한다. | 서비스·워크플로 테스트가 단일 입력 이미지로 세 분석 결과를 조합하는 경로를 검증한다. | 분석기마다 원본 바이트를 다시 디코딩하는 구조와, 공통 `QualifiedImage`를 나누어 쓰는 구조를 비교한다. | 확인 |
| 입력 판정 결과와 업무 분석 결과는 서로 다른 의미를 가진다. | `QualifiedImage`는 형식·가로·세로·디코딩 이미지를 담고, OCR·객체 탐지·바코드 결과는 `ImageAnalysisResults`에 별도로 담긴다. | 컨트롤러 테스트는 입력이 유효한 경우에만 `COMPLETED` 응답과 출입 정책 결과를 검증한다. | “입력 판정의 합격은 이미지가 분석 가능하다는 뜻이지, 글자·얼굴·QR을 찾았다는 뜻은 아니다.” | 확인 |
| 취소는 실패 응답으로 바꾸지 않고 상위 코루틴으로 전파한다. | 파일 읽기와 디코딩 예외 처리에서 `CancellationException`을 다시 던진다. | 업로드 읽기 중 발생한 취소가 `image_read_failed`로 변환되지 않고 그대로 전파되는 테스트가 있다. | 요청 취소를 손상된 이미지와 같은 업무 실패로 기록하지 않는다고 설명한다. | 확인 |
| 디코더 내부 오류 정보는 외부 응답에 노출하지 않는다. | 디코딩 실패는 안정적인 `image_not_decodable` 코드로 변환되며, 예외 처리기는 공개 가능한 설명만 반환한다. | 디코더가 내부 비밀이 포함된 오류를 던져도 응답에 그 문자열이 포함되지 않는 테스트가 있다. | “원인은 로그와 진단 경계에 남기고, API에는 안정적인 사유 코드만 공개한다.” | 확인 |

## 판정 순서와 공개 응답

| 순서 | 판정 | 실패 사유 코드 | HTTP 상태 | 디코더 호출 |
| ---: | --- | --- | ---: | ---: |
| 1 | 빈 입력 여부 | `empty_input` | 400 | 0 |
| 2 | 허용된 선언 MIME 여부 | `unsupported_media_type` | 400 | 0 |
| 3 | 업로드가 보고한 크기 | `payload_too_large` | 413 | 0 |
| 4 | 바이트 읽기 성공 여부 | `image_read_failed` | 400 | 0 |
| 5 | 실제 바이트 크기 | `payload_too_large` | 413 | 0 |
| 6 | PNG·JPEG·WebP 시그니처 여부 | `unsupported_image_format` | 400 | 0 |
| 7 | 선언 MIME과 실제 형식 일치 여부 | `media_type_mismatch` | 400 | 0 |
| 8 | 이미지 크기 정보 확인 가능 여부 | `image_not_decodable` | 400 | 0 |
| 9 | 한 변과 전체 픽셀 예산 | `payload_too_large` | 413 | 0 |
| 10 | 전체 이미지 디코딩 | `image_not_decodable` | 400 | 최대 1 |

`ImageIntelligenceProperties`의 기본 제한은 5 MiB, 한 변 8,192픽셀, 전체 16,777,216픽셀이다. 이 값은 보편적인 정답이 아니라 예제의 운영 안전장치이며, 실제 서비스에서는 서버 메모리, 동시 요청 수, 분석기 비용에 맞춰 조정해야 한다.

## 테스트가 증명하는 경계

| 테스트 관점 | 증명할 내용 |
| --- | --- |
| 정상 입력 | 공통 판정을 통과한 이미지가 정확히 한 번 디코딩된다. |
| 형식 거부 | 지원하지 않는 MIME, 시그니처 불일치, 선언과 실제 형식 불일치는 디코딩 전에 끝난다. |
| 용량 거부 | 보고된 크기뿐 아니라 실제로 읽은 바이트 크기도 제한한다. |
| 해상도 거부 | 한 변 또는 전체 픽셀 예산을 넘는 이미지는 전체 디코딩 전에 끝난다. |
| 취소 | 코루틴 취소는 업무 오류로 변환되지 않는다. |
| 오류 위생 | 디코더의 내부 메시지는 공개 API 응답에 노출되지 않는다. |

## 글의 범위에서 제외할 내용

- OCR 엔진 선택과 네이티브 런타임 운영은 기존 OCR 글로 연결한다.
- 일반적인 요청 본문·압축 해제·컬렉션 크기 제한은 기존 입력 경계 글로 연결한다.
- Pure JVM과 libvips의 성능 비교는 기존 벤치마크 글로 연결한다.
- 바이러스 검사, 콘텐츠 무해화, EXIF 개인정보 제거, 이미지 저장 정책은 이 예제가 보장하지 않는 별도 보안·운영 경계로 명시한다.
- 기본 제한값을 모든 서비스에 적용할 권장값처럼 표현하지 않는다.

## 독자용 자료

- `bluetape4k-image`의 `ImageUploadQualifier`: 공통 입력 판정과 단일 디코딩 구현
- `ImageIntelligenceService`와 `ImageIntelligenceWorkflow`: 판정된 이미지가 여러 분석기로 전달되는 경로
- `ImageUploadQualifierTest`: 정상 입력 1회 디코딩과 거부 입력 0회 디코딩을 검증하는 테스트
- 기존 글: OCR API 운영 경계, 서버 입력 경계, Pure JVM과 libvips 성능 비교
