# 한국어 블로그 교정 1차 배치 설계

## 상태

- 작업 유형: Type E 문서 유지보수
- 선정 방식: `blog.date`가 오래된 한국어 글부터 두 편씩 처리
- 1차 대상:
  - `src/content/docs/ko/blog/ai-assisted-library-development.mdx`
  - `src/content/docs/ko/blog/ai-collaboration-environment.mdx`
- 전달 범위: 글과 다이어그램을 로컬에서 검토할 수 있는 상태까지
- 후속 범위: 사용자 승인 뒤 PR을 만들며, 병합과 배포는 별도 승인을 받는다.

## 배경

기존 한국어 블로그 글을 한꺼번에 기계적으로 바꾸면 기술적 의미가 흔들리고 검토 범위도 지나치게 커진다.
따라서 게시일이 오래된 글부터 두 편씩 읽고, 실제 기술 문서와 보고서에서 쓰는 자연스러운 한국어로
교정한다. 각 배치에서 반복해서 발견한 문제는 `bluetape-writer`의 한국어 교정 체크리스트 후보로
축적해 다음 글의 품질 기준으로 재사용한다.

본문에 포함된 기술 다이어그램도 글의 일부다. 다이어그램의 제목, 설명, 카드, 연결선 라벨, 주석에 있는
한국어를 함께 교정한다. 기존에 영어 다이어그램만 공유하는 한국어 글은 한국어 자산을 별도로 만들고,
기술 다이어그램은 현재 사이트의 dark style로 통일한다.

## 목표

1. 오래된 한국어 블로그 글을 게시일 순으로 빠짐없이 교정한다.
2. 사실, 수치, 코드, 식별자와 기술적 의미를 보존하면서 번역체와 부자연스러운 표현을 바로잡는다.
3. 기술 다이어그램의 한국어와 본문 용어를 일치시킨다.
4. 기술 다이어그램을 dark style의 SVG 원본과 PNG 결과물 쌍으로 유지한다.
5. 한국어 글이 영어 다이어그램을 공유할 때 locale별 자산을 분리한다.
6. 여러 글에서 반복되는 교정 규칙을 검증한 뒤 `bluetape-writer` 체크리스트에 반영한다.

## 제외 범위

- 글의 주장, 사례, 벤치마크 수치, 공개일과 기술적 결론 변경
- 코드, 명령, API, 클래스·함수·설정 키와 제품 이름의 임의 번역
- 대표 이미지와 장식용 hero 이미지의 재생성 또는 dark style 변환
- 일반 스크린샷의 재제작 또는 locale 분리
- 이번 두 글보다 새로운 게시일의 글
- 사용자 승인 전 PR 생성, 병합과 배포

## 1차 배치 선정

한국어 블로그의 frontmatter `blog.date`를 기준으로 오래된 두 글을 선택한다.

| 순서 | 게시 시각 | 글 |
|---:|---|---|
| 1 | `2026-05-18T01:00:00+09:00` | AI와 3개월 동안 키운 대규모 Kotlin 라이브러리 생태계 |
| 2 | `2026-05-18T02:00:00+09:00` | AI와 일하는 환경을 인프라로 만들기 |

첫 번째 글은 공유 hero만 사용하므로 다이어그램 변경 대상이 없다. 두 번째 글은 locale별 기술
다이어그램을 이미 갖고 있지만 현재 자산이 밝은 스타일이므로, 한국어 문구를 교정하면서 한·영 자산을
같은 dark style로 다시 설계한다.

## 한국어 교정 원칙

### 의미 보존 장부

각 글을 고치기 전에 다음 항목을 바꾸지 않을 정보로 정리한다.

- 고유명사와 기술 식별자
- 숫자, 기간, 버전, 명령과 경로
- 원인과 결과의 관계
- 인용과 링크가 뒷받침하는 주장
- 글의 문단 순서와 결론

교정 뒤에는 이 장부와 대조해 내용이 추가되거나 빠지지 않았는지 확인한다.

### 표현 기준

- 구어체가 아니라 기술 글과 보고서에 어울리는 문장으로 쓴다.
- 영어 어순을 그대로 옮긴 문장과 불필요한 피동형을 줄인다.
- 추상 명사를 연속해서 나열하지 않고 주체와 행위를 분명히 한다.
- 기술 용어가 아닌 표현은 자연스러운 한국어로 바꾼다.
- `값싼 검사`처럼 일상어로 들리는 표현은 문맥에 맞는 `저비용 검사` 같은 용어로 고친다.
- 같은 의미를 되풀이하는 문장과 문단은 합치되, 근거와 예시는 삭제하지 않는다.
- 한 문장에 여러 판단이 겹치면 문장을 나눠 논리 순서를 드러낸다.

## 다이어그램 처리 원칙

### 대상 판정

다음 figure class에 속하는 기술 다이어그램·차트·시퀀스 그림을 대상으로 한다.

- `bt4k-architecture`
- `bt4k-chart`
- `bt4k-sequence`

`bt4k-blog-hero`, `bt4k-post-hero`, 장식 이미지와 일반 스크린샷은 제외한다.

### locale 분리

기술 다이어그램에 독자용 텍스트가 있으면 영어와 한국어 SVG·PNG를 각각 유지한다.

```text
public/assets/<stem>-en.svg
public/assets/<stem>-en.png
public/assets/<stem>-ko.svg
public/assets/<stem>-ko.png
```

영어 글은 `-en.png`, 한국어 글은 `-ko.png`만 참조한다. 한 locale의 다이어그램을 다른 locale의
글이 공유하지 않는다. 이번 배치의 `ai-collaboration-process`는 이미 이 명명 규칙을 따르므로 파일명은
유지하고 시각 설계와 문구만 갱신한다.

### 번역과 교정 범위

다음 독자용 문구를 본문과 함께 교정한다.

- 제목과 부제
- 컴포넌트 제목과 설명
- 연결선 라벨
- 단계, 영역과 계층 이름
- 범례, 축 설명, footer와 주석
- MDX의 `alt`, `title`과 캡션

클래스, 함수, API 경로, 설정 키, 명령, 코드와 제품 이름은 그대로 보존한다. 한국어 설명과 식별자가 한
문장에 섞여 읽기 어려우면 줄이나 시각 계층을 분리한다.

### 시각 설계

- 짙은 남색·청록 계열 배경과 밝은 본문색을 사용해 기존 dark technical diagram 계열에 맞춘다.
- 한국어는 `goorm Sans`와 `goorm Sans Code`, 영어는 `Architects Daughter`와 `Comic Mono`를
  사용한다.
- 번역한 문구를 맞추려고 글꼴을 과도하게 줄이지 않고 카드와 canvas 크기를 조정한다.
- 연결선은 카드와 라벨을 침범하지 않으며 같은 역할의 화살촉 크기와 방향을 일치시킨다.
- SVG를 원본으로 유지하고 CairoSVG `-s 2`로 PNG를 만든다.
- 한 자산씩 SVG 작성, PNG 렌더링, 자동 검사, 전체 크기 시각 검토를 마친 뒤 다음 자산으로 이동한다.

## 1차 배치의 다이어그램 설계

`ai-collaboration-process`는 Goal, Context, Routing, Execution, Memory, Verification이 반복 가능한
협업 기반을 이루는 과정을 보여준다. 밝은 배경의 기존 구도와 핵심 관계는 유지하되 다음 기준으로
dark style을 적용한다.

- 제목과 부제에서 “운영 루프”의 목적을 먼저 드러낸다.
- 여섯 단계는 같은 시각 계층을 사용하되 단계별 역할은 색상과 번호로 구분한다.
- 단계 사이 연결은 흐름의 방향을 명확히 표시한다.
- footer의 축적 규칙은 작은 각주가 아니라 읽을 수 있는 독립 영역으로 둔다.
- 한국어의 `config`, `workflow`, `skill`, `memory`는 실제 운영 표면을 가리키는 식별자이므로
  임의 번역하지 않고 문장만 자연스럽게 다듬는다.
- 영어와 한국어 다이어그램의 주장, 단계 수와 관계는 같게 유지한다.

## 체크리스트 개선 방식

본문을 고치면서 발견한 모든 표현을 곧바로 전역 규칙으로 만들지는 않는다. 다음 조건 중 하나를 만족할 때
체크리스트 후보로 채택한다.

1. 서로 다른 두 글 이상에서 같은 유형의 문제가 반복된다.
2. 한 번만 나타났더라도 기존 체크리스트가 놓치는 중대한 의미 왜곡이나 문서 품질 문제가 확인된다.

후보를 `bluetape-writer`에 반영할 때는 `writing-skills`와 TDD 절차를 따른다.

1. 기존 체크리스트만 제공한 압박 시나리오에서 문제를 놓치는 RED 기준을 기록한다.
2. 반복 문제를 막는 최소 규칙과 예시만 추가한다.
3. 같은 시나리오와 반대 사례를 다시 실행해 GREEN 결과를 확인한다.
4. `~/.local/share/chezmoi`의 관리 원본을 먼저 수정한다.
5. `chezmoi apply` 뒤 관리 원본, 렌더링 결과와 live skill의 동등성을 검증한다.
6. skill 변경은 블로그 저장소 변경과 분리해 독립적으로 검토하고 커밋한다.

## 작업 순서

1. 두 글의 의미 보존 장부와 다이어그램 목록을 확정한다.
2. 첫 번째 글을 교정하고 사실·링크·식별자 보존 여부를 확인한다.
3. 두 번째 글의 본문과 다이어그램 문구를 함께 교정한다.
4. `ai-collaboration-process` 한·영 SVG를 dark style로 갱신한다.
5. SVG에서 한·영 PNG를 다시 렌더링하고 자동 검사와 시각 검토를 수행한다.
6. 두 글에서 반복된 교정 문제를 분류한다.
7. 기준을 충족한 항목이 있으면 `bluetape-writer` 체크리스트를 RED/GREEN 방식으로 개선한다.
8. 사이트 빌드와 로컬 페이지를 확인하고 사용자 검토를 받는다.
9. 사용자 승인 뒤 PR을 만들며 병합과 배포는 별도 승인으로 남긴다.

## 검증 기준

- 교정 전후에 숫자, 코드, 식별자, URL과 기술적 주장이 일치한다.
- 두 글이 기술 글과 보고서에 적합한 자연스러운 한국어로 읽힌다.
- 본문, 캡션, 대체 텍스트와 다이어그램이 같은 용어를 사용한다.
- 한국어 글은 한국어 다이어그램, 영어 글은 영어 다이어그램을 참조한다.
- SVG는 XML, 텍스트 정규화, 연결선, 기하, endpoint와 모서리 검사를 통과한다.
- PNG는 CairoSVG `-s 2` 결과이며 전체 크기에서 잘림, 겹침과 지나치게 작은 글자가 없다.
- 기술 다이어그램의 제목과 크게 보기 UI가 유지된다.
- `git diff --check`, 관련 테스트와 `npm run build`가 통과한다.
- 로컬 한국어 글 두 편의 본문과 다이어그램을 직접 확인한다.
- 체크리스트를 바꾼 경우 RED 재현과 GREEN 검증, chezmoi source/live 동등성이 확인된다.

## 후속 배치

1차 배치가 승인·병합된 뒤 다시 `blog.date`를 조회해 아직 교정하지 않은 가장 오래된 두 글을 선택한다.
배치마다 같은 설계 원칙과 검증 기준을 적용하되, 다이어그램 유무와 locale 상태는 매번 다시 조사한다.
