# 이미지 인텔리전스 Part 2: 입력 자격 판정과 단일 디코딩 설계

## 상태

- 대상 이슈: [#201](https://github.com/bluetape4k/bluetape4k.github.io/issues/201)
- 시리즈: Image Intelligence API
- 편: Part 2
- 작업 유형: Type E 문서 작업
- 공개 범위: 한국어와 영어 블로그 글, 기술 다이어그램
- 전달 범위: PR까지. 병합과 배포는 별도 승인을 받는다.

## 배경

Part 1은 방문증 이미지 한 장에서 OCR, 객체 검출, 바코드·QR 판독을 함께 수행하는 서비스의 전체 경계를
설명했다. Part 2는 여러 분석기를 실행하기 전에 공통 입력 경계가 무엇을 판정해야 하는지, 그리고 통과한
이미지를 왜 한 번만 디코딩해야 하는지에 집중한다.

기존 공개 글에는 OCR 업로드 제한, 큰 이미지의 메모리 비용, 네이티브 OCR 운영 조건, 일반적인 API 입력
경계가 이미 설명되어 있다. 따라서 이번 글은 검증 항목을 다시 나열하는 데 그치지 않고, 여러 분석기가
공유하는 입력 자격 판정과 단일 디코딩을 하나의 서비스 설계 경계로 설명한다.

## 독자가 해결할 문제

한 업로드를 OCR, 객체 검출, QR 판독기가 각각 다시 읽고 검증하고 디코딩하면 다음 문제가 생긴다.

1. 분석기마다 지원 형식과 크기 제한을 다르게 해석할 수 있다.
2. 같은 압축 바이트를 여러 번 디코딩해 CPU와 메모리를 반복해서 사용한다.
3. 한 분석기는 요청을 거부하고 다른 분석기는 실행하는 모순된 상태가 생길 수 있다.
4. 잘못된 입력과 정상 입력의 분석 실패가 같은 오류로 섞인다.

독자는 글을 읽은 뒤 “분석을 시작할 수 있는 입력인가?”라는 질문을 공통 경계에서 한 번만 판정하고,
그 결과인 불변 이미지 객체를 여러 분석기에 전달하는 이유와 구현 순서를 설명할 수 있어야 한다.

## 중심 메시지

> 입력 자격 판정은 이미지에서 무엇을 찾을 수 있는지 결정하지 않는다. 비용이 큰 분석 작업을 시작해도
> 되는 입력인지 판정하고, 통과한 바이트를 한 번만 디코딩해 모든 분석기가 같은 이미지를 보게 한다.

입력 자격 판정은 OCR 인식률, 얼굴 존재 여부, QR 포함 여부를 판단하지 않는다. 이런 값은 각 분석기가
반환할 정상적인 사실 또는 빈 결과다. 공통 경계가 업무 결과까지 판단하면 “QR이 없는 이미지”와
“이미지로 처리할 수 없는 요청”이 같은 실패로 바뀐다.

## 구현 근거

주요 근거는 `bluetape4k-image`의
`examples/spring-boot-image-intelligence-api` 모듈이다.

- `ImageUploadQualifier`
  - 빈 multipart 입력을 거부한다.
  - 선언된 미디어 타입을 PNG, JPEG, WebP로 제한한다.
  - multipart가 보고한 크기와 실제로 읽은 바이트 크기를 모두 제한한다.
  - PNG, JPEG, WebP 파일 시그니처를 직접 확인한다.
  - 선언된 미디어 타입과 실제 이미지 형식이 같은지 확인한다.
  - 이미지 헤더에서 가로·세로 길이와 전체 픽셀 수를 조사한다.
  - 한 변과 전체 픽셀 수 제한을 디코딩 전에 적용한다.
  - 통과한 바이트를 `ImmutableImage`로 한 번 디코딩한다.
- `ImageUploadQualifierTest`
  - 정상 PNG는 정확히 한 번 디코딩된다.
  - 미디어 타입, 크기, 이미지 크기 제한에 걸린 입력은 디코딩되지 않는다.
  - 디코더 내부 오류는 외부에 노출되지 않는 안정적인 오류로 바뀐다.
  - 업로드 읽기 취소는 입력 오류로 바꾸지 않고 다시 전파한다.
- `ImageIntelligenceService`
  - `QualifiedImage.image`을 분석 흐름에 전달한다.
  - OCR, 객체 검출, 바코드·QR 경로가 같은 불변 이미지 객체를 읽는다.

## 설명할 처리 순서

글에서는 다음 순서를 비용과 신뢰 경계 관점에서 설명한다.

1. 빈 입력을 거부한다.
2. 선언된 미디어 타입이 지원 범위에 있는지 확인한다.
3. multipart가 보고한 압축 크기를 먼저 제한한다.
4. 업로드 바이트를 한 번 읽고 실제 크기를 다시 제한한다.
5. 파일 시그니처로 실제 이미지 형식을 확인한다.
6. 선언된 형식과 실제 형식이 같은지 확인한다.
7. 헤더에서 이미지 크기를 조사하고 한 변과 전체 픽셀 수를 제한한다.
8. 통과한 바이트를 `ImmutableImage`로 한 번 디코딩한다.
9. 같은 불변 이미지를 OCR, 객체 검출, 바코드·QR 경로에 전달한다.

이 순서에서 앞 단계가 실패하면 뒤의 비싼 작업은 실행하지 않는다. 성공 경로에서는 디코딩 횟수가 1이고,
입력 거부 경로에서는 0이라는 테스트 관점을 함께 설명한다.

## 글 구성

### 1. 같은 이미지를 세 번 검증하면 경계도 세 개가 된다

방문증 이미지를 각 분석기가 따로 읽는 단순 구현으로 문제를 시작한다. 반복 디코딩 비용뿐 아니라 분석기별
판정 불일치가 더 큰 문제임을 보여준다.

### 2. 입력 자격과 분석 결과를 분리한다

입력 자격 판정이 답해야 할 질문과 답하지 말아야 할 질문을 표로 비교한다.

| 입력 자격 판정 | 각 분석기의 결과 |
|---|---|
| 실제 지원 이미지 형식인가 | 읽을 수 있는 글자가 있는가 |
| 압축 크기 제한 안에 있는가 | 얼굴이나 민감 영역이 있는가 |
| 이미지 크기와 픽셀 수가 제한 안에 있는가 | QR 값이 있는가 |
| 전체 디코딩이 가능한가 | 결과가 비었거나 분석기가 실패했는가 |

### 3. 싼 검사부터 수행하고 디코딩은 마지막에 한 번만 한다

`ImageUploadQualifier`의 처리 순서를 짧은 의사코드로 보여주고 각 단계가 다음 비용을 막는 이유를 설명한다.
multipart 보고 크기와 실제 바이트 크기를 모두 확인하는 이유, 압축 크기와 디코딩된 픽셀 수를 함께
제한하는 이유도 포함한다.

### 4. 파일 이름과 MIME 선언을 신뢰하지 않는다

확장자보다 실제 파일 시그니처를 확인하고, 선언된 미디어 타입과 실제 형식이 다르면 분석 전에 거부하는
이유를 설명한다. 이 부분은 보안 공격 목록으로 확장하지 않고 서비스 계약의 일관성에 집중한다.

### 5. 입력을 통과시키면 모든 분석기가 같은 이미지를 본다

`QualifiedImage`가 미디어 타입, 이미지 크기, 한 번 디코딩한 `ImmutableImage`를 묶는 역할을 설명한다.
각 분석기가 multipart나 원본 바이트를 다시 읽지 않는다는 불변식을 강조한다.

### 6. 테스트는 정상 결과보다 실행하지 않은 작업을 증명한다

정상 입력의 디코딩 횟수 1과 거부 입력의 디코딩 횟수 0을 중심으로 테스트를 설명한다. 디코더 내부 메시지를
숨기는 오류 정규화와 `CancellationException` 전파도 함께 다룬다.

### 7. 실패 응답은 클라이언트가 다음 행동을 정하게 한다

현재 구현의 안정적인 `reasonCode`와 HTTP 응답을 표로 정리한다. `400`과 `413`을 구분하되 OCR 실행 실패나
부분 실패 계약은 Part 3과 Part 6에 남긴다.

### 8. 마무리와 다음 편

공통 입력 경계와 단일 디코딩이 OCR, 객체 검출, QR 분석의 공통 출발점이라는 결론을 내린다. Part 3의 OCR
처리 경로로 연결하고 Part 1과 Part 3 링크를 함께 제공한다.

## 시각 자료

### 대표 이미지

Part 1과 같은 3D 작업대 계열을 사용한다. 한 방문증 업로드가 검수대를 통과해 하나의 이미지 객체로 바뀌고,
세 분석 작업대로 전달되는 장면을 단순하게 표현한다. 대표 이미지는 기술 다이어그램 확대 대상에서 제외한다.

### 다이어그램 1: 입력 자격 판정의 수직 흐름

- 종류: flow-style architecture
- 방향: 위에서 아래로 흐르는 수직 구성
- 흐름:
  - multipart 업로드
  - 선언 미디어 타입과 보고 크기
  - 실제 바이트와 파일 시그니처
  - 가로·세로와 전체 픽셀 수
  - 단일 디코딩
  - `QualifiedImage`
- 각 거부 지점은 다음 단계의 비싼 작업을 실행하지 않는다는 사실을 보여준다.
- 한국어와 영어 SVG·PNG를 별도로 만든다.

### 다이어그램 2: 반복 디코딩과 공통 단일 디코딩 비교

- 종류: static architecture comparison
- 왼쪽:
  - OCR, 객체 검출, QR 경로가 업로드를 각각 읽고 디코딩
  - 중복 비용과 서로 다른 입력 판정
- 오른쪽:
  - `ImageUploadQualifier`가 입력을 한 번 판정하고 한 번 디코딩
  - 하나의 `ImmutableImage`를 세 경로가 읽기 전용으로 공유
- 컴포넌트를 연결하는 선은 카드와 충분히 떨어뜨리고 같은 역할의 화살촉 크기와 방향을 일치시킨다.
- 한국어와 영어 SVG·PNG를 별도로 만든다.

두 다이어그램 모두 Part 1의 dark style을 따르고 기술 다이어그램 제목과 크게 보기 UI를 제공한다. SVG를
원본으로 유지하되 CairoSVG로 만든 PNG를 최종 판정 기준으로 삼는다.

## 기존 글과의 중복 방지

- [OCR 서비스를 실전에서 운영하기]
  - 업로드 제한과 네이티브 OCR, 전처리 비용, OCR 실패 응답의 상세 설명은 반복하지 않는다.
  - 이번 글에서는 여러 분석기가 공유하는 입력 경계와 단일 디코딩 근거만 확장한다.
- [Kotlin API 입력 경계]
  - 이미지 외 텍스트·파일 입력의 일반적인 방어 원칙은 반복하지 않는다.
  - 이번 글에서는 이미지 시그니처, 픽셀 예산, 분석기 간 불변 이미지 공유에 집중한다.
- [Pure JVM에서 libvips로]
  - 이미지 처리 backend 성능 수치와 선택 기준은 반복하지 않는다.
  - 디코딩과 전처리가 공짜가 아니라는 배경 자료로만 연결한다.

## 한국어와 영어 동등성

한국어 글을 먼저 작성하고 로컬에서 검토받는다. 승인된 한국어의 주장과 구조를 기준으로 영어 글을 작성한다.
영문은 한국어 어순을 그대로 옮기지 않고 자연스러운 기술 영어로 쓴다. 두 언어는 다음 항목을 맞춘다.

- Part 번호와 경로
- 주장과 구현 근거
- 표와 의사코드
- 소스 링크
- 다이어그램 구도와 의미
- Part 1·2·3 시리즈 탐색

## 최종 한국어 교정

PR 전에 한국어 글 전체를 다시 읽고 다음 표현을 고친다.

- 영어 어순을 그대로 옮긴 문장
- 불필요한 명사 나열과 피동형
- 기술 용어가 아닌데 영어로 남은 표현
- 한 문장에 여러 판단이 겹친 긴 문장
- 같은 의미를 되풀이하는 문단

교정 과정에서는 API 이름, 식별자, 숫자, 오류 코드, 링크와 기술적 의미를 바꾸지 않는다.

## 검증 기준

- 글의 모든 구현 주장은 현재 `develop`의 예제 코드 또는 테스트에 근거한다.
- 한국어 글을 먼저 로컬에서 검토받는다.
- 모든 SVG는 XML 검증을 통과한다.
- 모든 PNG는 CairoSVG `-s 2`로 만들고 전체 크기로 직접 확인한다.
- 화살촉, 연결선, 라벨, 카드 간격, 글꼴, 여백 검사를 통과한다.
- 기술 다이어그램은 제목과 크게 보기 UI가 작동한다.
- 한국어와 영어 글의 링크, 이미지, Part 번호, 시리즈 탐색이 일치한다.
- `git diff --check`와 `npm run build`를 통과한다.
- 한국어 번역체 교정 후 의미 보존을 다시 확인한다.
- PR 본문의 마지막 `##` 절은 `## DoD Status`다.
