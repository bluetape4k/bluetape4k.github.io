# 고객 희망 내원 날짜와 예약 확정 글 설계

> 기준일: 2026-08-13
> 관리 항목: `clinic-appointment` Epic #275, Issue #282
> 구현 근거: `clinic-appointment` Issue #184, PR #197
> 작업 유형: Type E 기술문서

## 1. 독자와 목적

대상 독자는 병원 예약 업무를 설계하거나 운영하는 상품기획자, 상담·운영 담당자,
개발자다. 환자가 희망한 날짜를 그대로 예약으로 저장하면 왜 변경, 동의, 자원 충돌을
안전하게 다룰 수 없는지 하나의 환자 사례로 설명한다.

글의 중심 문장은 다음과 같다.

> 고객 희망 내원 날짜는 일정 의도이고, 예약 확정은 구체적인 제안·자원 점유·병원 승인·해당 제안에 대한 고객 동의가 결합된 결과다.

## 2. 용어

- `고객 희망 날짜`, `고객 희망일`은 사용하지 않고 `고객 희망 내원 날짜`로 통일한다.
- `commitment`의 상태·행위는 독자 문장에서 `예약 확정`으로 쓴다. 확정 결과의 실제
  날짜와 시간을 가리킬 때만 `확정된 예약일시`로 쓰고, 코드·모델은
  `AppointmentCommitment`로 유지한다.
- `proposal`은 `제안`, `allocation`은 `자원 점유`로 쓴다.
- `event`는 시스템 메시지일 때만 `이벤트`로 쓰고, 환자의 행동은 `행위`로 쓴다.
- `capacity ceiling`은 독자 문장에서 `요청당 처리 한도`로 풀어 쓴다. 이 값은 임상적 안전성을
  뜻하지 않고 항목 수·의존 관계 수·탐색 기간처럼 한 요청이 처리할 수 있는 규모를 제한한다.

## 3. 서사 구조

환자 A가 패키지 상품의 첫 방문을 예약하는 사례를 따른다.

1. 환자 A가 `8월 20일 오전`을 고객 희망 내원 날짜로 제출한다.
2. 예약서비스가 계획 버전, 상품 정의 해시, 요청당 처리 한도, 병원 정책을 검증한다.
3. 조건에 따라 `PROPOSED` 또는 유효 시간이 있는 `HELD` 상태가 된다.
4. 병원이 같은 조건을 승인하면 원 요청에 결합된 동의를 사용해 `CONFIRMED`가 된다.
5. 시간·항목·자원이 달라지면 새 제안을 만들고 고객의 새 동의를 받는다.
6. 변경 제안이 거절·만료되거나 새 자원 점유에 실패해도 기존 예약의 확정 상태와 예약일시는 유지한다.

## 4. 기술적 구분

| 개념 | 의미 | 아직 보장하지 않는 것 |
| --- | --- | --- |
| `PROPOSED` | 일정 후보가 기록됐지만 자원과 합의가 확정되지 않음 | 방문 보장, 자원 점유 |
| `HELD` | 제한된 시간 동안 필요한 자원을 선점함 | 최종 합의, 영구 점유 |
| `CONFIRMED` | 구체적인 제안과 해당 제안에 대한 고객 동의, 자원 점유가 한 트랜잭션으로 결합됨 | 진료 완료 |

`AppointmentState`와 commitment 상태를 섞지 않는다. 전자는 방문의 접수·진행·완료
축이고, 후자는 고객과 병원이 어느 일정에 합의했는지를 나타내는 축이다.

## 5. 시각 자료

### 5.1 환자 A의 예약 확정 흐름

환자 A, 고객 채널, 예약서비스, 병원 운영자, 자원 원장을 세로 participant로 두는
시퀀스 다이어그램을 만든다. `PROPOSED → HELD → CONFIRMED`를 시간 순서로 보여주되,
상태를 단순한 직선 단계로 오해하지 않도록 다음 분기를 명시한다.

- 동일 조건 승인: 기존 동의 증빙과 정확히 결합해 확정
- 조건 변경: 새 제안과 새 동의 필요
- 거절·만료·자원 충돌: 확정하지 않음

### 5.2 서비스별 책임 경계

고객 채널은 희망과 동의 증빙을 전달하고, 예약서비스는 제안·상태·적용 정책 기록을
소유하며, 병원 운영은 승인·대안을 제시하고, 자원 원장은 실제 점유 가능성을 판정한다.
임상서비스는 완료 사실을 소유하므로 이 확정 흐름의 밖에 둔다.
